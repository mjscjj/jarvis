# PRD 评审

读取用户或 Task 的完整指令、背景及同一 ScheduledTask 的历史结果，确认产品范围、关注点和交付要求。指定单篇文档时直接评审该文档；指定群或会议时按下面的方法定位批次。具体群、会议类型和时间范围由任务提供。

需要查找材料、读取文档与评论、保存证据或交付飞书报告时，读取 `product-tools`；工具操作方法由它维护，本 Skill 负责评审判断与交付要求。

## 定位与阅读

优先按 Task 指定的会议、批次或本周待评审清单定位材料；未指定批次时，才从目标群最新消息向前找最近一次相关产品会议。保留会议或批次时间、标题和来源消息，确认范围后停止；讨论旧会议时沿引用追溯，归属不明的会议不合并。

会前运行时，从本周通知及关联的需求池、收集表确认待评审 PRD，按运行时可读版本生成报告，注明材料尚可变更；不等待会后结论，不把历史最近一场替代本周批次。本周材料未就绪或没有需求时如实记录，未读材料列为未覆盖。

展开本次会议的线程、卡片、需求清单及 Meego、One Pager、Wiki 链接，找齐 PRD，按真实文档 token 去重，保留需求名、原链接和来源消息。历史材料仅作为必要引用。

## 阅读与评审方法

完整阅读每份 PRD 的正文、表格、关键图示和必要引用，解释它要解决谁的什么问题、目标与非目标、用户流程、业务规则、关键决策及依赖。区分原文事实、自己的理解和待确认事项，每个关键结论都能追溯到材料。

结合产品阶段和任务关注点，检查问题与目标是否一致，正常与异常流程是否闭合，规则是否矛盾，指标是否能衡量目标，依赖、验收标准和发布条件是否明确。只报告对当前范围有实际影响的问题，不要求固定章节，不默认引入复杂权限或流程引擎。引用未读、权限不足或材料不存在属于未覆盖范围，不能直接当成产品缺陷。

每个发现说明触发场景、原文依据、具体影响和可行建议，区分已确认缺陷、需业务决策的问题与可选改善。证据不足时明确不确定性，不编造严重问题或为数量重复表述。

## Claire 高频关注点

评审时逐项对照下列 Principal 高频关注点，主动在报告里前置回答；PRD 未讲清的即列为待澄清或待决策，不替它假设。以下按真实评论证据校准，证据底稿见 `docs/summery/group-prd-comments/`：

1. 必要性与目标人群：为什么做、谁会不用、与本季度目标/KR 的关系，方案未 sign off 时先判断哪些是基建；区分常规存量与本期增量，不拿常规工作凑数。
2. 核心逻辑质疑：不接受表面结论，追问底层逻辑与概念归属是否成立（如"认领不建联有没有用""这是固定指标还是活动页概念""是活动还是政策"）。
3. 交互与异常边界：反向和异常路径是否定义（可否关闭/撤销、为何互斥、状态变化时机、动效是否合理）。
4. 准入准出与存量兜底：存量对象如何迁移、准入/准出与退出逻辑、拒绝或不符合预期时的分支兜底。
5. 数据可见性与埋点：功能上线后运营/管理者从哪看数据、关键结论有无数据支撑、现状值与目标基线怎么算、是否达预期。
6. 审批/规则一致性：方案规则是否与既有决策口径一致，避免"每个都要批""争议才批"这类前后不一致。
7. 跨团队/平台对齐与复用：涉及哪些团队、是否漏 involve 相关方、与相邻平台/产品的边界与定位（如客服平台、Bax）、单点能力能否复用或沉淀为通用能力。
8. 含糊即要求讲清或举例：抽象描述、无指导意义的文案、模糊指标一律要求补例子、补细节或量化，反对空泛表述；样例最好基于真实用户/主播调研。
9. 可验证与工具化：倾向把逻辑做成可自助验证或可视化的产物（如输入 uid/agency id 看匹配结果的表或 agent、按流程画跟进图或时间线）。

## 报告与通知

会议批次评审默认每份可读 PRD 交付一份独立飞书报告，标题含需求名和会议，附原文链接及读取版本或时间。单篇评审按用户或 Task 指定的渠道交付；未要求飞书报告或通知时，在当前对话或 Task 输出结论。取证原始返回、下载正文、生成稿、创建/更新回读、通知 payload 与回执建议存入 `~/tmp/jarvis/prd-review/<task-or-date>/`，不进入 Git；只有用户明确要求长期保留的最终报告才提炼后放入 `docs/summery/`。篇幅适中，以读者能理解并采取行动为准：

- 开头用两三句话交代必要背景、总体判断及优先处理事项。
- 关键问题按影响排序，每项用一个短段说明：什么场景会遇到问题、原文如何规定或哪里存在缺口、为什么影响交付、建议如何处理。就近附证据链接，正文保留必要依据，不能只给结论让读者自行翻原文。
- 区分已确认问题与待决策；保留会影响实施的边界和未覆盖范围。合并同根因，不设固定问题数或字数上限，不遗漏独立的重要发现，也不凑项。

删除重复背景、同一问题的多次总结和通用检查清单，保留完整判断依据。简单问题简述，复杂问题展开必要推理；不要压成只有“问题 → 建议”的提纲。详细取证过程可留在 Task 或 `~/tmp/jarvis/prd-review/` 本地工作区。

交付多篇飞书报告时另建批次汇总：一句话总评加一张表，每份 PRD 仅列名称、最关键结论和报告链接。不可读材料标明原因，不建空报告。不重复单篇分析。

会议批次评审及明确要求通知的任务，在读回报告标题和关键内容后通知 Principal：简报发现、完成、未读数量，附汇总和各报告链接。按 `product-tools` 核验回执与记录 effects。

## 重跑与边界

先核对历史运行及已有报告、通知。Task 失败或无结果不代表没有外部产物；中断后读回并复用，只补缺失步骤。

出现新会议则处理新会议；同一会议按 token、版本或更新时间核对变化，只补新增 PRD、更新实质变化的报告及汇总。材料无变化且用户没有新增交付要求时，记录“无更新”结束。用户要求精简等修订时更新已有报告，不另建副本；通知按本次交付去重。

单篇周期复核也比较同一调度的历史结果，确认旧问题是否解决、是否引入新问题；无法取得旧版本时说明仅做当前版本评审，不声称完成差异审查。评审完成不代表建议已落地。

源 PRD 只读；本 Skill 仅交付报告、Principal 通知及运行记录，不修改需求、OKR、Meego 或群消息。
