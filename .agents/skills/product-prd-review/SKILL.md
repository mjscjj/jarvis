# 产品会议 PRD Review

读取 Task 完整指令、背景及同一 ScheduledTask 的历史结果，确认目标群、产品范围和交付要求。具体群、会议类型和时间范围由任务提供。

## 定位与阅读

使用 lark-cli 的 user 身份，优先按 Task 指定的会议、批次或本周待评审清单定位材料；未指定时，才从目标群最新消息向前找最近一次相关产品会议。保留会议或批次时间、标题和来源消息，确认范围后停止；讨论旧会议时沿引用追溯，归属不明的会议不合并。

会前运行时，从本周通知及关联的需求池、收集表确认待评审 PRD，按运行时可读版本生成报告，注明材料尚可变更；不等待会后结论，不把历史最近一场替代本周批次。本周材料未就绪或没有需求时如实记录，未读材料列为未覆盖。

展开本次会议的线程、卡片、需求清单及 Meego、One Pager、Wiki 链接，找齐 PRD，按真实文档 token 去重，保留需求名、原链接和来源消息。历史材料仅作为必要引用。

按资源类型使用 lark-im、lark-doc、lark-drive 等 Skill。权限不足时保留来源和原始错误，继续处理其他文档；不凭标题推测正文。下载附件前先创建目录，再将其设为 workdir。

每份 PRD 按 `product-doc-read` 和 `product-doc-review` 完成阅读与评审，包括表格、关键图示和必要引用。评审方法由这两份 Skill 维护。

评审时逐项对照下列 Principal 高频关注点，主动在报告里前置回答；PRD 未讲清的即列为待澄清或待决策，不替它假设：

1. 必要性与优先级：为什么做、谁会不用、与本季度目标/KR 的关系，区分常规存量与本期增量，不拿常规工作凑数。
2. 数据与预期：关键结论有无数据支撑，现状值、目标基线怎么算的、是否达预期。
3. 进展与时间线：当前进展、上线时间，滞后或"预计本周"类模糊排期要追问。
4. 交互与异常边界：反向和异常路径是否定义（可否关闭/撤销、为何互斥、状态变化时机）。
5. 存量、准出与兜底：存量对象如何处理、准出/退出逻辑、不符合预期时的兜底。
6. 逻辑与归因：因果如何论证、指标如何归因、分类与颗粒度是否自洽。
7. 跨团队与职责：涉及哪些团队、是否漏 involve 相关方、能力是否该产品化。
8. 能力复用与平台化：单点能力能否复用到其他场景（如 Rena/Bax）、是否沉淀为通用能力。
9. 调研与样例支撑：是否有样例、可否模拟、是否基于真实用户/主播调研，反对空泛描述。

## 报告与通知

每份可读 PRD 交付一份独立飞书报告，标题含需求名和会议，附原文链接及读取版本或时间。篇幅适中，以读者能理解并采取行动为准：

- 开头用两三句话交代必要背景、总体判断及优先处理事项。
- 关键问题按影响排序，每项用一个短段说明：什么场景会遇到问题、原文如何规定或哪里存在缺口、为什么影响交付、建议如何处理。就近附证据链接，正文保留必要依据，不能只给结论让读者自行翻原文。
- 区分已确认问题与待决策；保留会影响实施的边界和未覆盖范围。合并同根因，不设固定问题数或字数上限，不遗漏独立的重要发现，也不凑项。

删除重复背景、同一问题的多次总结和通用检查清单，保留完整判断依据。简单问题简述，复杂问题展开必要推理；不要压成只有“问题 → 建议”的提纲。详细取证过程可留在 Task 或本地材料。

多篇时另建批次汇总：一句话总评加一张表，每份 PRD 仅列名称、最关键结论和报告链接。不可读材料标明原因，不建空报告。不重复单篇分析。

读回报告标题和关键内容后，用 `jarvis-tools notice-principal` 由 Bot 通知 Principal：简报发现、完成、未读数量，附汇总和各报告链接。以会议稳定标识和文档集合派生幂等键，核验发送回执，将文档与消息记入本次执行结果的 effects。

## 重跑与边界

先核对历史运行及已有报告、通知。Task 失败或无结果不代表没有外部产物；中断后读回并复用，只补缺失步骤。

出现新会议则处理新会议；同一会议按 token、版本或更新时间核对变化，只补新增 PRD、更新实质变化的报告及汇总。材料无变化且用户没有新增交付要求时，记录“无更新”结束。用户要求精简等修订时更新已有报告，不另建副本；通知按本次交付去重。

源 PRD 只读；本 Skill 仅交付报告、Principal 通知及运行记录，不修改需求、OKR、Meego 或群消息。
