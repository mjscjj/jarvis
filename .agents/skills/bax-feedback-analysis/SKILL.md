# Bax 问题反馈分析

把“Bax- 问题反馈群”在指定时间段内的反馈整理为结构化、可追溯的中文飞书文档。

## 确认统计范围

1. 确认开始时间、结束时间和时区。用户没有提供开始或结束时间时，先追问，不自行假定日期。
2. 用户只给日期时，按该时区的自然日边界处理；未指定时区时，使用当前运行环境时区。
3. 以原始反馈首次发生时间判断是否纳入。对已纳入反馈，读取统计结束时间之后的后续回复，以判断最终状态和形成完整跟进总结。

## 收集反馈

1. 使用 `lark-im` Skill 定位名称精确匹配“Bax- 问题反馈群”的群聊。多个候选无法可靠区分时，请用户消歧。
2. 拉取统计范围内的全部消息，处理完整分页，并保留消息 ID、发送时间、发送者、正文、回复关系和原始链接。
3. 展开每条候选反馈的完整 topic 回复；没有独立 topic 时保留可追溯到原始反馈的消息链接。
4. 排除 Pulse 诊断机器人创建的周总结消息。遇到 `forwarded_messages` 时先展开并读取转发内容，不根据外层消息猜测。
5. 若消息或回复因权限、分页或接口限制未能完整读取，在文档概览中明确覆盖缺口，不把局部结果表述为全量。

## 抽取独立问题

完整阅读并严格执行 [抽取规则明细](references/extraction-rules.md)。以独立问题而非消息或 topic 数量为最终记录单位：

1. 拆分一个 topic 中彼此独立的问题。
2. 合并同一问题的补充、追问、同步和确认。
3. 去重描述同一对象、现象和处理链路的消息。
4. 为每个问题确定唯一状态、问题分类、问题简述、反馈人、Owner、原始链接和跟进总结。

不得根据参与程度猜测 Owner，也不得根据“处理中”“看一下”“待跟进”等非终态措辞推测解决状态。

## 创建飞书文档

使用 `lark-doc` Skill 创建中文飞书文档。除非用户明确要求 Markdown，否则不要改成交付本地 Markdown 文件。

文档依次包含：

1. **全量概览**：简要说明问题总数、三类状态数量、主要问题分类、处理进展和需关注事项。不要重复逐行内容。
2. **已解决**表格。
3. **无效问题**表格。
4. **未解决**表格。

三张表的列顺序固定为：

1. 问题分类
2. 问题简述
3. 反馈人
4. Owner
5. 飞书 topic 链接
6. AI topic 跟进情况总结

同一张表先按问题分类聚合，同类问题再按原始反馈时间或自然阅读顺序排列。用户当次明确指定语言、字段、摘要风格或排序方式时，以当次要求为准。

没有有效问题时仍创建文档，在概览中写明“本统计周期未发现有效反馈”，并保留三个状态章节。某类没有记录时，在对应章节标注“本周期无记录”，不要虚构表格行。

## 交付检查

创建文档前核对：

- 每条独立问题只出现一次，且恰好落入一种状态。
- 状态和 Owner 严格依据规则中的明确信号。
- 三张表均使用固定六列且列顺序一致。
- 同类问题相邻排列。
- 概览统计与各表实际行数一致。
- 问题简述是一句话，保留关键对象、异常现象和影响。
- 跟进总结只描述已发生事实，没有缺失性占位话术、评价或无依据推断。
- 每条记录的 topic 或消息链接可点击并能追溯到原始反馈。

完成后返回飞书文档链接，并简要说明问题总数、已解决数、无效问题数、未解决数和缺少明确 Owner 的问题数。
