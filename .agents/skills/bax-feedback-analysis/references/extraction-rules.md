# Bax 反馈抽取规则明细

## 独立问题与去重

- 一个 topic 只围绕一个问题时，记录为一条。
- 一个 topic 包含多个彼此独立的问题时，按问题拆成多条，并为拆出的各条复用同一 topic 链接。
- 多条消息只是同一问题的补充、追问、进度同步或确认时，合并为一条。
- 不同消息明显描述同一对象、异常现象和处理链路时，合并去重，不重复记账。
- 没有形成独立 topic、但能明确识别的问题仍记录为一条，并使用原始消息链接。
- 反馈人取原始问题的提出者。合并多条反馈时，取最早提出该独立问题的人；不要把后续跟进人记为反馈人。

## 解决状态

只按明确终态信号判断：

- 出现“你好，已成功解决该问题”或同一上下文中的 `/solve xxxx`，标记为“已解决”。
- 出现“无效问题”或同一上下文中的 `/invalid xxxx`，标记为“无效问题”。
- 未出现以上信号，标记为“未解决”。
- 同一问题多次更新状态时，按时间采用最后一个有效终态信号。

不要把“处理中”“看一下”“待跟进”“已经转交”等措辞当作解决信号。把 `/solve` 后的内容作为解决方式，把 `/invalid` 后的内容作为无效原因，并纳入跟进总结。

## Owner 归因

按以下优先级取 Owner：

1. “你好，已安排 xxx 对该问题进行跟进”中的 `xxx`。
2. “请值周同学 XXX 跟进该体验问题”中的 `XXX`。
3. 两类信号都不存在时留空。

不要根据回复频率、参与程度、角色或经验猜测 Owner。统计所有 Owner 为空的问题，在最终交付说明中给出总数；不要在每行跟进总结中插入“Owner 缺失”等占位描述。

## 问题分类

按用户感知和问题本质归纳稳定、少而清晰的业务类别，例如：

- 告警误报
- 功能异常
- 权限问题
- 数据问题
- 稳定性问题
- 体验问题
- 配置问题
- 集成/接口问题

同一批次中本质相同的问题必须使用同一分类名称，避免用近义词拆散。分类用于归纳，不影响状态或 Owner 的判断。

## 问题简述

- 用一句话概括，保留关键对象、异常现象和影响。
- 不把排查过程、解决方式或无效原因塞进问题简述；这些内容写入跟进总结。
- 不添加 topic 中没有得到支持的范围、原因或影响。

## AI topic 跟进情况总结

只总结 topic 中已经发生的事实，按实际信息优先覆盖：

1. 谁作出响应。
2. 做了什么排查或验证。
3. 是否转交，以及转交给谁。
4. 是否给出原因或处理动作。
5. 最终或当前状态。

使用客观、紧凑的表述。不要写“未看到根因”“暂无有效信息”“未发现 `/solve`”等缺失性或占位式话术。信息有限时，只描述已有沟通或动作，不补充推断。对于已解决或无效问题，将 `/solve` 后的解决方式或 `/invalid` 后的无效原因自然写入总结。

## 时间边界

- 按用户给定时区和起止边界读取消息。
- 用户只给日期时，按该日期的自然日范围处理。
- 以原始反馈首次发生时间决定是否纳入统计。
- 对范围内首次发生的反馈，完整读取范围外的后续 topic 回复，用于确定最后有效状态和总结跟进过程。
- 范围开始前已首次发生、仅在范围内继续回复的问题，不计入本期问题数，除非用户明确改变统计口径。
