# 初始化证据来源

## 时间与身份边界

- 默认窗口：当前时区最近 7 个自然日，报告准确起止时间。
- 所有飞书读取都显式使用本次 `--profile` 和 `--as user`（命令不支持 `--as` 时以 lark-cli schema 为准）。
- 先保存命令的原始成功 JSON，再做派生摘要。错误也单独保存原文，但必须去除 token、device_code 和授权 URL。
- 每个推断引用 `evidence/<file>#<JSON path 或简短定位>`，不要只写“来自飞书”。

## 三层取证

初始化不是固定爬取清单。Agent 先拿稳定锚点，再读取默认 7 天活动面；只有某个候选实体、关系或历史事实仍不确定时，才围绕该候选扩展关键词、文档章节、会话或时间范围。证据足以支持审阅后立即停止扩展，不追求穷举整个飞书历史。

### 稳定锚点

1. `auth status --verify`：确认 user openId、userName、tokenStatus、scope；保存前删除 token 类字段。
2. 本机 Git 身份：读取 `git config user.name`、`git config user.email`，并在当前仓库及已确认项目仓库抽样近期提交，确定可供 `git log --author` 使用的唯一模式。配置与提交不一致或有多个候选时列为未知项，请用户确认，不得猜测。
3. 通讯录当前用户：姓名、部门、职务、企业邮箱等稳定字段。
4. 用户详情：读取 `leader_user_id` 等直属上级字段。现有 shortcut 不足时才用 `lark-openapi-explorer` 找官方通讯录接口。
5. 直属上级详情：只在得到明确 leader id 后查询；跨 app 的 open_id 不能混用。
6. 本人 OKR 文档：用 `drive +search --query "<okr关键词>" --created-by-me --doc-types doc,docx,wiki --sort edit_time` 从本人原始创建的文档中搜索 OKR、目标、关键结果和周期线索；先查 `OKR`，再由 Agent 根据用户语境扩展关键词。按 `has_more` 翻页，保存候选的 URL/token、类型、标题、创建/编辑时间和原始创建者证据。再用 `docs +fetch` 读取候选目录、关键词命中或相关章节，结合正文判断当前有效版本，不按标题机械认定。

### 最近活动面

7. 最近一周本人文档：以本次证据窗口的绝对起止时间运行 `drive +search --query "" --edited-since <from> --edited-until <until> --doc-types doc,docx,wiki --sort edit_time`；按 `has_more` 翻页并按 URL/token 去重，若受当前 `lark-drive` 单轮分页上限中断则保存查询条件和 `page_token` 供下一轮继续，只有 `has_more=false` 才算完整。`my_edit_time` 表示本人参与编辑，因此既覆盖本人原始创建的文档，也保留本人参与撰写的协作文档。再用 `docs +fetch` 读取与项目、职责、决策和未闭环事项相关的章节。
8. 会话列表：按活跃度取群和必要的 p2p，不把所有历史会话当候选。
9. 消息：限定 7 天；优先本人消息、@本人、线程回复及候选群。分页到时间边界，记录是否完整。
10. 群成员：只查进入候选集的群，用于识别长期协作者和 owner。

### 定向扩展

- 候选项目缺少持续目标时，围绕项目名、仓库、owner 或关键文档扩展搜索；仍只有一次性活动就不建 Project。
- 候选人物的职责不清时，只扩展到能判断其是否为关键协作者；不要为了补人物简介搜索无关历史。
- 候选关系缺少双方角色或有效期时，读取直接支持该关系的消息或文档；单条称呼不能建立关系。
- 候选历史事实缺少发生时间或影响时，定向读取原始章节/线程；补不齐就不写 Fact。
- 默认窗口没有覆盖到仍明显有效的项目背景时，可以扩大时间范围，但必须在证据文件与工作稿中记录实际范围和扩大的理由。

每个候选项维护证据覆盖：已读取的来源、未覆盖的分页/时间、原始错误和证据冲突。范围扩大是 Agent 的调查判断，不是必须依次执行的固定阶段。

## 证据强度

- 强：通讯录直属上级字段、当前 OKR、用户本人明确陈述、稳定 repo/项目链接。
- 中：多条独立消息持续指向同一目标、同一协作关系在多个群重复出现。
- 弱：单个群名、一次性会议标题、单条转发、模型仅凭称呼猜测。

只有弱证据时将 `confidence` 设为 `low`，默认不自动写入；可作为 `unknowns` 请用户确认。

## 权限和失败

- 权限错误按 `lark-shared` 处理：user 只增量申请明确缺失的只读 scope；bot 缺权限给后台链接。
- 企业策略不支持 OKR 权限；初始化不得加载 `lark-okr`、调用 OKR API 或申请 OKR scope。OKR 证据的唯一来源是本人撰写且当前身份可读的文档；这条限制优先于 `lark-shared` 的通用缺失 scope 恢复规则。
- 文档搜索为空、搜索分页未覆盖完整、候选正文不可读和确实没有匹配文档，是不同结论。缺少 `search:docs:read` 或文档读取 scope 时记录原始错误并增量申请对应只读权限，不得改走 OKR API。
- API 不提供字段、租户未开放字段和用户确实没有该数据，是三种不同结论。
- 某一来源失败不允许伪装成空数据。工作稿的未知项必须包含来源、原始错误文件和它阻断的判断。
