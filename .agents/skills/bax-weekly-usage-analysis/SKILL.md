# BAX 周度用户对话使用分析

把 BAX AM 一周对话使用变化做成可重复、可追溯的分析。目标不是复述看板，而是回答：

- 本周使用是否真的下降；
- 下降来自数据口径、用户覆盖、使用深度、人群/区域、还是具体场景变化；
- principal 需要知道什么，以及是否需要进一步对外同步。

## 运行范围

1. 解析目标自然周。用户给出日期时，使用该日期所在的周一到周日；用户给出周一日期时直接使用该周。周期触发且没有显式日期时，默认分析触发时刻之前最近一个完整自然周。
2. 默认时区为 Asia/Shanghai，除非用户或调度上下文显式指定其它时区。
3. 比较窗口固定为“目标周”对“前一完整周”，不要把尚未完整的一周与完整周比较。
4. 先确认数据新鲜度：目标周内业务日期必须已经落到最新可用分区；若分区滞后，在报告开头明确写出可覆盖到哪一天，并只对已覆盖区间下结论。

可先本地 dry-run 查询计划：

```bash
bash <skill-dir>/scripts/dry-run.sh [周一 YYYY-MM-DD]
```

dry-run 只打印时间窗口、核心数据源和查询命令模板，不访问 Aeolus、不创建文档、不发送消息。

## 数据源

优先使用新的 BAX AM 用户使用数据集：

- Aeolus dataset `3574811`：`【公会BAX】Agent X Session X message 统计数据集`
- region：`sg`
- site：所有 bytedcli 调用都显式带 `--site i18n-tt`
- 业务日期：优先使用 `min_span_created_time` 转日期
- BAX AM 过滤：`tenant_id_type = 'bax-am'`
- 基础清洗：排除 test/debug/e2e 类 session 或 prompt；不能确认字段时先用字段列表和少量样例核实

旧数据集只作为历史口径对照，不作为 W35 之后的默认周度来源：

- Aeolus dashboard `740208` / sheet `1023684` / dataset `3459500`
- 已知用途：BAX Weekly 旧口径，WAU 以 `role=user` 的 `feishu_open_id` 周去重，Session 以 `session_id` 去重，Message 以 `log_id` 去重
- 已知限制：2026-09-08 调查时只能可靠覆盖到 W34，不能直接代表 2026-08-31 之后的周度情况

详细口径见 [references/metric-contract.md](references/metric-contract.md)。

## 查询步骤

1. 读取字段，确认本次可用维度和指标：

```bash
bytedcli --site i18n-tt --json aeolus dataset-fields -r sg 3574811
```

2. 查询最新分区和业务日期范围。若最新分区存在但业务日期未覆盖目标周，不要把分区日期当成业务日期。
3. 汇总目标周与上一周的核心指标：
   - WAU：按有效用户标识周去重；
   - DAU：按业务日期和有效用户标识日去重，再取日均和每日明细；
   - 会话数：按 `session_id` 去重；
   - 消息数：按 `log_id` 或等价消息标识去重；
   - 缺失用户标识记录数：单独列出，不混进 WAU。
4. 做用户 cohort：
   - retained：上周、本周都活跃；
   - lost：上周活跃、本周未活跃；
   - new：本周活跃、上周未活跃；
   - 分别统计人数、会话、消息和占比。
5. 做人群和场景拆解：
   - 人群优先按部门、区域、国家/地区、用户类型、是否产研拆分；
   - 场景优先按 agent、skill、intent、入口渠道、核心功能拆分；
   - 字段名称不确定时先从 `dataset-fields` 选最贴近含义的字段，不臆造列名。
6. 如果用户要求“不含产研”，按 [references/metric-contract.md](references/metric-contract.md) 中的产研排除口径出一版；没有明确要求时，默认同时给“全量”和“不含产研”差异，避免把产研自测流量和真实 AM 使用混在一起。

## 判断方法

先判断数据质量，再解释业务变化：

1. 数据质量：分区是否新鲜、业务日期是否完整、用户标识是否缺失、test/debug/e2e 是否污染、旧口径和新口径是否混用。
2. 总量变化：WAU、DAU、会话、消息分别给绝对值和环比百分比。指标方向冲突时逐项解释，例如 WAU 下跌但消息上涨通常说明少数重度用户或缺用户标识记录拉高了消息量。
3. 用户覆盖：用 retained/lost/new 解释“少人用了”还是“同一批人用少了”。
4. 人群归因：按净下降贡献排序，指出主要区域/部门是否集中，避免把全局下滑误判成单一区域问题。
5. 场景归因：看哪些 agent/skill/场景贡献最大下降或增长，区分 GTM/触达缺失、功能回归、口径切换和正常场景迁移。
6. 只在有证据时才写“性能不是主因”“某次发布导致下降”这类因果判断；否则写成待验证假设。

## 输出

报告使用中文，默认写在 Task 输出里；只有用户明确要求或当前运行上下文已授权时，才创建飞书文档或发送群消息。

推荐结构：

1. 标题：`BAX AM 周度用户对话使用分析：<目标周>`
2. 范围与覆盖：时间窗口、时区、数据源、最新分区、业务日期覆盖、已知缺口。
3. 一句话结论：先说是否真实下滑和最主要原因。
4. 核心指标表：目标周、上一周、环比、备注。
5. 用户 cohort：retained/lost/new 的人数、会话、消息贡献。
6. 人群拆解：按部门/区域/国家或可用人群字段展示净变化贡献。
7. 场景拆解：按 agent/skill/intent/入口展示净变化贡献。
8. 解释与建议：可立即确认的结论、仍需补证的假设、建议下一步。
9. 证据：Aeolus dataset/report ID、查询时间、查询命令或报告链接。

## 周期运行注意事项

- 本 Skill 是分析流程的唯一语义真源；不要为 BAX 周报新建 Go 专用链路。
- 周期任务只需把 instruction 写成“使用 `$bax-weekly-usage-analysis` 分析最近一个完整自然周的 BAX AM 用户对话使用数据，并把结果写入 Task 输出；若发现显著异常，私聊 principal 摘要”。创建、启停或发布周期任务按当前执行阶段审批策略处理。
- 周期 run 默认不要发群消息。需要同步到群时，先给出目标会话和完整文案，按审批策略请 principal 决定。
- 如果本周数据不完整，返回 `waiting` 或报告覆盖缺口；不要补造完整周结论。

## 完成检查

- 周区间、时区和数据覆盖写清楚。
- 指标口径与数据源没有混用。
- WAU/DAU、会话、消息、用户 cohort、人群、场景至少各有一个结论或明确缺口。
- 每个核心结论能回指 dataset/report ID、查询时间或命令。
- 对外消息、文档分享、周期任务创建或生产注册没有在未获批准时执行。
