# 飞书群当天总结

把群消息当作调查入口，而不是待压缩的文本。拉全指定自然日的消息，围绕群里真正推进的事项追查关键材料，再形成可供未参会者直接使用的结论。

## 确定范围

1. 确认目标群和日期。只有群名时先解析唯一 `chat_id`；有多个候选时列出候选并请用户消歧，不猜。
2. 按用户时区计算自然日半开区间 `[00:00, 次日 00:00)`；未给时区时使用当前运行环境时区。
3. 记录群名、`chat_id`、起止时间和本次证据截止时间。用户要求“当天”时，以执行时刻为截止时间，不能暗示覆盖了未来消息。

## 收集完整消息

按 [工具路径](references/tool-paths.md) 拉取消息。先获取整个时间窗口，不用关键词预筛选。

- 拉全分页，确认没有未读取的下一页；受权限、页数或接口限制时明确标记覆盖不完整。
- 保留消息的 `message_id`、时间、发送者、正文、回复关系、附件和原始链接。
- 展开承载实质信息的线程；不能只看主消息。
- 人工消息是主要证据。机器人卡片、命令回执和旧总结只用于发现线索或交叉核对，不作为同等的一手事实。
- 过滤无信息量的寒暄、纯表情和重复通知，但不要因为消息短就丢掉决定、确认或阻塞。

## 沿线索补充背景

先把消息归并成若干事项，再决定哪些外部材料值得读取。不要机械打开每个链接。

- 消息引用飞书文档，且文档承载方案、结论、数据或状态时，读取与当前事项有关的章节；结构不明时先看目录再局部精读。
- 消息给出 commit、MR 或代码链接时，查看对应 revision 的说明和实际改动。只有 SHA 时先确定仓库；仓库不明则保留为未解析线索，不跨仓库猜测。
- 消息引用文件、图片、妙记或普通网页，且不读取就无法理解结论时，使用相应官方能力按需展开。
- 必要时读取群公告、项目背景或更早消息来解释术语和前因，但不得把窗口外背景冒充为当天进展。
- 为每个事项维护一个轻量证据账本：当天消息、补充材料、能支持的结论、仍不确定的点。

补充材料的价值是验证和具体化群内信息。不要因为材料内容丰富，就让总结偏离当天群聊真正发生的推进。

## 形成判断

对每个事项明确区分：

- **已落地**：有完成、合入、发布、验证结果或等价证据。
- **已形成结论**：群内明确拍板或材料给出确定结论，但不等于已实现。
- **进行中**：有人正在推进，尚无完成证据。
- **阻塞或风险**：存在具体问题、依赖、失败或未决分歧。
- **下一步**：消息中明确承诺、分配或自然导出的动作；自然导出的动作必须标为建议，不能伪装成群内承诺。

不要把“计划做”写成“已完成”，不要把“发了 commit”写成“已上线”，不要虚构测试、owner、截止时间或共识。存在冲突时呈现最终状态和必要的演变过程。

## 输出总结

根据当天内容调整篇幅和小节，不强制输出空栏目。默认使用下面的最小骨架：

1. 标题与范围：群名、日期、时区、截至时间、消息覆盖情况。
2. 一句话结论：直接说当天最重要的推进、结果或问题。
3. 主题进展：每个主题先写结论，再写关键事实、影响/当前状态，以及明确的负责人或下一步。
4. 关键决定与未决问题：只保留会影响后续行动的决定、分歧和依赖。
5. 材料：列出真正支撑结论的文档、commit、MR、文件或网页链接，并用一句话说明其作用。
6. 覆盖说明：仅在消息、线程或材料未能完整读取时列出缺口。

材料链接优先复用消息中的原始 URL，去重后按事项组织。只有在已知仓库或文档的规范地址时才补造直达链接；不要伪造消息 permalink。没有可点击链接的证据可用“发送者 + 时间 + `message_id`”标识。

## 质量检查

交付前确认：

- 每条核心结论都能回指当天消息或已读取材料。
- 总结能回答“今天具体推进了什么、结果是什么、还卡在哪里、接下来谁做什么”。
- 删除“大家积极讨论”“取得阶段性进展”等没有事实承载的句子。
- 讨论、决定、实现、验证和发布没有混写。
- 关键文档、commit、MR 和链接已读取或明确标为未能读取。
- 材料列表只包含与正文结论有关的链接。
- 若当天没有实质进展，直接说明“无可确认的实质进展”，并概括实际消息类型，不凑内容。
