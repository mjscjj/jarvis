# OKR Review 两轮催填

目标：每周根据张若怡的真实日程定位当周 `Platform Team Weekly Catch Up`，在会前完成两轮 OKR Review 填写质量提醒。第一轮由“Jarvis通知机器人”私聊负责人，第二轮由 Jarvis Bot 在 `[Core Group] Platform Team` 群内按 O-KR 维度汇总。

## 稳定范围与时间

- 全部时间按 `Asia/Shanghai` 计算。周期 ScheduledTask 只负责每周一 09:00 启动本 Task；会议相对时间由本 Task 使用 `yield-until` 恢复同一执行会话，不另建两条独立业务调度。
- 日历参与人固定为张若怡（`ou_4f9796d856ffa67c1b32206f6e81e5bf`）；查询本周周一 00:00 至下周一 00:00 的日程，标题必须与 `Platform Team Weekly Catch Up` 完全一致。只接受唯一个未取消的会议实例；无结果或多结果时不猜测、不发送。
- 第一轮为会议开始前一个自然日的 19:30，同时完成填写完整性检查和 AI 进展质量评审；第二轮为会议开始前 4 小时。使用带 `+08:00` 的 RFC3339 绝对时间创建恢复等待。
- 每次初始执行或恢复都重新查询同一会议实例。会议取消就终止剩余轮次；会议改期则重新计算尚未执行轮次。周一首次发现时某轮目标时间已过，则跳过该轮而不倒补。
- 目标群固定为 `[Core Group] Platform Team`（`oc_c9249426d3b7a1bf31d69ae658d60225`）。第二轮发送前必须回读群名与 Bot 成员，不得按群名改选其它群。
- 季度固定为 `2026-Q3`；周次以会议所在自然周对应的已开启 Review 周为准。找不到唯一对应周时不隐式开周。`2026-Q3` 结束后停止发送并报告配置已过期。

## 判断

- 每轮发送前都回读目标周、上一有效周及两周完整 Biz OKR board；只按稳定 KR/Point ID 比较，不复用上一轮或任务创建时的统计。
- 每条 KR 独立判断四类问题：`进展缺失`＝名下 Point 没有有效进展；`核心数据缺失`＝没有非空核心数据；`评分缺失`＝一级 KR 的 `score` 为空；`跟上周内容一致`＝两周都有有效内容，且核心数据或 Point 进展至少一部分在忽略版本、记录 ID、来源等元数据后相同。两周都空不能算相同。
- 收件人取 KR `owners` 与其 Point `owners` 的并集，必须有已核验的完整 `email`；按负责人聚合，每类按 KR ID 去重。同一 KR 可进入多类。

## 第一轮新增任务：AI 进展质量评审

- 同一轮 Board 读取成功后，再读取 `okr_agent_progress_review` Prompt，复用其中“结果、原因、业务影响、风险和下一步”的 AI 评审视角；本任务仍以本 Prompt 的范围、收件人和发送口径为准。
- 审查目标周 Board 中每个有内容的 O、一级 KR，以及其下每个 `strategy` / `product` 具体 KR。逐项判断当前进展是否需要修改或润色，重点识别三类问题：支撑结论的业务数据缺失；只写完成、推进或上线了什么，却没有说明实际或预期业务效果、验证方式；与上一有效周的对应进展在忽略记录 ID、版本和来源等元数据后全文一致。没有上一有效周时只跳过第三类判断。
- 以一级 KR 为通知中的一条 OKR 汇总单元，同时综合判断它所属 O 和其下全部 `strategy` / `product` 具体 KR；每个一级 KR 最多输出一句可直接执行的修改建议，不展开多条问题、不复述原文。内部留痕仍保留命中问题的具体对象稳定 ID 和依据。
- 只有满足以下任一条件才需要提醒：支撑结论的数据不完整；当前进展与上一有效周没有实质差异；没有写清实际或预期业务价值及验证方式。数据足以支撑结论、与上周有实质差异且业务价值已经写清时，该一级 KR 及其下内容通过评审，不生成建议、不推送提醒；不得为了覆盖全部 OKR 而制造问题，也不得虚构数据、效果或结论。
- AI 评审提醒只路由给以下固定人员中、同时出现在问题所属一级 KR `owners` 里的负责人；以 Board 中与姓名精确匹配的完整企业邮箱为发送身份，不按 Point owner 扩大范围：吴拓、刘洋、耿馨妍、苏穆辰、刘寅、张月仁、刘力华。姓名不存在、重名或邮箱为空时跳过该人并报告缺口，不猜身份。
- O 级问题只发给能够由具体问题 KR 归属到的上述负责人，不把一个 O 的问题广播给名单内所有人。每人按 O → 一级 KR 聚合，每个一级 KR 仅保留一句综合修改建议；没有需要修改内容的人不发送 AI 评审提醒。

## 第一轮：逐人私聊

- 使用 `weekly_report_reminder_template`。顺序固定为“进展、核心数据、评分、跟上周内容一致、AI 评审建议”；每个非零类别都列出数量和具体 KR 标题，AI 评审建议按上一节渲染为每个一级 KR 一句话，零项整段省略。每人最多一条，把该人的填写问题和 AI 评审建议合并，以负责人姓名开头；正文末尾必须包含“以上为AI评审判断，仅供参考”。直接私聊不再 `@` 收件人或 principal，不要添加“同步：”字段。
- 发送前读取 `feishu-broadcast` Skill，把全部负责人和各自最终文案冻结成一份广播计划。OKR Owner 已使用完整企业邮箱；读取当前 OKR 模块的固定通知应用配置，直接按邮箱发送，不按姓名猜人或依赖 CLI 默认应用。由于每个人的问题不同，按邮箱使用个性化广播路径逐人直发；不得搜索、复用或创建助手群。
- 使用“Jarvis通知机器人”、稳定幂等键并逐条回读消息。发送失败保留原始错误，不切换身份、收件人、会话或 Bot。没有问题时不发送；部分失败也要继续等待第二轮。

## 第二轮：群内 O-KR 汇总

- 重新计算尚未解决的问题，按 Objective 当前顺序分组，组内按 KR 当前顺序排列。同一 KR 的多类问题合并为一行，标签顺序固定为“进展缺失 / 核心数据缺失 / 评分缺失 / 跟上周内容一致”。
- 每条 KR 后面真实 `@` 该 KR 与 Point 的问题负责人，同一人在同一 KR 内只 `@` 一次；群消息接口需要临时 ID 时，先在同一通知应用内按完整邮箱精确取得其接口 ID，再渲染为飞书 `<at user_id="...">姓名</at>`，禁止只写普通文本 `@姓名`。不额外 `@` principal，不用 `@all`。
- 最终文案使用以下格式，最后一行必须原样保留：

```text
本周（{{week}}）OKR 填写问题（按 O-KR 维度）：

- O：{{objective_title}}
  - KR：{{kr_title}}｜{{issue_labels}}｜{{owner_mentions}}

请尽快更新：https://emily.bytedance.net/#/weekly-report?quarter=2026-Q3&tab=review-fill
```

- 发送前读取 `feishu-send-message` Skill，用 OKR 配置指定的通知 Bot 对固定 `chat_id` 主动发送一条群公告，使用稳定幂等键并回读消息；回读的 `mentions[]` 必须完整覆盖本轮负责人在该通知应用内的临时 ID，否则本轮视为未确认发送并保留原始差异。没有问题时不发空消息。

每次等待都把会议 `event_id`、当前阶段、已完成轮次和下次目标时间写入 `progress_summary` 与 waiting reason。完成时报告会议实例与两轮计划/实际时间、两轮 Board 范围和四类去重 KR 数、两轮成功/失败/跳过项、消息回读与覆盖缺口。
