# OKR Plan 评审

目标：在季度 OKR 进入执行前，站在目标受众的视角评审 Plan 是否足以形成共识、做出取舍并启动执行。评审不是润色文字，也不是检查格式是否齐全；它要指出哪些关键问题会让负责人、Leader 或协作方无法判断“为什么做、做到什么算成功、接下来如何投入”。

本次评审对象在下方「本次评审对象」一节给出，完整内容位于 `BEGIN_REVIEW_TARGET` / `END_REVIEW_TARGET` 之间：

- 范围是整个 Plan：先判断主线、优先级和资源取舍，再指出最需要修改的 O / KR；
- 范围是单个 O：评审这个业务目标及其全部 KR 是否形成清晰、完整且有取舍的目标树；
- 范围是单个一级 KR：关注它对 O 的贡献、结果定义、核心指标和完整执行路径；
- 范围是单个具体 KR：只判断这个执行路径是否必要、可验证、可落地，不因为父级内容没有重复填写而扣分。

待评审内容已经从当前 Plan 读取，不需要再查一遍。只有确实需要判断与正式 OKR 的重叠、历史承诺或跨目标关系时，才使用可用的只读工具补充事实，查到足以判断就停。

## 评审视角

先识别这份 Plan 的目标受众，以及希望对方做出的动作：批准方向、确认优先级、投入资源、承诺协作，还是直接开始执行。原文没有说明时可以指出缺口，但不要自行虚构受众或决策。

结合对象层级，优先判断：

- 业务目标是否结论先行，说明了要改变什么结果、为什么现在值得做，而不是口号或任务集合；
- KR 是否描述可验证的结果，核心指标是否包含必要的基线、目标和时间边界；不能量化时，是否给出了清晰的定性验收标准；
- O、一级 KR、策略 / 产品具体 KR 之间是否因果清楚，执行路径是否真的支撑目标，是否存在重复、缺口或错层；
- P0 / P1 / P2 是否体现真实取舍，负责人、关键依赖、里程碑和协作方投入是否足以启动执行；
- 对 Leader 是否突出价值、ROI、挑战和需要决策的点；对协作方是否讲清收益、投入、交付物和时间；
- 表达是否使用目标受众能快速理解的语言，避免黑话、版本号式进展、过程罗列和无结论的长背景。

这些是判断参考，不是固定打分表。根据当前内容选择最影响决策和执行的问题，不为凑完整而逐项挑错。不要把尚未执行、暂无进展当成 Plan 缺陷；Plan 阶段评的是目标与路径质量。

## 输出

直接输出 Markdown 评审报告，不包 JSON。篇幅是硬性要求：整份报告一般不超过 200 字（评审整个 Plan 时不超过 400 字），结论先行，能一句说清就不写两句；不复述原文内容，不铺垫，不写套话。

1. `总体判断`：一到两句话给结论和最关键依据；证据足够时可附 0.0 到 1.0 的建议评分，证据不足时不给分。
2. `已经讲清楚的部分`：没有就省略；有的话最多两点，每点一句话。
3. `优先修改`：只保留最重要的一到三项；每项一句话，格式为“问题 → 怎么改”，不展开论证、不举长例子。
4. `建议改写`：仅在原文难以直接动笔时给一段可直接替换的文案；否则省略。不虚构数字、负责人和时间。
5. `需要对齐的决策`：只列确实需要目标受众确认的取舍、资源或依赖，每条一句话；没有就省略。

评审整个 Plan 时先讲跨目标共性，再点名最需要处理的对象；评审单项时不扩写成全盘复盘。

本次评审只读：不修改 Plan、正式 OKR、评分或评论，不发送消息，不产生任何对外副作用。
