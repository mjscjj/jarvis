### 巡视流程的设计要点与工程约束

流程图展示了巡视的四个步骤，但真正决定这套机制能否长期运行的，是刻在每一步里的"节制"。一个每小时醒来、能读全量世界状态、又能直接创建 Task 的 Agent，如果不设边界，很快就会从"数字分身"退化成"定时噪音发生器"。因此巡视的第一设计原则不是"尽量多做"，而是"只做此刻真正值得做的那一件"。

**注意力是有限资源，新 Task 是昂贵副作用。** 巡视默认每轮只创建 0–1 个新 Task，只有多个事项各自具备独立证据、边界清楚且今天确实紧急时才允许破例，且硬上限为 3 个。这条约束写在 System Prompt 里，由 Agent 自行遵守，而不是靠后置限流——因为创建 Task 不只是写一行数据库记录，它会唤醒强 M5、消耗高成本模型配额、占用执行槽位，并在用户的任务列表里产生可见条目。与新建 Task 的克制相对应，更新、启动、关闭已有 Task 不计入这个上限：看护存量是巡视的本职，制造增量才需要被约束。同样，未闭环关键事项（KeyMatter）只看默认倒序的前 10 个，启用资源只看前 50 个。这不是因为系统读不了更多，而是刻意把注意力锚定在"最近仍被证据确认活跃"的工作集上——容量满了但没有可靠闭环依据时，宁可保持现状，也不允许为了腾位置清掉仍有效的事项。创建新 Task 必须同时满足四个条件：对 Principal 或活跃项目有**具体价值**（不是"也许有用"的泛泛改进）；"为什么是现在"能被**当前证据**解释（不是早一天晚一天都行）；下一步**边界清楚**、强 M5 能独立调查并推进（不是开放型探索）；已查重 Todo 和所有状态的 Task，**不存在等价事项**（不重复派单）。四条缺一不可，不满足时继续调查、保留观察或直接返回 NOTHING 都是合法结果——NOTHING 被明确定义为高质量输出，而不是"巡视失败"。

**失速不是沉默，堆积才是噪音。** 一个 Task 长时间停留在 `pending / executing / waiting / needs_human / awaiting_approval`，并不自动意味着它该被关闭——跨日、对方未回复、Principal 未批准，本身都不是关闭理由。巡视要做的是结合新证据判断它属于哪种情况：外部条件已变化值得重试的，推进；目标假设已被新事实推翻的，更新 `title / target / summary` 或重新调查；M5 自报 done 但真实世界缺证据的，记录新证据并创建带引用的 follow-up Task，而不是偷偷改写原 Task 的完成历史。对于一天、尤其是两天前仍未闭环的 Task，巡视会重点核查是否该废弃或关闭，因为不主动清理就会堆积，堆积会让后续每轮巡视的候选集越来越大、判断越来越稀释，最终整个看护机制失焦。但"闭环"在工程上是标记状态而非删除数据：`close-task` 只写终态和事件，历史 Task、TaskEvent 和 Fact 全部保留为只追加记录。KeyMatter 同理，它有两个不同的时间信号——`last_progress_at` 只在 Summary 真实变化时移动，`last_active_at` 是"仍值得看护"的显式信号——这让系统能区分"事项还在被关注但本周无实质进展"和"事项已经被彻底遗忘"，从而做出不同处置。

**等待不是遗忘，恢复不丢上下文。** `waiting` 状态的 Task 由 M5 在执行中显式创建一个 `resume_task` 类型的 ScheduledTask，并把它绑定到当时那个 ExecutionRun 的 Codex Session 上；调度到点后，恢复动作直接续接同一个 Session，而不是新建一条执行链——之前的调查结果、已经读过的文件、中间推理都还在对话上下文里。`needs_human` 采用同样的机制持久化 run 和 Session ID，等用户回复后续跑同一执行会话。巡视每轮检查这些等待中的 Task，核对等待条件是否已经满足、外部结果是否已经返回、最新上下文是否改变了判断；条件满足就恢复，条件不满足就继续保留，不会因为"等得够久了"而强制关闭。`awaiting_approval` 是更敏感的状态：它已经携带待审方案，巡视只允许更新 `summary` 补充进展，不得暗改标题、目标或执行指示，避免绕过审批语义。

**每一步都留有可追溯的痕迹。** 每轮巡视启动时先在 `proactive_run` 表写入一条记录，包含触发方式（定时/手动）、引擎与模型、完整输入 Prompt、开始时间；Agent 返回后写入最终输出或错误详情、结束时间和毫秒级耗时。这让空跑率、失败率、平均耗时、Token 成本都可以直接从数据库统计，而不需要解析日志。Task 侧的所有状态变迁——创建、启动、等待调度、恢复、请求人工、审批、关闭——都通过统一的 TaskEvent 流记录，并标注 actor 类型（`proactive / m5 / user / system`），因此"这一步是巡视主动关闭的还是 M5 自己结束的"在审计上完全可区分。巡视结束时的自然语言摘要只服务人工观测，真正的状态真源是工具写入的结果和 Task ID；摘要和事件流两者配合，既让人能快速读懂本轮发生了什么，也让任何一次创建或关闭都能回溯到具体证据。

| 巡视步骤 | 检查对象 | 判断条件 | 动作 | 节制约束 |
|---|---|---|---|---|
| ① 看护未闭环事项 | 最近活跃的未闭环 KeyMatter（≤10）、启用资源（≤50） | 新证据是否改变进展/状态/截止时间/归属；是否已有肯定闭环证据 | 更新、`touch` 续活、闭环；必要时维护内部世界模型 | 不因为"本轮看过"就 touch；无可靠依据不得为腾位置清理有效对象；KeyMatter 不直接执行 |
| ② 清理跨日非终态 Task | 今天之前的 `pending / executing / waiting / needs_human / awaiting_approval` | 是否失速、失效、误关单；外部条件是否变化；重点核查两天前 Task | `update-task` 修正、`start-task` 推进、`close-task` 有证据收口、保留观察 | 更新/启动/关闭不计入新建上限；跨日、未回复、未批准本身不是关闭理由；终态 Task 不改写、不删除 |
| ③ 处理今天的 Task | 今天新增或变化的非终态 Task | pending 是否仍值得做；waiting/needs_human 条件是否满足；executing 是否真实在跑 | `start-task`、`update-task`、恢复同一 Codex Session、验证后关闭 | 不创建重复 Task；awaiting_approval 只改 summary；今天活跃执行保持不动 |
| ④ 发现新工作 | 今天沉淀的消息、会议、事实、关系、Todo、项目进展 | 具体价值 + why now 有证据 + 边界清楚 + 无等价 Task | 创建完整普通 Task（带根目标、证据、成功标准、约束） | 默认 0–1 个，硬上限 3 个；不执行刚创建的 Task、不派生子 Task；无合格事项返回 NOTHING |
