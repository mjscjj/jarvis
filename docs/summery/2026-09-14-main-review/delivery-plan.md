# Jarvis 桌面交付完整链路方案

日期：2026-09-14。状态：分阶段实施中的设计方案。`14b207ab` 已交付发布 Skill、独立 checkout 操作流程、候选产物摘要和 `publish-update.sh --candidate`；本文其余桌面恢复能力、历史资源修复和业务缺陷仍未实现。本方案基于当日 main 审查及对打包、发布、桌面启动、资源同步、supervisor 的代码回读。当前发布操作以 [桌面发布 Skill](../../../.agents/skills/release-jarvis-desktop/SKILL.md) 和 [打包指引](../../../packaging/macos/README.md) 为准。

目标：一个确定版本，经过一次构建和完整验收交付到用户机器；保留用户数据，默认资源跟随应用升级；启动失败时仍可诊断、重试和安装修复版本。保留 Tauri、Go app-service、jarvis-server 及现有 updater，不引入新的后台恢复服务或另一套安装器。

## 1. 现在实际运行的链路

开发工作区 → publish-update.sh → build-dmg.sh → prepare-runtime.sh → 构建 Web 和 Go → 拷贝 conf/Skills/scripts/依赖 → Tauri 打包 → updater 签名 → 上传版本文件 → 切换 latest.json。

用户业务页面点击更新 → Tauri updater 下载、安装 → 应用重启 → 桌面壳启动 jarvis-app-service → Prepare 同步包内资源到用户 runtime → 启动 Qdrant → 启动 jarvis-server → /healthz 就绪 → 壳跳转到 Go 提供的 Web 页面 → 加载 JS、请求 API → 业务可用。

新安装也走同一条启动链，只是用户目录尚不存在；服务起来后再进入首次配置。重装 DMG 主要替换 App，不等于清空或修复 Application Support 中的状态。

当前执行代码在 App 中，但配置、默认文本、Web 和脚本还会同步到可写 runtime，再与长期保留的数据一起被使用。因此“App 已经更新”并不等于“最终生效内容已经更新”。

## 2. 为什么会反复出问题

| 环节 | 当前事实 | 后果 |
| --- | --- | --- |
| 打包输入 | 发布脚本从当前工作区构建；Web/Go 编译后才复制其他资源，一部分二进制来自打包机 | 并行修改工作区时，不能保证整个包来自同一个源码时刻；本轮没有证明线上实际出现混包。 |
| 生效资源 | 默认配置与用户定制共用同步机制；此前 config.yaml 改过就保留 | 新代码会遇到旧基线。今天强制更新基线修复了这个具体矛盾。 |
| 历史资源 | manifest 用旧包哈希推断是否用户修改；早期缺 manifest 会保留旧文件却写新哈希 | 今天修复“现在缺 manifest”，不能识别“早已生成错误 manifest”的历史状态，旧 prompt 仍可冻结。 |
| 页面 | WebView 有跨版本缓存，业务 Web 又由 Go 服务提供 | 旧 index 指向已不存在的 chunk 就可能白屏。今天 no-store 和版本入口应保留。 |
| 成功标准 | HTTP 健康、脚本检查、模拟更新测试各自通过 | 没证明真实旧用户状态能被新包启动，也没证明 WKWebView 实际完成加载。 |
| 恢复 | 桌面壳显示启动错误，更新操作入口主要在业务 Web 中 | 业务启动失败或白屏，会连带阻断获取修复版本。 |

前五环中的小问题被最后一环放大：用户不能自行更新，只能人工诊断或重装；若根因在用户目录，单纯重装仍可能失败。

自动采集恢复边界和设置接口静默忽略，是另外两个业务缺陷。它们应在下一次发布前修复，但不能把它们归因于打包，更不能靠换打包脚本修好。

## 3. 固定语义所有权

| 内容 | 所有者 | 升级处理 |
| --- | --- | --- |
| Tauri、Go、Web、scripts、基线 config.yaml | 应用版本 | 来自同一包，必须更新。程序不能把用户定制写入基线。 |
| config.runtime.yaml、连接配置 | 用户设置及对应设置模块 | 保留，只修改模块拥有的字段；与当前基线合并读取。已弃用未知键沿用目前明确的忽略并记录策略，类型错误仍暴露。 |
| 包内 prompt/rules/Skills 默认内容 | 仓库 | 未定制的副本自动更新；已有定制不能当作新版本默认内容。 |
| 用户定制 prompt/Skills | 用户 | 保留并明确显示为定制；默认更新与该定制有差异时，提供差异及备份恢复操作。 |
| SQLite、Qdrant、Task/Run、授权和运行数据 | 各数据模块 | 不由资源同步删除或覆盖。数据库变更由明确的 schema 迁移负责。 |
| .bundle-assets.json | 同步器 | 是已分发包资源的记录，不是用户意图的权威来源；丢失不能等同于“全部定制”。 |
| 启动、进程退出、重试、安装更新 | 桌面壳与 app-service | 不依赖业务 React 正常运行。 |

近期继续使用现有目录，不做大规模搬家。必须建立的产品语义是：保留旧 prompt 是因为它是显式定制，而不是悄悄把它当成最新默认内容。历史状态无法自动判定时显示冲突和恢复选项，不能假装判断成功。

## 4. 目标完整流程

### 4.1 开发与候选版本

1. 完成代码及相应测试，提交得到确定 SHA。版本修改进入同一候选提交。
2. 发布入口接收这个 SHA，建立独立 checkout；开发工作区可以继续改动，构建不再读它。
3. 固定包内依赖版本和摘要。已固定的 Lark CLI 保留；Trae、Node、Qdrant、CC Connect 等不能只用“PATH 里找得到”作为交付身份。已有本地二进制可以作为输入，但要核对锁定身份，不符合就失败。
4. 在候选构建记录中保存版本、commit、平台、依赖版本/摘要；完成后记录 app、DMG、更新归档的摘要。

一个版本只对应一份候选源码和最终产物。候选验收失败可以改代码、重新生成候选；重新构建的包必须重新验收，不能沿用上一个包的通过记录。

### 4.2 构建与发布分开

保留 build-dmg.sh 和 prepare-runtime.sh 的主要职责，只从冻结 checkout 和固定依赖构建。现在可按发布 Skill 在独立 checkout 调用既有构建脚本，再封存到 release 候选目录。`candidate.json` 记录版本、commit 和 DMG/更新归档的摘要；未被 manifest 锁定的打包机依赖仍由执行者核对并在 `acceptance.md` 记录，尚非机器强制完全可复现构建。

`publish-update.sh --candidate` 已可消费已封存的候选目录，验收同一份产物后发布时不会再重新 build；原不带 `--candidate` 的命令仍保留构建后直接发布模式，不能用于验收后发布。DMG 与 updater 归档来自同一个完成签名的 App；产物摘要由代码校验，实际用户安装升级结果由 `acceptance.md` 留证。

发布时上传版本化不可变文件，校验远端实际内容，再切换 latest.json。现有“先上传产物、最后移动 latest.json”和禁止覆盖已有版本的规则值得保留。latest 指向新版本之前，任何下载失败都不影响已有发布版本。切换后从用户使用的公开地址读回版本与产物摘要，而不仅检查 HTTP 可达。

这不要求先搭建大型 CI 平台；本机脚本也可以先实现冻结、构建、验收、发布四个清楚的步骤。

### 4.3 用户正常更新

1. 桌面更新模块查询 manifest，展示版本及说明；正常业务页也调用同一个模块。
2. 用户选择安装，下载并由已有 Tauri updater 完成签名验证；下载或验证失败保留当前应用运行，明确显示原因。
3. 进入实际替换前，由桌面壳协调停止旧 app-service 及其子进程，避免旧程序继续读写即将切换的资源。具体接入现有插件的安装阶段，不自写安装器。
4. 安装完成后重启，进入下面统一的启动流程。

“下载完成”“App 安装完成”“服务启动成功”“业务页面可用”是不同状态。只有最后一项完成，才把这次更新标为已成功启动；不新增一套业务 Task 状态。

### 4.4 启动与资源准备

桌面壳先显示包内自带的启动页面，再后台启动 app-service。不要让启动进度页面等待 Go 就绪后才存在。

app-service 负责串行完成资源准备、配置检查和服务启动。需要写 runtime 的准备及修复都使用同一进程互斥范围，避免另一个实例或修复操作并发修改。资源没有准备成功就不启动 jarvis-server。

资源同步规则：

| 状态 | 动作 |
| --- | --- |
| 新安装，目标不存在 | 写入包内资源，创建最小用户覆盖文件。 |
| 程序资源或基线不同 | 更新为当前包版本，用户参数继续由覆盖文件提供。 |
| 默认文本等于上次分发版本 | 更新为当前包版本。 |
| 默认文本被改过，manifest 有效 | 保留定制，显示当前存在定制及与新默认的差异，不宣称默认已更新。 |
| manifest 缺失且目标不同 | 先成功备份，再恢复包内版本，逐项记录路径；备份失败立即终止。 |
| 历史冻结与主动定制无法区分 | 不猜测覆盖；通过明确的“备份并恢复默认资源”操作处理。 |
| 读取、复制或配置校验失败 | 报出阶段、文件和具体错误，进入桌面恢复页面。 |

同步期间保持业务服务停止，逐文件原子写，全部完成后再提交 manifest。中途退出可在重启后重做；不能将部分同步标记为已完成。此步骤不承诺整个应用和数据库跨文件事务，也不引入自动降级。

配置检查保持严格边界：包内基线严格，用户 overlay 按现有策略合并；数据库按现有明确迁移执行。已知仅涉及早期源码开发者的退役列，不在本次扩大成通用历史库迁移。

Qdrant、jarvis-server 依次就绪后，壳使用版本化入口打开业务页面。HTTP 健康后还要等待前端加载完成的通知：当前前端版本与包版本一致、关键启动请求完成；未配置用户进入引导也算成功展示，不要求先完成飞书授权。超过明确期限仍未完成，显示加载诊断与恢复入口。

### 4.5 正常运行与故障恢复

恢复页面是 Tauri 包内独立静态页面，不向 jarvis-server 请求页面本身；恢复动作通过原生命令执行。桌面原生菜单始终提供入口，业务页面白屏时也能打开。

| 故障 | 用户看到什么 | 可执行动作 |
| --- | --- | --- |
| 包内资源缺失或校验失败 | 当前版本、失败文件、错误原因 | 查看诊断、检查并安装修复版本。 |
| 用户配置语法或类型错误 | 精确文件与字段 | 打开配置位置，修正后重试；不能悄悄恢复默认设置。 |
| 资源历史冲突 | 受影响的默认文件及差异 | 明确选择后备份并恢复默认资源。 |
| 服务启动失败或进程退出 | 出错组件、阶段与日志位置 | 查看诊断、重试启动、安装修复版本。 |
| Web 页面加载失败 | 页面加载阶段与版本信息 | 重新加载、进入同一个更新模块。 |
| 下载失败或签名错误 | 具体下载/验证错误 | 用户重试；不替换当前 App。 |

“备份并恢复默认资源”的范围必须预览：只处理应用分发的资源，保留差异文件和备份索引；不删除 runtime override、数据库、会话、授权信息和用户独立新增的 Skills。执行前停止业务进程，备份全部成功后才开始替换，失败不报告成功。备份目录可以直接打开。

历史有旧 manifest 的用户也能主动使用这个入口，而不仅在 manifest 缺失时才运行。对可能已冻结的默认文件，通过差异提示和版本说明引导处理，不声称能自动识别所有历史受影响用户。

不默认自动回滚旧 App：新版本可能已经迁移数据库，倒退二进制不一定可运行。短期恢复策略是保留数据、暴露原因、安装修复版本；要支持降级必须单独明确数据库和资源的兼容范围。

旧版用户尚未获得新的恢复页面时，一次手动安装修复 DMG 仍可能必要。这是把恢复能力送达旧用户的过渡步骤；重装后仍需运行明确的资源修复，不能承诺替换 App 本身就能修掉历史状态。

## 5. 怎么证明真的完成

同一个候选包，使用隔离的用户状态目录，在真实 macOS App/WKWebView 上至少覆盖：

| 场景 | 验收结果 |
| --- | --- |
| 全新安装 | 界面展示、进入引导、保存设置、重启后保留；安装机器无需源码 checkout 或碰巧已安装的 CLI。 |
| 已发布旧版正常升级 | 设置、数据、登录按约定保留；App、后端和前端属于同一发布，默认资源更新。 |
| 基线曾被编辑、overlay 有旧键 | 基线更新，overlay 保留，未知键记录，类型错误准确报告。 |
| manifest 丢失 | 冲突文件备份可读，新资源实际生效；再次重启无重复破坏。 |
| 旧版本已经重建错误 manifest | 明确的备份恢复操作能解除冻结，不损失用户数据。 |
| 有意定制 prompt/Skill | 正常升级保留定制并可见；用户选择恢复才替换。 |
| 旧 WebView 缓存 | 新入口及 chunk 正常加载；更新入口可用。 |
| 服务失败、业务页不加载 | 包内恢复页面和原生更新能力仍可用。 |
| 同步中断、下载中断或验证失败 | 不宣称升级成功；重试可解释、备份可追溯、数据未误删。 |
| 采集重新开启后首次发现会话 | 关闭期间消息不入库，首次安装回看语义不被误改。 |
| 修改自动监听数量 | 唯一写入口实际生效，旧写入口明确拒绝，不静默忽略。 |
| waiting 续跑及重启 | 旧执行清理完再启动；已有后续 Run 不被重复激活。 |

前三类代码测试、模拟浏览器测试继续保留，它们用于快速发现问题。真实升级验收负责跨进程、文件系统、WebKit、安装器和历史状态组合，二者互相补充。

真实 Feishu 首次授权及配置后的最小联通验证另列结果：用户身份机器能用不能替代新用户已验收；涉及真实消息的操作按具体授权执行。

## 6. 落地顺序与模块

1. **先修确定缺陷。** capture 持久化自动监听恢复边界；config/API 收口监听数量写入口；为 waiting 恢复补专项测试。它们独立于打包，不再混成缓存或安装问题。
2. **完成资源恢复闭环。** appservice 统一正常同步和显式恢复的文件规则、备份、错误记录、互斥；增加历史错误 manifest 及中断重试测试。保留本次 config.yaml 强制升级修复。
3. **桌面壳具备独立恢复能力。** main.rs 异步启动并保留本地页面；原生命令持有唯一更新实现；正常 AppUpdate 与本地恢复页复用；增加前端就绪通知和原生菜单入口。
4. **发布脚本分离候选构建和正式发布（已完成第一阶段）。** 发布 Skill 指导独立 checkout 与依赖身份记录，`release-candidate.mjs` 封存产物，`publish-update.sh --candidate` 只提升该候选；仍须真正执行首次安装与旧版升级验收，打包机其他依赖的身份还没有全部成为机器强制校验。现有版本文件不可变和最后切换 latest 的机制保留。
5. **对一个候选版本完成真实安装/升级矩阵，再发布一次。** 这些工作可分成小提交验证，不必每个提交都打一遍对外版本。候选内容变化则重新验收新产物。

本次不更换技术栈、不引入独立 prompt 热更新平台、不建设通用历史迁移系统。默认资源与用户定制若将来规模扩大，再安排明确的目录与覆盖层迁移；本次通过清晰所有权、差异可见和显式恢复先完成最小交付闭环。

完成标准：能够回答“用户实际运行哪份包、用了哪些定制、失败在哪一步、在哪里获取修复”，且在业务服务失败时这四件事仍然可用。
