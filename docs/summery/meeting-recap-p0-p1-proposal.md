# 会议回顾 P0 / P1 方案（精简版）

状态：P0 / P1 代码已实现并验证，尚未部署重启。更新：2026-09-10。本版替代此前的扩展方案。

## 1. 改造尺度

沿用现有采集 → M2 → M3 → Task → M5 → 会议回顾页。优先修正现有规则、减少重复调用、修复已确认的代码错误。以完成这次问题修复所需的最小语义闭包为范围。

不新增会议业务表、状态机、产物类型、Skill、事件队列或评测平台。现有能力缺少必要的原子查询时，可以补一个通用工具，但不为会议另建流程。

基线来自此前审查的北京时间 2026-09-07 至 09-10 12:30：25 场候选全部采集，14 场有总结；已有总结的中位延迟约 26 分钟；巡扫平均约 7 分 40 秒。没有总结的会议包含未参加、无内容等情况，需要分别核验。

## 2. P0：先把结果做对

### 2.1 没有待办，也应有会议回顾

修改 `conf/rules/m3.md`、`conf/rules/m5.md` 的现有会议段落：

- Principal 实际参加、尚无回顾的已结束会议，默认进入 M5 整理。删除“责任人正常推进即可跳过回顾”的旧依据。
- M3 只看会议基础证据和同一 meeting_id 的已有回顾事项；不拉转写判断会议内容多少。信息不确定时交给 M5 核验。
- 已有回顾或有效回顾 Task 就复用，其他行动 Task 不等于回顾已完成。明确未参加、取消、重复的记录保留原因。
- M5 先完成回顾，再按需要处理独立行动项；长期跟进不拖住总结。确实缺少材料时如实记录，不把空 AI 摘要当成“会议无内容”。

仍是一场会议的普通回顾 Task，不增加新的准入阶段。

### 2.2 等待中的任务，按真实证据处理

修改 `conf/prompts/proactive-system-prompt.md` 的现有等待核验要求：

- 关闭前读取目标、最新运行、等待原因和恢复计划；没有完成或失效证据就保留。
- 摘要为空、产物生成中、授权未生效，都不构成任务完成证据。
- 优先使用现有 Task 和定时任务查询，不另建会议查询接口，也不限制某个阶段的修改权。

修复 `internal/execute/store.go`、必要时 `internal/scheduledtask/service.go`：

- Task 确实关闭后，清理它已绑定、尚未执行的恢复调度。当前只清理未绑定调度的问题需要修掉。
- 沿用 Task 版本、来源 run 和现有状态处理关闭/恢复竞态；旧唤醒不能重新执行已关闭任务。
- 保留关闭和调度处理原因；不新增事务或专用状态，不顺带重构其它生命周期。

### 2.3 时间正确，一场会议只显示一次

修改现有采集 Skill、`internal/insight/meeting_review.go` 和 `web/src/review/MeetingSummaryView.tsx`：

- Unix 秒按运行配置的时区，用可复用的机械转换命令或小脚本生成 RFC3339；保留原始时间。不使用机器默认时区，不让模型手算。
- 页面只认符合现有采集契约的原始会议线索，按 meeting_id 去重；派生行动线索和无效测试 ID 不成为会议 Tab。去掉任意 message ID 被当成会议 ID 的兜底。
- 按绝对时间转到配置时区后筛选日期，修正当前正文日期字符串预筛选造成的跨日遗漏。
- 页面展示已有 Task 状态与最近处理说明；done 没有总结时明确显示“已结束处理，但未生成总结”。原因缺失就说明缺失，不由代码猜测原因。

继续读取现有 `meeting_summary`，不增加 `meeting_facts` 或历史覆盖协议。

## 3. P1：减少重复工作，改善总结

### 3.1 先优化当前巡扫

保留现有每 10 分钟调度和事件唤醒方式，也保留会前扫描节奏。先不拆调度、不改事件传递、不加游标。

只改现有采集步骤：

1. 搜出过去 24 小时的候选 meeting_id 后，先查询本地已采集记录；已经采集的已结束会议跳过详情和联系人查询。
2. 优先复用现有通用消息查询。若不能准确按外部 ID 查询，补一个通用批量存在性查询；以原始线索是否落库为准，不能用“是否已有 Task”替代。
3. 新会议查完就投递，让下游立即开始。完整参会人 ID 保留，姓名按需解析，不让全员姓名补齐阻断采集。
4. 删除两个采集 Skill 中要求逐场写报告的段落，输出形式以巡扫系统提示词的一行要求为唯一真源。

会前日程可能变更，不套用“ID 见过就永久跳过”。本轮不扩大到日历增量同步。

若减少重复调用后巡扫仍明显慢，再依据实测决定是否值得做事件定向采集；不预先承担那套调度复杂度。

### 3.2 用现有 M5 规则定义好总结

在 `conf/rules/m5.md` 保留简短的交付标准，具体查询继续引用已有 `lark-meeting` Skill，删除重复的 vc/minutes 命令手册：

- 独立总结要读原始转写；转写已可读就不等待 AI 摘要。按已有 Skill 选择 Note/Minutes，不假定只有妙记。
- 交付前核对：关键结论、已定决策、行动项及 Owner/时间、未决问题、与 Principal 的关系、材料依据。没有的内容可省略，不为凑模板编造。
- 区分会上决定、个人建议、会外背景；未知 Owner 或截止时间明确写未知。
- 长会议分段读全，检查后半段是否推翻前面的结论；复用已读材料，避免重复加载全文。
- 先给简短结论，再展开必要细节；不把工具调用、内部查重或 Task 处理过程混进会议总结。

M3 同时改用短而完整的原文片段作为 source_quote，避免复制长参与者名单后改写导致验证失败；完整原文继续冻结保存，不放宽证据校验。

本轮保留现有模型配置。先确认重复工作减少后的效果，避免同时改模型而难以判断质量变化。

## 4. 实施与验证

按 P0 → P1 两批实施，分别检查各阶段实际收到的完整 prompt/rules/Skill 组合，避免旧要求和新要求并存。

必要代码测试只覆盖真实风险：跨日时间、原始会议与派生线索区分、同会去重、关闭后的恢复调度及竞态。行为用 5 场代表性材料验证：无待办周会、长技术讨论、生成中、权限等待、误命中/无内容。

验收直接看四件事：

1. 应总结的会议不因“无待办”被跳过，不能总结的有证据和原因。
2. 等待不误关，关闭后的旧调度不重新执行。
3. 时间和会议条目正确，决策/Owner/日期不编造，关键内容不遗漏。
4. 全部重复的会后候选不再读取详情/联系人；从现有日志对比巡扫耗时、材料可读后的总结耗时。飞书生成/授权等待单列，同时保留端到端耗时。

先实测，再设合理的延迟指标；不建设新的观测或评测平台，也不承诺现有 10 分钟轮询一定能达到 3 分钟采集。

历史漏项在修复后逐场列出并用现有能力补做。重复 append-clue 不会更新旧记录或重新触发；不为历史补做新增长期兼容层，也不改写冻结快照。历史页面的错误时间不会仅因转换修复而自动纠正，需单独列明待更正项。本轮先修持续产生问题的根因。

本次保留工作区其他开发改动。需要构建或重启时使用 `scripts/rebuild-server.sh`；检查时主服务仍有 3 个执行中的 Task，未中断它们进行重启。文本规则按各自 reader 读取，后端与生产页面需部署后生效。

- 使用当前新代码以 SQLite `mode=ro` 读取真实数据：9 月 7 / 8 / 9 日分别得到 9 / 4 / 12 场唯一会议，保留原有 7 / 2 / 5 份总结；9 月 10 日的测试会议不再显示。所有基础会议 ID 的精确查询都能命中。
