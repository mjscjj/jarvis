# 安装时统一补齐飞书能力：MVP 修改方案

状态：代码已实现，验证结果见文末；未打包或发布安装包。

## 目标

第一次安装即引导用户完成当前 Jarvis 内置功能需要的应用权限、事件配置和个人授权；已经配置过的应用复用原配置。缺少什么就在安装页明确显示，一次列全，避免运行到妙记、聊天或卡片审批时才逐个报错。

“申请全”指当前内置功能需要的权限。保持现有产品范围，不扩大到平台所有业务域；企业策略不支持的权限和可选外部插件继续沿用各自约定。

## 用户看到的安装流程

采用一个安装页，按实际缺项显示下一步操作；不增加步骤引擎。正常首次安装顺序：

**连接飞书 → 展示当前应用 → 补齐应用权限和事件 → 授权个人账号 → 登录 Agent → 按需补填该应用的聊天密钥并开始使用。**

### 连接后先明确“这是哪个助手”

未连接时只显示“连接飞书”，不展示无归属的 App Secret 输入框。连接完成后，将当前应用信息固定显示在后续操作上方：

```text
正在连接的飞书助手：张三的 Jarvis
应用 App ID：cli_xxxxx
[打开这个应用的管理页面]
```

名称来自当前应用的真实返回，App ID 始终显示。名称暂时读取失败时明确提示，并显示已经确定的 App ID，不把默认的“Jarvis”当作真实应用名称。

此处显示应用名称和机器人身份，不把 OAuth 登录人的姓名当作 Bot 名称。已有应用继续复用，不提供隐式重建或切换应用的路径。

### 先完成应用配置和个人授权

应用配置缺项直接显示在当前应用信息下，补齐后使用现有授权按钮一次申请内置功能所需权限。完成个人授权后另显示“已授权账号：张三”，让用户区分应用与本人。

只要 lark-cli 当前应用连接有效，个人授权可以在手动补填聊天密钥之前完成。若应用凭据本身已失效，则先对这个明确的 App ID 修复凭据；不能把重新个人授权当作修复应用凭据的办法。

### 最后按需补聊天密钥

已有匹配当前 App ID 的聊天密钥且验证通过时跳过输入。首次安装尚无聊天配置时，使用以下文案：

```text
让这个助手在飞书里回复你

请填写「张三的 Jarvis」的应用密钥（App Secret）
App ID：cli_xxxxx
[打开这个应用的管理页面]
进入“凭证与基础信息”，复制 App Secret。

[密钥输入框]
[验证并继续]
```

帮助说明保留一句：“这是上方应用的密钥，不是个人密码。”不让用户重新选择应用或再次输入 App ID。应用链接只生成当前 App ID 对应的管理入口。

验证时使用当前 App ID 与输入密钥组成的一对凭据。验证失败保留输入和应用身份，显示错误；验证通过后复用现有配置写入链路，完成安装。缺事件、缺个人 scope 时不展开密钥修复输入框。

### MVP 的密钥复用边界

当前 `savedSecret` 只读取 `cc-connect/config.toml` 中匹配当前 App ID 的已有密钥；`currentLarkConfig` 并未读取 lark-cli 密钥。因此“飞书连接成功”不等于 Jarvis 已取得聊天启动所需的密钥。

本次复用已有聊天配置，不新增密钥存储、跨工具凭据提取机制或 CLI 私有配置解析。首次安装仍可能需要复制一次 App Secret，重点是放在用户已明确应用身份之后，并给出直接定位。

## 当前证据与问题边界

- `scripts/jarvis-lark-auth` 已包含会议与妙记权限，包括 `minutes:minutes:readonly`、`minutes:minutes.basic:read`、`minutes:minutes.artifacts:read`、`minutes:minutes.search:read`。申请和检查共用同一清单；`larkStatus` 对已有有效登录也执行检查。因此不能把最新源码的问题简单归结为“忘了加妙记 scope”。
- 截图来自 `checkBotEvents` 的统一错误。代码在解析失败、`ok=false`、`decision.status!=ready` 时都丢掉具体原因，因此截图不足以确认对方应用究竟缺少哪项配置。
- 本机 lark-cli 1.0.93 的 `event schema card.action.trigger` 声明需要 `im:message:readonly` 和控制台事件 `card.action.trigger`。本机当前应用两个事件的 dry-run 都返回 ready；这不代表对方安装环境已通过。
- `checkBotEvents` 只在 Finalize 执行。安装状态未提前暴露事件配置缺口，用户走到“开始使用”才失败。
- 新应用创建调用 `config init --new`。当前 CLI help 没有自定义 scope 或事件参数；不能假定给这条命令追加参数就能自动配置全部应用能力。
- 尚未取得对方的安装版本、CLI 版本、原始检查结果和妙记失败响应。旧安装包、个人 OAuth 缺项、应用侧未开放、单篇资源访问限制须由这些证据区分。

## 修改方案

### 1. 复用现有清单，补齐应用侧配置入口

保留 `scripts/jarvis-lark-auth` 作为用户 OAuth scope 真源，增加只读清单输出入口，安装页和安装文档从这里获取需要开通的权限，不手抄第二份用户 scope。

按当前实际 Bot 消费能力核对应用身份权限，提供一份可复制的开放平台批量导入配置。用户权限与应用权限分别映射，不能将全部 user scope 原样当作 Bot scope。导入使用 `scopes.tenant` / `scopes.user` 格式，用户清单与 OAuth 申请共用真源。

同一页面列出机器人能力、长连接接收方式、`im.message.receive_v1`、`card.action.trigger` 以及发布版本的步骤。权限开通与事件订阅属于不同配置项，必须一起引导完成；权限导入不代表事件已订阅。现有应用直接补齐，不要求重新创建 Bot。

当前 CLI 不支持自定义创建模板，MVP 使用明确的控制台操作指引与复制入口，不新增自动操作开发者后台的系统。用户 OAuth 仍通过现有一次扫码申请整份清单。

### 2. 把检查提前，并一次列出缺项

在安装检查和“重新检查”时复用现有事件 dry-run，分别检查两个事件并展示各自结果，不在第一项失败时隐藏第二项。Finalize 保留同一个检查实现作为完成前验证。

安装界面区分三个需要用户操作的位置：应用配置、个人授权、凭据修复。事件未订阅不再引导修改 App Secret；个人缺 scope 则显示“补齐飞书授权”。复用现有 status 和 setupAction，不引入独立向导引擎、数据库或复杂状态机。

事件 dry-run 的 JSON 使用已有 stdout/stderr 分离读取能力。保留 CLI 的 preconditions、原因和修复提示；JSON 解析失败明确显示解析错误，不能伪装成“应用权限不足”。原始诊断信息可展开查看。

### 3. 妙记按真实失败点修复

用户 token 缺权限：使用现有统一授权入口重新申请，完成后用同一份 scope 清单检查。

应用侧尚未开放对应用户权限：在同一个应用开通并完成必要发布/审批，再继续个人授权；明确告诉用户操作发生在哪个环节。

单篇妙记未对当前用户开放：保留具体资源错误，提示申请该资源访问权限；不反复拉起 OAuth，也不让一篇不可访问的妙记阻塞整个安装。权限开通不能替代资源分享。

## 修改范围

- `scripts/jarvis-lark-auth`：复用清单并提供只读导出。
- `internal/onboarding/service.go` 及相关类型：提前检查应用事件，保留真实诊断；复用既有执行与解析工具。
- `web/src/onboardingState.ts`、`web/src/Onboarding.tsx` 及接口类型：固定展示真实应用身份，按缺项选择操作，个人授权后按需补填聊天密钥；显示应用配置缺项、复制权限配置、区分修复入口。
- `internal/onboarding/credentials.go`：复用同一 App ID 的密钥验证与配置写入，不增加第二套凭据存储。
- 安装授权说明和必要测试：同步源码与桌面路径，不复制另一套授权流程。

## 验收

1. 有效 token 但缺妙记 scope：必须展示补授权入口，补齐后检查通过。
2. 应用缺少卡片事件：进入安装页即提示具体缺项；补好并发布后重新检查通过，无需改密钥。
3. CLI 响应损坏或协议不支持：显示原始工具问题，不误报权限缺失。
4. 对一个干净安装环境验证应用开通、个人授权和安装完成的全链路；随后实际读取一篇当前用户可访问的妙记。真实消息与卡片交互测试在指定测试会话和明确授权下执行。
5. 检查实际交付版本包含这些修改；不能以源码单测或开发机现有权限代替新用户验收。打包与交付另按用户安排，本方案不启动打包。
6. 全新用户连接前看不到无归属的密钥框；连接后始终看得到真实应用名称和 App ID。正常连接下先完成个人授权，再补聊天密钥。
7. 已有有效聊天配置时跳过密钥输入；填错密钥时保留输入与应用信息，无法进入完成状态。个人权限和事件配置失败不误引导用户改密钥。

## 本次不做

不建设权限管理平台、不自动代用户审批、不绕过卡片检查、不加入隐式 fallback、不在后台无限重试。主要改动集中在安装链路，业务流水线不变。

## 本次验证结果

- `go test -race ./internal/onboarding` 与 `go test ./internal/api` 通过。
- 前端 51 项单测及 TypeScript 检查通过。
- 浏览器安装测试 11 项通过：应用身份展示、个人授权前不显示密钥、事件缺项与完整权限配置展示、错误密钥保留输入、修正后完成安装，以及已安装应用的草稿保留与连接修复。
- 权限导出执行真实脚本，验证导出的用户 scope 与 OAuth 命令请求的 scope 完全一致；CLI stdout/stderr 分离使用真实子进程验证。
- 浏览器使用隔离 API fixture，未对真实飞书应用申请权限、修改配置或发送消息。开发者后台的现场访问被企业设备策略拦截，未绕过；新用户的控制台导入、审批、授权和实际妙记访问仍待交付环境验收。
- 未打包、未发布安装包、未重启主服务。为复用现有安装状态，保留 Agent 登录先于最终聊天密钥填写；个人飞书授权始终在正常首次填写密钥之前。
