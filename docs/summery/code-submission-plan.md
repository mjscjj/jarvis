# 代码提交与评审方案

飞书阅读版：[Jarvis 代码提交与评审方案](https://bytedance.my.larkoffice.com/docx/G3qVd66DuoIDmHxGCY9mCXrXy2c)。

> Status: proposal
> Authority: non-normative proposal，待与 principal 对齐
> Last verified: 2026-09-10 @ 8f86e8d + 当时工作区改动

本方案先按“Jarvis 仓库如何组织分支、commit 和 MR”讨论，以 [插件解耦](plugin-extension-spec.md) 为首个实例。这里约定的是交付方式；Jarvis 执行 Agent 自动提交代码的运行流程尚不在本次实施范围内。

建议采用：**一个可独立验收的结果对应一个 MR，MR 内按完整逻辑拆 commit，依次合入；代码提交、合并和部署分别说明完成到哪一步。** 本文是待对齐方案，当前没有据此提交代码或发布 MR。

## 1. 先明确“提交到哪一步”

| 交付终点 | 应交付的证据 | 不能据此声称 |
|---|---|---|
| 本地可评审改动 | 工作目录、基线、diff、验证结果 | 已 commit、已推送 |
| 本地 commit | 分支、commit SHA、提交范围与验证结果 | 远端已有代码 |
| 远端分支 / MR | remote、分支、远端 SHA、MR 链接及目标分支 | 已合入主干、已部署 |
| 合并 | MR 合并状态与目标分支中的提交 | 运行中服务已更新 |
| 部署 | 实际构建版本、部署与服务验证结果 | 仅凭 git 操作不能判定 |

本次用户要求“出方案并对齐”，终点就是本文。以后按该次任务已经明确的交付范围做到终点，不能完成本地修改就冒称代码已提交，也不能把“提交代码”默认为部署生产服务。

## 2. 当前工作区怎么处理

核对时当前分支为 `main`，跟踪 `origin/main`；暂存区为空。工作区同时存在插件、会议采集/回顾、任务反馈、背景和 UI 等多项改动，其中还有未跟踪的 Skill 与测试。这些都是观察事实，不代表本方案取得了提交这些改动的授权。

尤其要注意：插件规范引用了工作区中的“我的交办”能力。新的 worktree 从已提交基线创建时，不会自动带入这些未提交实现，不能把当前目录能用的功能当成主干已有功能。

处理顺序建议：

1. 为本次实际要交付的事项列出相关文件和必要依赖，保留其它改动原状；相同文件混有不同事项时按 hunk 核对。
2. 先确定插件改造的基线：现有未提交插件功能若要保留，应单独形成可验证的前置提交；若已有对应分支/MR，直接等待或复用它的明确提交。不能为启动解耦把整个工作区打包进去。
3. 基线明确后，在独立 worktree 的功能分支中做新改造。原工作区作为其它工作的现场保留，不自动 stash、reset、clean 或切换分支。
4. 确需迁移未提交的相关内容时，只迁移核对过的改动和明确列出的新文件，核对目标目录 diff，并重新验证。

隔离 worktree 只为减少并发工作相互覆盖，不建立 Agent 权限隔离，也不复制一套运行中的服务配置和业务数据库。

## 3. 分支与 commit 约定

目标分支按实际仓库核验，不把所有项目一律当成 `main`。本仓库建议功能分支使用 `feat/<topic>`、修复使用 `fix/<topic>`、纯文档使用 `docs/<topic>`。

默认一个 MR 一个短期分支，上一批合入后，下一批从更新后的目标分支创建。不提前建立多层依赖分支；确实需要并行开发时再在 MR 描述中写明依赖关系。

一个 commit 应表达一个完整、可检查的行为变化：

- 同一行为涉及实现、声明迁移、API、前端和必要测试时，可以放在同一 commit 中。
- 不按文件类型机械拆成“先后端、再前端、最后测试”，造成中间提交无法工作。
- 新真源生效时同步删除旧真源。文件化注册表不能提交成“YAML 与 Go 清单暂时各存一份”。
- 不夹带其它事项、运行数据、构建产物或本机配置。当前已有 `.gitignore` 不替代对暂存区的检查，尤其已跟踪文件仍需逐项确认。

建议标题格式与现有历史保持一致：`类型(范围): 具体变化`，例如：

```text
refactor(plugin): load declarations and skill bindings from files
feat(plugin): render configuration fields from declarations
refactor(plugin): isolate external authorization providers
refactor(tasks): move delegation presentation into plugin views
```

提交时显式选择路径或 hunk，再查看 `git diff --cached`。共享且有其它工作改动的目录不使用 `git add .`、`git add -A` 或 `git commit -a` 一次收走所有内容；已有他人暂存内容时也不擅自取消暂存或一并提交。

## 4. 插件解耦怎么拆批提交

建议分四个可独立验收的 MR，串行合入。启动核对与失败恢复放进第一批生命周期改造一起完成，避免最后才处理新加载器留下的运行缺口。

| 批次 | 可评审的结果 | 主要范围 | 合入前验收 |
|---|---|---|---|
| 前置：基线整理 | 明确现有插件功能哪些已经提交、哪些应保留并提交 | 只处理本事项必需的现有插件代码、Skill 和依赖；另列清单 | 新 checkout 能复现规范采用的基线，不依赖原目录未提交文件 |
| MR 1：声明与绑定 | 插件从文件注册，Skill 绑定只保留一份 | `internal/plugin`、`internal/skill`、主入口、`conf/plugins/`、`conf/skills.yaml`；同步安装打包中相关文件复制入口 | 四个插件的目录/inline 生效内容一致；重复身份/缺文件报错；重启与失败重跑不重复建采集计划 |
| MR 2：通用配置页面 | 新增已有类型的配置字段无需改公共页面 | 插件声明、API View、前端类型与 `Plugins.tsx`；删除前端和 Skill 中重复默认值 | Codebase/Meego 时间范围和 Oncall 关键词可读写；未知配置键保留；UI 与采集 Task 有效配置一致 |
| MR 3：授权适配 | 生命周期只认识授权接口 | provider 实现与注册、插件服务装配及相关测试 | 现有授权流程行为保持；复用 provider 只改声明；异常明确可定位 |
| MR 4：任务展示 | 交办展示归插件，公共列表不理解交办字段 | 通用视图贡献、交办组件、导航/任务/详情页、Task 列表投影 | 普通与交办任务都可查看；停用后历史仍可查；业务字段不再进入公共投影 |

每批内默认只保留少量完整逻辑提交，修正本批实现的零碎 commit 可在发布前整理。建议合入时 squash 成一个可回退提交；这是待确认的仓库偏好，不假定远端已配置该合并方式。

纯文档方案可先独立提交；当某批实现落地时，再在同一 MR 中更新规范的实现状态与当前说明。不能先把全部提案标成已实现。

MR 4 有一个明确的展示取舍需要对齐：最简做法是公共列表保留通用进展，负责人等交办字段进入插件详情；如果要求列表保留原有交办卡片，就在插件组件中实现卡片并通过单一注册入口接入。两种方式都不把字段解析留在核心执行层。

## 5. 怎么验证“这批代码能提交”

验证对象应是该 MR 要提交的完整文件集合。不能依靠工作区里未纳入提交的文件让测试通过；最终应在可复现该分支的干净目录核对。

| 改动范围 | 必要验证 |
|---|---|
| 纯文档 | 相对链接、示例与代码事实、diff 空白检查；不为文档改动重跑全量应用测试 |
| Go 行为 | 对应模块行为测试；涉及跨模块契约时覆盖消费者，并在 MR 最终版本运行仓库 Go 测试 |
| 前端/API | 类型检查、相关行为测试、构建；涉及页面交互时验证真实显示与操作，不只看编译 |
| prompt / rules / Skill 绑定 | 检查开关前后完整有效输入；覆盖 extract/execute、目录/inline；必要时用受控证据验证实际行为 |
| 新文件加载位置 | 仓库启动及安装包的资源复制/加载路径都能找到文件，不只验证开发目录 |
| 调度与配置 | 开启、停用、重新启用、重启、保存冲突及中途失败重跑；验证历史保留与计划幂等 |

仓库现有测试入口来自 [README](../../README.md)：

```bash
go test ./...
npm --prefix web run typecheck
npm --prefix web test
npm --prefix web run build
git diff --check
git diff --cached --check
```

按本批范围执行相应检查，记录命令与结果；通过后只有新改动、失败或未解决疑点才需要重复。依赖真实 CLI、模型或外部账号的验证，未运行时说明原因与影响，不能报成通过。当前没有核实远端 CI 配置，实际提交 MR 时应读取并处理它要求的检查。

验证代码不自动重启生产实例。需要验收主服务构建或重启时，遵守 [AGENTS.md](../../AGENTS.md) 使用 `./scripts/rebuild-server.sh`，并检查正在运行的任务；合并与部署分开安排。

## 6. MR 应让你看到什么

每个 MR 开头先说具体问题和改后行为，再给范围、验证和必要限制。建议正文：

```markdown
当前新增一个插件必须同步修改 Go 注册表与 Skill 配置，容易遗漏绑定。
本次改为从声明文件加载插件及其 Skill 绑定；迁移现有插件并删除旧注册清单。

实现范围：……
基线与依赖：……
验证：实际执行的检查、结果，以及未验证的范围。
运行影响：是否需要重启、配置文件迁移，以及已有任务如何继续运行。
回退：需要恢复的代码、声明或配置，回退后如何核验。
```

不写调查流水账，不沿用已经过时的标题；范围调整后同步重写。创建 MR 前核对 source/target 分支和全部 diff，确认它只包含本批事项。

若本次授权尚未覆盖推送或创建 MR，先完成本地代码、验证和 MR 文案，再拿可审查的结果对齐远端动作。已有明确授权就按范围继续，不重复询问。Jarvis M5 的具体审批判断仍归其 [审批策略](../../conf/prompts/m5-approval-policy.md)，本文不创建第二套代码审批规则，也不增加 Go 中的提交审批状态机。

## 7. 失败与回退

- 本地验证失败：修复本批问题再提交；确认是原有失败时记录基线证据，不用跳过测试把它写成成功。
- 推送或创建 MR 结果不确定：先查询远端 SHA 和已有 MR，再决定重试，避免重复创建。
- 合并冲突：在自己的功能分支解决，重新验证受影响内容；不覆盖其它人的新改动。
- 已合入代码需要撤回：优先新增 revert 提交，保留历史；同步还原本批引入的声明/绑定。不要只回退加载器却留下它无法读取的配置。
- 本地运行状态受影响：按实际记录处理配置和采集计划，保留 Task 与执行历史。代码 revert 不代表外部副作用和数据库状态已自动撤销。

## 8. 本轮建议对齐的决定

1. **提交节奏**：推荐四个独立 MR 串行交付，每批形成完整可验收结果；不做一个大 MR，也不建立复杂的分支堆叠。
2. **合入历史**：推荐 MR 内允许少量逻辑 commit，合入时 squash 为一个提交，便于回退；远端能力与团队约定在实际提交前核实。
3. **交付终点**：推荐插件改造先交付已验证的 MR；合并、重启和部署分别由实际授权范围决定，不把它们隐含在“代码已提交”里。
4. **第一批前置条件**：先列清应纳入基线的现有插件改动，确认“我的交办”等未提交能力的去向，再开始文件化改造。

确认上述方向后，下一份实际实施清单应细化第一批的文件范围、测试案例和 MR 文案；确认本方案本身不等于授权提交当前整个工作区。
