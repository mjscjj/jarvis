# OKR 固定飞书应用与稳定人员身份方案

状态：完整实施方案 v1（2026-09-14）；尚未修改运行代码、飞书配置、授权或产品数据。权限开通与真实发送是实施阶段的独立动作，不属于本次设计执行范围。

## 结论

OKR 的人员查询、头像、登录与通知统一归属飞书应用 `cli_a96a2422f03bdbd7`，本机通过 `jarvis-notify-audit` 显式调用。应用 ID 是身份依据，profile 名只是本机配置别名；每次启动核验两者匹配，不能退回 CLI 默认应用。

MVP 统一用**已核验的完整企业邮箱**作为 OKR 负责人和评论收件人的业务标识及通知地址。已有登录会话继续使用 `union_id` 识别人；目录能提供的 `union_id` 可以保存用于核验，但不自动替换邮箱主键。邮箱前缀只用于搜索与展示。

Emily 继续承担个人助手工作，可以继续是 CLI 默认应用。OKR 不再读取这个默认值。当前另一个同名 Emily 配置不参与本方案。

## 为什么选完整邮箱，而不是邮箱前缀或强制 union_id

| 字段 | 用途 | 约束 |
|---|---|---|
| 完整企业邮箱 | OKR 人员关联、去重、筛选、通知收件地址 | 必须来自飞书目录或经核验的历史映射；保留域名 |
| `union_id` | 沿用登录身份；目录身份的补充核验 | 跨应用一致有开发者范围条件，不能认为任意应用之间都相同；当前人员搜索结果也不保证返回它 |
| 邮箱前缀 | 输入查询、界面辅助区分同名人 | 不能作为唯一键，不能自动拼接域名后直接发信或发通知 |
| 姓名 | 显示和历史快照 | 改名不应改变人员关联，不能按姓名自动合并身份 |
| `open_id` | 仅飞书适配器内部的原始 API 字段、旧数据迁移证据 | 不进入新 OKR 业务关联和通知参数；临时保存时必须与来源 App 成对 |

完整邮箱解决本次“更换应用导致身份变化”的问题，但不声称邮箱永远不变。员工邮箱更名需要有证据的显式迁移，不能把新旧邮箱凭姓名自动合并，也不能把失效地址自动猜成另一个地址。统一规范化去除首尾空白；域名大小写统一，local-part 不擅自删除点号、加号或改写别名。用户输入只是查询条件，保存时使用目录返回的规范地址；不直接把用户输入的大小写变体作为另一名人员入库。

不设计“有 union_id 时用 union_id、缺失时用邮箱、补齐后再自动换 key”的隐式规则，避免同一个人补资料后变成另一个业务对象。以后若要改为 union_id 主键，应是独立且可审计的整体迁移。

## 应用与调用链

| 功能 | 飞书应用 | 调用身份 |
|---|---|---|
| OKR 搜索人员、读取姓名/邮箱/头像 | Jarvis通知机器人 | 应用身份 `--as bot`，新增所需目录读取权限后使用 |
| OKR 登录 | 同一个通知应用 | 每位访客自己的登录身份，沿用现有登录流程 |
| 评论 @ 与 OKR 催填通知 | 同一个通知应用 | `--as bot`，按完整邮箱投递 |
| Emily 私聊、个人日历和其他助手工作 | Emily | 依照原个人助手配置 |

目标链路：

```text
通知应用的授权通讯录
  → 人员搜索结果：姓名 + 完整企业邮箱 + 可选 union_id/头像
  → 用户选择明确人员
  → 负责人/评论保存 email 与姓名快照
  → 通知应用按 receive_id_type=email 发卡片
  → 同应用读取消息回执
```

通知阶段删除“使用旧主应用将 open_id 转邮箱”的运行时步骤。接收邮箱的发送接口不再依赖 principal 的用户 token，也不要求旧主应用仍存在。

配置以 OKR 模块的飞书集成为唯一入口，明确配置 `app_id` 与 CLI profile，启动组装时向人员适配器、登录组件和通知组件传递同一应用身份。profile 改名可以更新别名，但实际 App ID 不匹配要直接报配置错误。通用通知适配器接受调用方注入的明确应用绑定，不反向依赖 OKR 业务；OKR 调用方及其催填 Skill 读取同一模块配置，不在各文件继续复制“旧主应用”常量。

建议在已有实例覆盖文件 `conf/okr-module.runtime.yaml` 中使用以下新结构（字段为拟议设计，不是当前已支持配置）：

```yaml
feishu:
  app_id: cli_a96a2422f03bdbd7
  cli_profile: jarvis-notify-audit
identity:
  # 其余登录参数沿用现有配置；不再单独保存 app_id。
  app_secret_env: JARVIS_OKR_EMILY_APP_SECRET
```

配置迁移把 `identity.app_id` 移到 `feishu.app_id`，移除 OKR 启动链对 `JARVIS_BROADCAST_LARK_PROFILE` 的独立选择与旧主应用常量。若迁移输入有多个互相冲突的应用值，报告冲突而不是按覆盖顺序猜测。通用非 OKR 调用可以显式注入自己的既有配置，不借本次改动重定义全局通知或个人助手配置。调用子进程时检查实际生效的 App，避免继承其他 App 的身份环境变量而覆盖显式 profile；只调整 OKR 子进程环境，不修改宿主机的全局环境和默认 profile。

## 查人能力的落地前提

当前 CLI 的 `contact +search-user` 是 user 身份接口，不适合直接作为通知 Bot 的查人实现。目标方案使用应用身份可访问的通讯录 API：读取授权范围、加载该范围内的人员及必要的部门分页，形成仅包含姓名、完整企业邮箱、可选 union_id、头像的轻量搜索缓存。

缓存是飞书目录的可重建索引，不是 Jarvis 世界模型的 Person 真源，也不另外维护一套人工通讯录。范围以 OKR 需要覆盖且已获授权的人员/部门为准，不默认同步全公司。姓名、完整邮箱、邮箱前缀都在该索引中搜索；同名或相同前缀返回多候选，展示完整邮箱供选择。只有有完整、已核验邮箱的候选才能成为可通知人员。

需要在开发者后台为通知应用增加**应用身份**读取授权范围、必要部门/人员基本资料、企业邮箱的能力，并配置对应数据范围；具体 scope 组合应按实际启用的 API 核验。不要为了复用 user 搜索接口，给所有 OKR 登录用户追加通讯录搜索授权。

这是接入条件，不是已完成事项。正式切换前必须用通知 Bot 真实读取一名有代表性的目标人员及邮箱，并核验分页与范围。权限无法获得时，不能声称“已全部统一”；可先固定独立目录 profile 并输出邮箱、通知固定用通知 Bot，作为明确标注的过渡方案，不静默回退，也不让全局默认 profile 决定来源。

MVP 缓存按需初始化并定期刷新，搜索缺失时允许一次明确刷新。分页失败不能把不完整结果当成完整目录覆盖旧快照；过期、缺权限或缺字段必须可见。缓存不应让新增人员永远搜不到，失效人员也不能无限期被当成有效通知地址。

初始实现采用按需刷新：缓存超过 15 分钟时，下一次查询触发一次刷新；同一应用最多一个并发刷新任务，不增加独立定时 Agent 或 Task。刷新所有授权分页成功后原子替换快照，记录 `app_id`、生成时间和完整性。无结果时允许合并并发的一次刷新，避免每次按键都拉取目录。缓存超过 24 小时且无法刷新时，可保留旧负责人展示，但不给出可新选中的目录结果。发送前按完整邮箱做必要的有效性核验；飞书明确返回离职、范围外或无此用户时，记录不可投递，不能按姓名改投。头像缺失只影响显示，不阻塞有效邮箱的使用。

上述时间是 MVP 初始运行参数，独立于身份规则，后续可根据实际规模调整。目录缓存只存必要字段和同 App 的接口内部 ID，放实例私有缓存目录，不写进产品资源或 Git；它不是完整公司目录备份。

## 数据与代码的最小闭包

统一复用一个轻量的 OKR 人员值对象，例如：

```json
{
  "email": "fengcheng.charles@bytedance.com",
  "name": "冯程",
  "union_id": "<有真实返回时才保存>"
}
```

其中 email 是已解析人员的业务身份；name 是展示快照，union_id 可空。不新增独立的全局人员 ID 系统。

同步覆盖 KR/Point 负责人、Follow-up 负责人、Plan、评论 mentions、本地负责人候选、人员筛选/去重、头像缓存、导入导出、催填收件人输出和已存在的相关快照。用同一规范化函数处理 email。已有只有姓名的负责人可继续作为未解析文本展示，但不能生成有效 @ 或进入发送计划。

`owner_key` 改为只由规范化完整邮箱生成，姓名变化不改变 key；现有 `person_id` 若继续作为模块内派生键，也必须同步迁移。仅姓名记录保留单独的未解析处理，不能通过同名直接与真实人员合并。删除业务响应里的 `main_feishu_app` 假定，所有新业务写入不接受裸 open_id 作为人员身份。

生产者：目录适配器产生已核验邮箱；所有者：OKR 人员值对象及已有 Owner/Comment 数据；组装器：服务启动时注入固定应用；消费者：前端选择、保存、关联、通知均读取 email。登录的 `union_id` 仍由 auth 所有。当前公共 `/api/people/search` 也服务 Jarvis 后台，不能直接把其全局默认语义改成通知应用；复用工具封装和 UI 搜索交互，通过显式的 OKR 查询入口/依赖组装隔离调用上下文，避免影响个人助手。

主要改动点：`internal/larkcli/` 的目录/通知边界、`cmd/jarvis-server/main.go` 组装、`internal/okrworkspace/domain/models.go` 与 `service.go`、`comments.go`、`comment_mentions.go`、API 投影、`CommentMentionInput`/`FeishuPeoplePicker`/`people.ts`/`api.ts`，以及相关 Skill、模块文档和接口说明。

### API 与存储约定

| 边界 | 新约定 | 旧行为处理 |
|---|---|---|
| OKR 人员搜索 | 明确的 OKR 查询入口返回 `candidates: [{email,name,union_id?,avatar_url?}]` 与目录更新时间；搜索交互与普通人员搜索复用 UI 能力 | 当前公共 `/api/people/search` 的个人助手语义保留；现有 Biz 兼容路由按新契约改造并同步前端 |
| KR/Point/Follow-up/Plan 的 owners | 已解析项使用 `email,name,union_id?`；未解析项允许仅有 name，但不能被当作可通知对象 | 旧客户端仅提交 open_id 的已解析项，在写入前返回明确的刷新/重新选人错误，不保存成功后才报通知失败 |
| 创建评论 | `mentions: [{email,name,union_id?}]`，每项与正文 `@姓名` 对应；邮箱必须匹配目录或已核验迁移结果 | 姓名、邮箱冲突应在保存前返回可读错误；旧裸 open_id 请求不得静默降级为可发送对象 |
| 作者、自提醒排除 | 沿用服务器认证会话的 union_id；目录或登录返回的已核验邮箱用于邮箱比较 | 不把作者的登录应用 open_id 与收件人相比较；作者邮箱缺失时，可用已确认同开发者范围内的 union_id 核验，不凭姓名排除 |
| Owner 关系表 | 增加 email、可选 union_id；email 建必要索引，owner_key/person_id 统一重算 | 人员字段的新旧语义不双写长期运行；完整迁移后移除旧业务身份读取路径 |
| Follow-up/评论 JSON | 替换内部人员值对象，保留正文/姓名快照 | 旧 open_id 与其来源仅保存在受控迁移证据中；无法解析的历史项保留可见内容、标记未解析 |
| 头像与前端选择缓存 | 按完整邮箱关联与缓存，头像来自固定通知 App 目录 | 一次性清理/升级旧 open_id、按同名缓存和浏览器选择历史，不把旧缓存复活为新人员身份 |
| 通知发送 | `SendCardToEmail(...)`，显式 profile 与 `receive_id_type=email`；输出可持久化消息回执 | 删除 `SendCardToMainAppUser` 运行时回查，禁止按昵称回退或换 Bot |

数据只需要在现有 Owner 行与 JSON 对象中增补字段，不新建一个跨模块人员注册中心。PersonID 当前是派生键，不是 Jarvis 世界模型 Person ID；迁移必须保持这条模块边界。

服务端不能只信任浏览器提交的 email/name 配对，应匹配目录快照或已核验的存储记录后使用其规范值；这是保证收件人正确的参数校验，不引入 Agent 内部权限或额外审批流程。已存在正式负责人有冲突邮箱/union_id 时列为数据冲突，不自动覆盖。

对仅姓名负责人，保留其现有未解析记录 key，不因新算 email 哈希得到同一个空值 key；明确选中目录人员后才转换为邮箱身份。同一 KR/Point 下迁移出相同邮箱的重复关系折叠为一条，保留最早排序位置；统计和审计报告解释减少的关系行数。派生数值键发生冲突时拒绝提交该迁移，不吞掉另一条关系。

现有登录及 token 文件名仍可在认证适配器内部使用 open_id，因为它们保存的是同 App 的真实凭证，不是 OKR 人员业务主键。本次应用 ID 没变，无需迁移 token 文件或让同事重新登录；不把 union_id/email 伪装成飞书凭证的 open_id。

## 旧数据迁移与失败评论

1. 先只读盘点全部人员引用，生成迁移预览、数据库备份及待处理项。当前工作区已有产品数据改动，实施时必须合并保留，不能用旧 Git 版本覆盖正在使用的数据库。
2. 根据可证明的来源 App 回读旧 open_id，取得完整企业邮箱。已验证的旧 Jarvis 与当前 Emily 都可以作为一次性迁移证据源；这不是新运行时的多应用 fallback。来源未知、同名多人或互相冲突的记录留在待处理清单，不凭空标成旧主应用。
3. 同一精确邮箱下合并重复人员引用，在事务内迁移 owner_key/person_id、Owner 与 mention、其他实际引用和缓存版本。保留原始评论正文、署名、时间、讨论层级和业务内容。
4. 迁移脚本必须可重复执行；保存原 ID→来源应用→已核验邮箱的核对清单。验证人员关系、排序、评论数与业务内容保持一致。
5. 历史评论只补身份映射，不触发通知。已经发送的提醒不重发；失败评论需要单独执行“补发这条提醒”，不让用户重发整条评论。对已有通知回执不明的记录，先核验再决定是否补发。

通知仍在评论保存后执行；失败返回简短可操作提示，例如“评论已保存，提醒冯程失败：暂时无法投递”。原始 CLI 错误只进服务日志，通过请求标识追踪。幂等依据评论 ID 和规范化邮箱；重试复用同一次投递标识及已有消息回执。飞书提供的幂等有效期不能替代长期回执；涉及补发时保存投递结果，避免成功后读回失败导致重复发送。

### 投递记录与补发的具体语义

增加最小的评论提醒投递表，按 `(comment_id, recipient_email)` 唯一。必要字段为：通知 App ID、收件邮箱、待发送卡片快照、幂等标识、状态、message_id、最近尝试时间、尝试次数、可读错误码和追踪标识。卡片冻结为创建评论时的内容，编辑评论不会偷偷改变待重试的消息。

状态只服务于评论通知这个外部副作用，不进入 M2/M3/M5 通用 Task 状态，也不新建专用 Agent 流水线：

| 状态 | 含义 | 下一步 |
|---|---|---|
| pending | 评论与投递意图已在同一事务保存，尚未请求发送 | 原请求在事务提交后发送；服务中断则页面可恢复这条投递 |
| sending | 已原子领取发送，其他请求不可同时发送同一行 | 成功持久化 message_id；若执行中断且无法确定结果，进入待核验 |
| delivered | 已取得 message_id，且同应用读回通过 | 永不因重试按钮或迁移再发送 |
| failed | 已明确知道未投递成功，例如参数、范围或身份无效 | 显示简短原因；满足条件后可重试同一行 |
| unknown | 发送超时/崩溃导致结果不明，或已取得 message_id 但读回未完成 | 有 message_id 时先只读核验；结果不明时不盲目重发 |

首次发送在同一评论创建请求的提交后尝试，沿用现有产品时序；此方案不新增自动群发或定时重发机制。pending 行是崩溃恢复依据；领取使用数据库条件更新避免双击/并发请求重复发送。重试保持同一评论、邮箱和幂等标识，飞书去重有效期以实施时接口核验为准，不依赖其永久去重。

GET 评论接口带回每位收件人的投递状态。新增“重试提醒”动作只接受原评论中已保存的收件人，不能顺带修改收件人或正文；明确失败和未发送可重试，已送达只返回已有回执，未知结果先核验。预期接口为 `POST /api/biz-okr/comments/:id/notifications/retry`，复用现有评论访问上下文，不增加按角色授权的新体系。页面显示“已提醒 / 提醒失败，重试 / 正在核验”，详细命令、stderr 不再直接展示。

旧评论没有这张投递记录，不能批量伪造 delivered，也不能全部标成 failed 后自动补发。历史迁移报告记录“未保存投递回执”。本次冯程案例有保存前后原始错误，证明发送前查人失败，可以作为单独补发的明确依据；真正发送仍应沿用用户对补发的授权。

### 邮箱变更和删除

邮箱更名时，由目录中的稳定 union_id 或其他明确企业证据建立旧→新邮箱映射，事务迁移当前负责人/筛选关系并处理重复项。已投递通知保留原始收件地址与回执；历史评论正文、显示姓名和历史投递证据不改写。未发送或失败的旧收件地址不自动改投新地址，需形成明确的新投递依据；不通过更新业务邮箱绕开旧回执造成重复发送。评论删除继续遵循已有产品语义，不能把删除已发送通知当成本次默认行为。

## 验收与交付顺序

先验证通知应用目录能力，再实现统一字段和固定应用配置，最后在短暂写入切换窗口完成迁移与部署。部署前保留数据库及配置备份；若需回退，代码与对应数据版本一起恢复，不能单独回退代码解释新字段。

必要验收：

- 自动化用不同默认 profile 的模拟环境验证 OKR 查询/发送仍显式使用通知应用；不通过修改用户全局 profile 来做测试。
- 冯程两个旧应用 ID 迁移为同一完整邮箱，姓名变化不改变负责人 key；同名前缀不同域名不会合并。
- KR/Point/Follow-up/Plan/评论/筛选/头像都消费新字段，旧缓存不能重新带回裸 open_id。
- 通知应用无需 principal 用户登录就能查询已授权人员；缺少权限、邮箱、范围或分页失败均有明确结果。
- 评论保存成功而通知失败时，页面可继续使用；重试不会重复创建评论或重复通知已确认成功的收件人。
- 经明确授权后做一条真实通知发送与读回验收；本设计阶段不发送任何消息。

交付时同步更新 `docs/design-dual-app-identity.md`，淘汰其旧默认应用描述；更新 `feishu-broadcast` 和周报相关说明，删除固定旧主应用回查路径。实施产生的 `data/okr/okr.db` 及新增/修改产品资源须按仓库规则随改动提交。构建或重启主服务使用 `./scripts/jarvis-deploy --skip-pull`。

### 分阶段工作包与完成条件

| 阶段 | 工作 | 必须交付的证据 |
|---|---|---|
| 0. 能力验证 | 配齐通知 App 的 tenant 目录/企业邮箱权限、目录范围及应用可用范围；用 Bot 查询少量代表人员、同名案例和分页 | 实际 endpoint/scope 清单、脱敏回读结果、已覆盖范围；不取得权限则不能发布“全部统一”的最终方案 |
| 1. 代码与接口 | 固定应用配置、Bot 目录适配、人员字段、key、前后端选人/筛选/头像、按邮箱通知和投递记录 | 聚焦集成测试通过，旧裸 open_id 写入不会落库；认证登录回归通过 |
| 2. 迁移预演 | 对一致性数据库副本离线迁移，盘点旧数据，保留明确来源映射 | 迁移前后计数、重复折叠清单、冲突/未解析清单、无正文改写检查、重跑零新增变化 |
| 3. 部署切换 | 冻结所有共享 OKR 数据库写入者，做最终一致性备份；运行迁移，部署匹配版本，验证后恢复写入 | 完整备份、应用绑定、版本信息、schema版本、健康检查、实际页面回读 |
| 4. 真实验收 | 用通知 App 查询人员；在已有明确发送授权下执行一条测试通知并读回；单独处理冯程失败提醒 | 精确收件人、message_id、同应用回执；不存在迁移触发的历史群发 |

不同服务和开发容器当前可能共享产品数据。维护窗口需覆盖所有写入者，并在迁移前对最终快照版本/摘要做再次核验，不能只停止当前一个进程。备份采用 SQLite 一致性备份机制；不能只复制正在运行数据库的主文件而遗漏 WAL。旧服务遇到新 schema 应拒绝业务写入，旧浏览器得到可读刷新提示。

回滚只在数据一致的窗口进行：恢复成套代码、配置和备份前，先停止新版本写入；如果切换后已有新评论/负责人修改，先保存这部分增量，不能直接恢复旧库丢掉用户数据。已经发出的飞书消息无法通过数据库回滚撤销，投递台账必须随回滚保留或合并，避免恢复旧库后再次发送同一提醒。

### 测试矩阵

| 场景 | 通过标准 |
|---|---|
| CLI 默认是旧 Jarvis、Emily 或其他应用 | OKR 的实际调用始终绑定通知 App；继承的异 App 身份环境不得覆盖绑定 |
| 改 profile 别名/配置错误 App ID | 同 App 别名可配置使用；App ID 不匹配明确失败，绝不回退默认 |
| 冯程两个旧 ID | 迁移后为同一精确邮箱，owner筛选和 @ 候选一致 |
| 同名不同邮箱、同前缀不同域名 | 不合并，页面能区分；姓名变化不改变已解析 owner key |
| 目录无邮箱、范围外、离职、过期缓存、分页失败 | 不把不可靠候选作为可投递对象；既有业务内容仍能显示，失败有明确原因 |
| 前端任意邮箱/name冲突或旧格式 | 保存前可读拒绝，不形成错误的真实收件人；未解析姓名负责人仍可存在 |
| 发送成功但读回失败；发送超时；发送后进程退出 | 使用已存 message_id 先核验；不明结果不盲重发，不伪造成功 |
| 双击重试/并发请求/服务重启 | 同一投递行只被一个执行者领取；已确认成功的消息不再发送 |
| 迁移重跑、已有数据并发变化 | 幂等；快照不一致时停止提交，不覆盖用户新写入 |
| 老登录会话、评论署名与自提醒排除 | 继续使用原通知 App 登录身份，union_id归属不变；不要求所有人重新登录 |
| 周报预览与真正发送 | 预览仍是 preview_only，不因补邮箱或投递表新增自动发送；Skill发送输出邮箱与真实回执 |

## 范围与最终交付物

本次覆盖 OKR 业务人员关联和通知使用的应用边界；不把 Jarvis 世界模型人员、个人助手消息/日历、所有既有飞书 token 一并重构。模型可在飞书 API 原始协议中看到 open_id，但新 OKR 人员业务字段不能再用它做主键或收件参数。

实施交付包括：代码与接口变更、必要测试、实例配置迁移、目录权限/范围验证记录、可重跑数据迁移及报告、产品数据库及资源提交、投递状态与重试交互、真实验收回执和完整回滚记录。迁移映射与数据库备份按既有数据管理方式保存；用户 token、应用 secret 和目录全量缓存不得写入仓库。
