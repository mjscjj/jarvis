## 保存链路的具体问题

1. 历史客户端的 `toAPIPlanObjective` 对 Owner 序列化为 `{open_id,name}`；当前客户端改为 `{email,name,union_id}`。历史实现可在 `c1cc30c8^:web/src/okr/emily/api.ts` 查到，当前实现位于同文件的 `toAPIPlanObjective`。
2. `internal/api/okr_plans.go:136` 在调用业务写入前执行 `decodeStrictJSON`；`internal/api/todos.go:205` 使用 DisallowUnknownFields。此类 400 请求在落库前失败，不会形成可从数据库找回的完整草稿。
3. `web/src/okr/emily/planStore.tsx:293` 的 saveNow 按 dirtyObjectives 顺序保存，单个目标失败即 throw，外层停止；已失败目标仍在集合中。之后编辑其它内容可能继续触发同一首个失败，而后续目标未被提交。具体 Point 使用独立 savePointNow，因此可以成功。
4. 草稿主要保存在 React state/ref；没有 localStorage/IndexedDB 草稿持久化。beforeunload 只做离开提醒，不能在刷新后恢复草稿；loadRemote 成功会以服务器数据替换草稿。PlanApp 的 localStorage 只存滚动位置。
5. `internal/api/okr_module_routes.go:133` 等 Plan 写路由未调用已有的 requireIdentity；`internal/api/okr_identity.go:113` 因此取不到用户，回落为 Jarvis。这是编辑留痕缺口，不应将日志中的 Jarvis 理解为 Agent 实际执行。
6. `internal/okrworkspace/activity.go` 只保留时间、操作者、目标及短摘要；目标保存摘要为 objective_saved，无完整 before/after，失败写入不记 activity。`writeAPIError` 也未保留请求正文。本次日志无法重建未落库请求全文。

历史客户端的 Point PATCH 是字段级更新：只有 pending patch 包含 owners 时才序列化 `owners[].open_id`。因此这 14 次失败不只是泛泛的旧页面报错，而是**请求里携带了待保存的 Owner 数据**；再结合失败后 pending patch 保留、后续字段继续合并，负责人变更以及此后同条目上的新增文字都可能一起被拒绝。不能从现有日志恢复他原本想选的新 Owner。22:46:42.259、.375、.382 三个条目在 123ms 内一起失败，符合页面批量重试积压 Point 的行为。

同时，原本看似属于另一组负责人的 354 次 `plan-o_civl1g` 错误，与这次 AI 条目编辑形成极强时序关联：

- 22:00–23:08 共 201 次 Point 成功保存，197 次在随后 1.5 秒内触发该目标失败；其中 190 次间隔在 0.85–1.05 秒，间隔中位数为 0.938 秒。
- 仅统计“AI提效”，172 次 Point 成功保存中，168 次在随后 1.5 秒内出现该错误；161 次在 0.85–1.05 秒，中位数 0.940 秒。此处包括后来被移除条目的成功保存，因此与“现存 10 条 / 165 次”的口径不同。
- 例如主播孵化条目 23:07:43.415 保存成功，23:07:44.352 同一个目标报错，相隔 0.936 秒。
- 当前及迁移前客户端的 savePointNow finally 都会在 dirtyObjectives 非空时调用 scheduleSave，延迟 700ms 重试目标；加上请求往返，与该时序吻合。

由此推断，**一个客户端先把“公会平台基建”目标留在失败队列，随后持续编辑“AI提效”；具体 Point 可独立成功，但整个目标队列反复卡在同一首项。** 这个解释比“354 次是另一批完全独立用户的偶发报错”更符合代码与密集时序。按用户提供的负责人假设，吴拓本次编辑很可能走了这条失败链路。

进一步收窄可能丢失的内容：三个总 KR 的 title 在 21:29 快照与调查快照中逐字相同，仍保留 `xx`、`XXXX` 等旧占位文字；四个失败 Point 的 Owner 也完全未变。若这次主要调整的是总 KR 文案、负责人、指标、增删结构，这些字段比已成功写入的 Point 正文更值得核对。单凭旧值不能证明他一定改过这些字段。

补充找到真实账号旁证：OKR Chat 中有 owner_id 为吴拓 union_id 的会话，23:01:16 创建、23:15:27 更新，支持其账号在该窗口访问应用；该会话无消息，draft 文本和 sources 均为空，没有找到额外草稿。AI 评审接口只接受实体 ID 并读取服务端内容，不接收浏览器完整草稿，无法补回这次未落库文字。
