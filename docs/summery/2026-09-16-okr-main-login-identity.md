# OKR 与主模块登录身份互通

## 动机和范围

储节节（`chujiejie.1`）与李潇琳（`lixiaolin`）本来就是当前实例的完整访问用户；其他协作者仍只使用 OKR 模块及其隔离聊天。本次不是新增权限，而是消除两位用户登录 OKR 后仍须再次进行字节登录的重复步骤。

当前 OKR 登录只建立 `jarvis_okr_session`，主模块只识别 `jarvis_session`。前端还硬编码了两人的识别逻辑，导致界面认识用户、后端却不认可该登录。两人的既有飞书会话都有稳定 `union_id`，邮箱可能为空，不能用姓名或邮箱猜测身份。

## 实现方案

采用直接认可有效 OKR 会话的简化方案，不交换令牌、不签发衍生主会话、不新增表或迁移历史。

1. `internal/authn` 统一解析浏览器请求身份：有效 OKR 会话按固定 `union_id` 映射主账号，并再次检查实例现有 `auth.principals`；没有有效 OKR 会话时仍认可原有字节会话。有效 OKR 身份优先，普通 OKR 用户不能借同浏览器残留的主会话进入主模块。
2. 映射只包含储节节与李潇琳，不使用请求体、姓名、邮箱或客户端标志授予主模块身份。映射说明的是跨系统账号对应关系，访问许可仍由 `auth.principals` 决定。
3. 主模块状态、浏览器门禁、请求审计和初始化身份读取共用请求身份解析。OKR 会话的原到期时间和退出状态直接生效，不复制生命周期；无身份配置的开发实例不把虚拟 OKR 用户映射为主用户。
4. 集成实例中，从主模块或 OKR 退出都清理该浏览器的两套会话和 Cookie；失败不得报告退出成功。独立挂载 OKR、没有主认证服务时仍只退出自身。
5. 前端监听 OKR 身份变化，刷新主登录状态，退出或换号后清理旧聊天组件状态；删除前端两人名单及二次登录提示。主聊天使用原 `/api/chat`，普通用户继续 `/api/okr-chat`，开发前缀仍走原开发隔离链路。
6. 聊天交互保持现状：OKR 底部输入、回复预览和完整工具能力沿用主聊天，展开历史进入现有对话页。不新增完整弹窗、不合并原隔离聊天记录、不更改宿主工具登录或世界模型 principal。

## 涉及模块

| 模块 | 修改内容 |
| --- | --- |
| `internal/authn` | 两人稳定身份映射、统一请求身份、两套会话退出 |
| `cmd/jarvis-server` | 将已有 OKR 身份服务接入主认证服务 |
| `internal/api` | 登录状态、退出、OKR 退出路由及初始化读取统一身份 |
| `internal/security` | 使用同一身份解析记录实际主账号 |

| `web/src/okr/IdentityBoundary.tsx` | 联动退出和身份刷新 |
| 现有测试与说明 | 后端身份/门禁/退出测试、浏览器入口回归和文档结果 |

## 验证计划

- 两位用户仅持有有效 OKR Cookie 时，主登录状态、受保护 API 和审计身份一致，无需 SSO；邮箱为空不影响映射。
- 普通协作者、同名或伪造邮箱、未知/过期 Cookie、主白名单移除均不能通过 OKR 获得主访问；普通人的 OKR 入口不受影响。
- 有效 OKR 账号与残留 SSO 账号不同时，以 OKR 身份为准；退出任一入口后两套旧 Cookie 均不可恢复身份，重新登录和换号正确。
- 浏览器验证两人登录后聊天使用 `/api/chat`，其他人保持 `/api/okr-chat`；完整历史仍按原方式跳转；开发前缀行为不变。
- 类型检查、受影响 Go 测试及已有聊天浏览器回归。浏览器模拟、真实会话验证与真人设备授权分开报告，不把模拟当真人授权。
