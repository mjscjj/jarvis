# Jarvis 技术产品方案：主动式任务数字分身

> 状态：演讲配套方案稿
> 当前事实快照：2026-08-18 18:55（Asia/Shanghai）
> 事实边界：当前能力以 `goal.md`、`README.md`、`docs/00-overview.md` 和代码为准；未来方向不冒充已实现能力。

## 一句话方案

Jarvis 是服务于 Principal 的主动式任务数字分身：它持续读取世界变化，从消息、会议、日程和外部线索中判断什么值得推进，使用工具把事情做完，并把结果写回可复用的世界状态。

主动式的分水岭不在执行端，而在输入端：普通 Agent 接收一个目标；Jarvis 接收“世界变了”，需要自己找到目标，并且在多数时候正确地决定不行动。

## 1. 解决什么问题

研发负责人、技术 Owner 和核心 IC 的大量工作不会先变成工单。它们散落在群聊追问、会议承诺、文档修改、日程变化、代码状态和他人等待中。人工工作流有三个长期损耗：

1. 需要持续盯住多个信息源，才能发现真正需要自己处理的事项；
2. 每次推进都要重新装配人、项目、历史和当前状态；
3. Agent 即使能执行，也不知道什么值得做、什么时候应该停、什么动作需要授权。

Jarvis 不尝试成为通用 Agent 平台，而是把这三类损耗收敛到一个单用户、本地可信的循环中。

## 3. 两个概念推出的硬约束

### 3.1 数字分身

数字分身不是等待指令的助手。它在协作现场代表 Principal，因此必须满足：

- 长期记忆是世界模型，而不是无限延长的聊天历史；
- 对外副作用必须能停下来请示，并且批准动作不可由模型自行推断；
- 每次判断和外部后果都可追溯。

### 3.2 主动式

主动式不是定时制造任务。它必须满足：

- 输入可以只是“世界发生了变化”，不要求人预先提供目标；
- 系统可以合法、明确地以 `observing` 或 `NOTHING` 收尾；
- 新来源只负责提交原始事实，不在采集层提前做语义判断。

## 4. 当前系统方案

### 4.1 世界模型：状态只有一份

世界状态分成两类互补载体：

- 实体 `summary` 页回答“现在是什么”；
- Fact 事件流回答“发生过什么”。

页面整体读写、有字符上限、有 CAS 并发保护和修订历史；事实流保留历史证据。默认上下文只提供摘要和计数，Agent 需要时再按实体、日期和来源下钻。这样写入单位与读取单位一致，世界模型才有可能被持续维护，而不是只追加噪声。

### 4.2 通用流水线：来源差异留在外围

```text
飞书消息 / 会议 / 日程 / 外部 Skill
                 │
                 ▼
M2 采集：存原文、幂等、唤醒
                 │
                 ▼
M3 准入：只判断是否值得启动一次执行
        ├── observing：保留事实，不创建 Task
        └── extracted
                 │
                 ▼
机械固化：不调用模型，幂等创建 Task
                 │
                 ▼
M5 执行：调查 → 选择动作 → 执行 → 验证 → 停止
        ├── done / observing / failed
        └── waiting / needs_human / awaiting_approval → 续跑
```

M2 不解释错误语义；M3 不提前做 M5 的工作；固化层不增加第二次判断；M5 持有完整语义判断权。新来源通过 `source + Skill/定时任务 + /api/clues` 接入，不在 Go 中复制专用流水线。

### 4.3 执行与审批：风险在动作内容里

审批不按 `action_type` 分流。改代码可能只是注释，也可能删除数据；发消息可能只是回复“收到”，也可能做出无法兑现的承诺。

模型结合即将发生的具体副作用决定是否请示；代码只提供：

1. `awaiting_approval` 状态；
2. 批准与驳回入口；
3. TaskEvent、ExecutionRun 和 effects 留痕。

批准是严格机器动作，纠偏保持自然语言。外部后果当前是 Agent 声明，不是独立 receipt verifier 的核验结果。

### 4.4 主动巡视：NOTHING 是高质量结果

主动巡视周期读取世界模型，优先看护未闭环工作，再检查今天的新变化。它可以维护明确的内部认知，但不能直接改变外部业务世界。需要外部动作时只创建普通 Task，交给同一个 M5 执行入口。

单轮没有值得推进的事时，应明确结束为 `NOTHING`，而不是为了显得主动制造工作。

## 5. 用户体验形态

Jarvis 对 Principal 的体验应收敛成三个稳定节律：

| 节律 | 回答的问题 | 主要载体 |
|---|---|---|
| 晨间简报 | 今天先完成什么 | 飞书 + 本地 Markdown |
| 协作主干 | 需要确认什么、卡在哪里、是否改方向 | 飞书原消息/卡片 + Task |
| 每日复盘 | 今天实际发生了什么 | 日报与 Worklog |

本地后台承担深度查看、配置、世界模型维护和运行观测；飞书承担低摩擦的触达、批准、纠偏和结果回传。

## 6. 当前不成立的部分

以下内容必须作为缺口呈现，不能写成已有能力：

- 没有独立 Goal Store、Supervisor 和 Verifier；
- effects 是 Agent 声明，不是外部系统回执核验；
- 冻结的上下文快照不是版本化实时世界状态；
- 世界模型页覆盖仍不完整：人物 41/103、项目 4/7、资料 8/35；
- 编辑已有飞书消息不会重新唤醒 M3；
- 仍有 72 个 Task 处于 failed，执行与工具链尚未达到稳定终态；
- `needs_human` 仍需继续压缩到“只有 Principal 才能回答”的问题。

## 7. 下一阶段建议

下一阶段不优先增加更多自动化场景，而是提升“判断可信度”：

1. **补齐世界模型覆盖与维护质量**：让关键人物、项目和资料页持续更新，并能用新事实淘汰旧结论；
2. **增加结果核验能力**：把关键外部副作用从 Agent 声明升级为可核对的 receipt；
3. **降低对人的廉价询问**：先查工具和世界状态，只有确实无法自行获得的答案才进入 `needs_human`；
4. **建立长任务目标控制**：在真实需要出现后，再增加最小 Goal、Supervisor 和 Verifier，而不是提前建设平台。

## 8. 成功标准

Jarvis 的成功不等于完成更多 Task。更准确的标准是：

- 该行动时行动，不该行动时不打扰；
- 每次行动都能解释依据、当前状态和外部后果；
- 上一次执行沉淀的认知，真实影响下一次判断；
- 新来源不污染核心流水线；
- 系统运行一个月后，世界状态仍然可读、可改、可复用。

> 主动式 Agent 最难的不是把活干完，而是在绝大多数时刻正确地什么都不做。
