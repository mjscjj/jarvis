## 1. 已确认的需求

1. 沿用现有域名、`/dev/` 入口和隔离设施，不增加子域名，不重做隔离体系。
2. OKR 业务数据继续由两个实例共享，主实例其他模块仍可读取共享数据。
3. 从主站进入 OKR 时，页面、编辑、对话和附件统一使用开发实例。
4. 主站以前分享出去的 OKR 链接也应自动进入 `/dev/`，原链接无需重发。
5. 主实例保留自己的私有系统、聊天、任务和定时任务；开发实例保留独立完整系统。
6. 实现局限在外层导航，复用现有代理、接口、登录和存储，不增加网关服务。
7. 先维护开发方案和问题记录，再按方案推进；用户已确认继续实施。

## 2. 总体方案

采用“进入 OKR 时整页切换安装路径”。主站首次打开 OKR 或从内部导航切入 OKR
时，把浏览器安装路径从 `/` 改为 `/dev/`，后续由开发实例运行整个页面。

```text
主站非 OKR 页面 ──────────────────→ 主实例代码、接口和私有运行数据
主站 OKR 入口 / 旧 OKR 分享链接
                  └─ 整页切换 /dev/ ─→ 已有代理 ─→ 开发实例页面、接口和聊天
主实例、开发实例 ──────────────────→ 共享 data/okr/ 业务目录
```

`#/biz-okr`、`#/weekly-report` 和旧别名 `#/okr` 均由现有路由解析器识别。
服务器收不到 URL 的 hash，因此判断放在前端入口及统一导航层。首次跳转在
挂载登录、OKR 页面和聊天组件前执行，避免先加载主站 OKR 数据再切换。

### 旧链接的明确承诺

目标示例：

```text
https://emily.bytedance.net/#/weekly-report?tab=okr-plan&quarter=2026-Q4&plan_id=abc
→
https://emily.bytedance.net/dev/#/weekly-report?tab=okr-plan&quarter=2026-Q4&plan_id=abc
```

只替换安装路径，完整保留 query 和 hash，包括 `tab`、`quarter`、`week`、
`plan_id`、`region`、`comment_id` 等参数。新分享链接沿用开发实例的
`public_base_url` 生成 `/dev/` 地址；旧通知卡片里的主站 OKR 链接同样切换。

**已在主站部署，并用公开域名真实浏览器验证：三种旧 OKR 链接都会自动进入 `/dev/`，query 与 hash 参数保留。跳转不等于免登录，开发实例仍使用自己的登录会话。**

## 3. 数据与请求归属

| 内容 | 归属及处理 |
| --- | --- |
| `data/okr/` 数据库、图片和产品资源 | 继续共享，保留当前挂载，不迁移、不复制 |
| 浏览器 OKR 页面、编辑和查询 | 开发实例 |
| 切换后发起的对话、历史与聊天附件 | 开发实例的运行数据 |
| 主实例已有私有聊天、任务、定时任务 | 保留主实例，不自动搬迁 |
| 开发实例自己的任务、定时任务和其他模块 | 保留开发实例，不自动跳回主实例 |
| 主实例其他模块对 OKR 的访问 | 保留本实例调用链，读取共享业务数据 |
| 登录状态与 CLI 授权 | 按实例保存；开发 OKR Cookie 使用独立名称和 /dev/ Path，不覆盖或清理主站 SSO |

不按 `/api/okr` 前缀全局转发主实例 API。浏览器整页切换后，依赖现有
`jarvis-base` / `appPath` 请求 `/dev/api/...`；主实例其他模块的调用不受影响。

主用户在开发实例有完整访问权限时，沿用开发实例 `/api/chat`；普通 OKR
协作者沿用开发实例 `/api/okr-chat`。两者都必须落在 `/dev/` 下。
聊天历史的“在对话页继续”保留当前实例和会话；显式“返回主工作台”才返回主站。
返回链接对开发者及原有其他 OKR 用户仍可见；指定主站账号改为菜单自动导航，见第 11 节。主站仍按原有规则检查访问权限。

仅决定浏览器是否自动切换，允许暂停自动切换而保留 `/dev/` 的直接访问。

### 身份真源与最小配置

飞书 union ID → 企业账号映射已从 `internal/authn/http.go` 的固定人员表迁至
本机 `auth.feishu_accounts`，详见第 14 节。不在前端重复判断姓名，不猜邮箱，
不把 URL 或客户端传入的邮箱当成登录身份。
开发实例新增一项本机配置：

```yaml
server:
  main_workbench_path: /
  main_workbench_accounts:
    - lixiaolin
```

列表支持已核验企业账号或其规范邮箱，启动时读取。`lixiaolin` 只出现在本机
导航配置中，前端不写死这个人。已有映射中的邮箱可用于配置匹配，但不能通过
一个未知 union ID 声称同样邮箱就获得这个偏好。

现有 `/api/auth/status` 返回可选布尔值 `prefer_main_workbench`；没有新增
业务 API 入参或接口。`RequestStatus` 可以为已经核验的 OKR 身份返回导航
偏好，同时仍返回本实例 principal `status=unauthenticated`、不提供 principal
`user`。偏好与访问权限分开，既有主/开发 principals 名单均不扩大。

## 16. 开发进程托管修复（2026-09-16）

### 问题与维护边界

第 15 节恢复之后，开发服务再次消失。可见日志记录 15:24:42 收到 TERM、

Docker 的 `unless-stopped` 只在容器退出时生效，存活的转发进程让容器继续

  检查报错，不能以进程管理器的 RUNNING 状态代替 HTTP 可用性。

  删除手工 kill / nohup 与 PID 文件真源。增加容器部署文件锁，串行构建及
  替换同一二进制。`--config` 必须与容器设置一致，换配置通过重建容器完成。
- `stop-jarvis.sh` 容器分支通过 Supervisor 显式停止，避免用户要求停止后
