# OKR 模块全量验收记录（2026-09-16）

## 目标与口径

本轮在主用户 OKR 登录复用主模块身份的改动基础上，对 OKR 模块做一次覆盖主要用户路径的发布验收。真实站只使用储节节本人现有飞书授权，所有临时业务数据使用 `[OKR真实验收 <运行编号>]` 标记并通过正式 API 精确清理；不冒充李潇琳执行真人登录，也不向同事或群聊发送测试通知。

验收分三层：公开主站验证真实身份、真实数据库和真实飞书集成；隔离浏览器工作流验证高副作用或边界场景；Go 与 TypeScript 自动测试验证服务、状态和纯逻辑。浏览器自动签发的短时会话来自储节节已保存且实时向飞书核验的授权，因此覆盖登录后的真实产品路径，不覆盖重新扫码或设备授权本身。

## 本轮发现与修复

真实 Plan 测试发现一个会影响用户的竞态：页面初始读取旧 Plan 列表尚未返回时，新建 Plan 已成功，随后旧响应可能把当前选择切回旧 Plan，导致下一步目标写入旧 Plan。

修复保持最小范围：`PlanBoardProvider.createPlan` 在创建前使既有读取代次失效；创建成功后明确恢复远端可保存状态。没有新增状态模型、接口或数据库结构。隔离浏览器加入“延迟旧 Plan 列表响应”的回归用例，确认旧响应不再覆盖新 Plan，且新 Plan 后续可继续自动保存。

## 边界与已知非阻断项

- 李潇琳的映射、接口门禁与浏览器行为由服务端和浏览器夹具覆盖；本轮没有她的独立真实浏览器授权，因此不声称完成第二个真人账号登录。
- 没有重复发送导出文档或 @ 通知；本轮复用并重新回读此前同一部署链路生成的真实证据。
- `go test ./...` 会把仓库忽略目录 `var/` 内的历史源码副本和 Go 缓存误当成当前模块包；明确测试当前源码范围 `./cmd/... ./internal/...` 全部通过。
- 前端生产构建仍提示既有的大 chunk 警告，部署依赖检查仍提示一个 high vulnerability；两者均不是本次身份或 Plan 修复引入，也不阻断本轮交付。

## 结论

未发现阻断发布的问题。两位主用户的 OKR 登录复用主模块能力符合既定权限范围，其他 OKR 用户隔离保持不变；本轮发现的 Plan 选择竞态已用最小改动修复并完成真实站与回归验证。
