# Jarvis 架构图三种 Skill 对比：统一简报

## 任务目标

基于同一组 Jarvis 架构事实，生成一份可独立阅读的中文架构图，突出各自 Skill 的表达优势。图的主标题统一为：

> Jarvis：从线索准入到真实结果闭环

核心叙事：**线索只是起点，真实结果才是终点。M3 低成本准入，M5 持续调查、判断、执行、验证；结果沉淀回世界状态，影响下一轮决策。**

受众是工程与产品架构评审。表达产物不是架构事实真源；事实以 `goal.md`、`docs/00-overview.md` 和当前代码为准。

## 必须准确表达的架构事实

1. 外部现实会通过消息、日程、文档、代码仓库、定时 Skill、主动巡视或人工介入产生新事实。
2. **M2 是机械采集层**：保留原始证据、来源和外部幂等键，唤醒 M3；不做语义分类，不按来源开专用流水线。
3. **M3 是低成本准入，不是“快脑”**：只调查到足以决定 `extracted` 或 `observing`，证据足够就停止；准入时冻结完整 `context_snapshot`，不制定执行方案、不选择副作用、不判断审批。
4. `extracted Todo → pending Task` 是机械、幂等的固化步骤。Task 保存完整 `source_payload` 与冻结 `background`；这些是开放线索和审计证据，不是不可修改的执行合同。
5. **M5 是唯一的语义决策与执行核心**。每次运行读取来源证据、冻结背景、实时 `current_world`、人工 supplements 和最近运行记录，并按需查实体 Summary、Fact 与外部系统。
6. M5 在同一个执行循环里完成：上下文装配 → 深入调查 → 判断下一步 → 调用工具产生动作 → 验证真实结果。它可以因新事实重新调查和改写当前目标；快慢思考是同一 M5 Agent 内的行为，不是两套流水线模块。
7. 等待、人工补充和审批会暂停并恢复同一个 Task；审批由 M5 针对具体副作用判断，可以发生在任意时刻，不按 `action_type` 分流。
8. 验证失败或现实变化必须回到调查/判断，而不是把“工具调用成功”当成任务完成。可结束为 `done`、`observing`、`waiting`、`needs_human`、`awaiting_approval` 或 `failed`。
9. 执行结果、`effects`、TaskEvent、ExecutionRun 等事实载体进入持续世界建模，形成实体 Summary、Fact 与后续运行可读的 `current_world`；闭环必须真的影响下一轮决策。
10. Go/runtime 只负责硬边界：持久化、状态、幂等、调度、权限/审批载体与 effects/event 审计；自然语言目标、调查、判断和计划留给模型。
11. 主动巡视可以读取世界状态；需要外部行动时创建普通 Task，仍交给同一个 M5 执行，不形成第二套决策链路。

## 不得引入的错误概念

- 不得把 M3 画成“快脑”或完整决策器。
- 不得把 M5 画成机械执行上游固定计划的 worker。
- 不得新增 M4、Goal Supervisor、独立 Verifier 等当前尚不存在的模块。
- 不得把 Qdrant 画成长期事实真源；它当前只服务 Todo 语义去重。
- 不得为会议、邮件、飞书等来源画专用 Go 流水线。
- 不得把审批画成所有任务必经的固定阶段。
- 不得用“API/工具返回成功”代替现实结果验证。

## 统一视觉与信息约束

- 中文文字必须准确、可读；优先使用短标签与分层说明，避免大段正文塞进节点。
- 主链路应清楚呈现：`外部现实 → M2 → M3 → Todo/Task → M5 → 真实结果 → 世界状态`。
- 必须明显画出两条反馈：
  - 验证失败/新事实 → 回到 M5 调查与判断；
  - 执行结果 → 世界状态 → 下一轮决策。
- 第一眼只保留 3–5 个一级概念；实现名、状态和边界放到二级标签、注释、图例或交互详情。
- 使用各 Skill 自己最擅长的视觉语言，不要求三份图采用同一几何布局。
- 连线不穿节点；文字不重叠、不截断；视觉层级、色彩语义和箭头方向必须一致。
- 在图或配套说明中注明：`架构事实源：goal.md、docs/00-overview.md 与当前代码；本图为表达产物。`

## 每个 subagent 的交付要求

1. 只编辑自己被分配的子目录，不覆盖现有架构图或其他 subagent 的文件。
2. 交付可编辑源文件、最终可查看产物、简短说明和验证记录。
3. 按对应 Skill 完成结构/语义校验与可视化检查；发现重叠、裁切或事实误读时迭代修正。
4. 保留有价值的中间版本；不要把临时缓存和依赖复制进交付目录。
5. 最终汇报：产物绝对路径、验证命令及结果、视觉检查结果、仍存在的限制。

## 验收问题

- 3 秒内能否看懂“这是从现实变化到真实结果、再回到世界状态的闭环”？
- M3 与 M5 的职责边界是否准确？
- M5 的调查—判断—执行—验证循环是否可见？
- 验证失败回路和世界状态反馈回路是否可见？
- 单独打开产物，不读本简报，是否仍能理解核心叙事？
- 是否不存在文字重叠、节点裁切、线穿节点和错误架构概念？
