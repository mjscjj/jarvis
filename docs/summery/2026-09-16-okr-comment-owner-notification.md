# OKR 新增评论负责人及 @ 通知交付说明

日期：2026-09-16

## 需求结论

新增评论保存后，系统基于评论所对应的 OKR 原文，生成一组确定的通知收件人：

1. 优先通知当前具体 KR（策略具体 KR 或产品具体 KR）的全部负责人。
2. 当前具体 KR 没有负责人时，向上通知所属 KR 的全部负责人。
3. KR 也没有负责人时，向上通知所属 O 的全部负责人。
4. 评论中显式 @ 的人员始终加入通知集合，不受上述负责人层级选择影响。
5. 同一人同时是负责人且被 @ 时只发送一次，并在状态中标记为“负责人 + @”。
6. 评论作者本人不接收自己触发的通知。

“当前层级已配置负责人但身份不可投递”不会回退通知上级负责人，因为这属于当前负责人身份数据问题，不应改变责任归属。

## 权威链路

```text
评论保存
  -> 固化评论原文、评论内容、O/KR/具体 KR 上下文
  -> 选择最近一层负责人
  -> 与显式 @ 人员取并集、按邮箱去重、排除作者
  -> 为每位收件人写入持久化 delivery intent
  -> Jarvis 通知机器人异步发送
  -> 保存 delivered / failed / unknown 状态及 message_id
  -> 页面显示负责人、@、负责人 + @ 的投递状态
```

投递重试只使用评论创建时持久化的原始意图，不重新读取后来变化的 OKR 负责人，避免重试内容和评论发生时的事实不一致。幂等键由评论 ID 和收件邮箱稳定生成。

## 实际改动

- 评论通知路由支持 Point -> KR -> O 的最近负责人回退，并与 @ 人员合并、去重。
- 新增 O 负责人持久化模型及核心 Board、Plan 的创建、更新、读取、删除链路。
- 补齐 Plan 聚合存储、人员索引、世界节点投影和邮箱迁移对 O 负责人的支持。
- 飞书卡片同时呈现评论内容与对应原文，并按原因显示“评论了你负责的产品具体 KR／策略具体 KR／KR／O”或“并 @ 了你”。
- 前端 O 标题支持选择和展示负责人；评论投递状态区分“负责人”“@”“负责人 + @”。
- 数据库迁移新增 `okr_workspace_objective_owner`，原有 `okr_workspace_comment_delivery` 继续作为投递真源。

## 边界

- 新规则只作用于部署后的新增评论，不回填或自动补发历史评论。
- 没有任何层级负责人且评论也没有 @ 人员时，不生成通知投递记录。
- 评论保存和通知发送解耦：评论先成功持久化；发送失败、结果未知或应用缺权限时保留投递状态，可沿既有重试入口处理。
- 构建与服务健康已验证；由于当前容器缺少浏览器运行时，本记录不声称页面实际交互已经验收。
- 源码与 `data/okr/okr.db` 已落盘并由当前服务使用，但在 Git 元数据恢复前无法按仓库规则提交产品数据库和代码改动。
