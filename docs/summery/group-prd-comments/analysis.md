## 一、九类高频关注点（按证据频次）

1. **必要性与目标人群** — 上来就问「为啥要做这个功能」「预期谁是不打开的」「整个方案没 sign off，先判断哪些是基建」「搞半天才 3400，这个咋算出来的」。要求 PRD 讲清楚做它的理由、不做会怎样、目标用户与非目标用户。
2. **核心逻辑质疑** — 不接受表面结论，追问「核心逻辑是不是也不只是认领，认领不建联有用么」「这不应该是个固定指标吧／应该是个活动页概念？」「这是活动还是政策的」。逼产品把底层逻辑、概念归属讲对。
3. **交互与异常边界** — 「这个弹窗能关闭吗」「这个要瞬间消失吗」「为啥只能二选一」「邀请制要不就对非邀请人不参与了吧」「这个交互左右滑不是很友好」。关注具体交互态、可关闭/可退出、二选一的合理性。
4. **准入准出与存量兜底** — 「准出逻辑是啥」「公会主播退出公会失去开播权限吗」「存量也是 opt out 吧」「若拒绝则继续适用原规则——怎么理解」。反复确认权限的准入/准出、存量用户如何迁移、拒绝/失败分支。
5. **数据可见性与埋点** — 「在哪能看领了多少条」，即功能上线后运营/管理者从哪看数据、效果如何度量。
6. **审批/规则一致性** — 「我记得这个决策不是说争议才批」「现在是每个变化比例都要批吗」「这个也是每个都要批吗」。拿 PRD 规则和既有决策口径对照，抓不一致。
7. **跨团队/平台对齐与复用** — 「这块对齐客服平台」「不是说不和 Bax 融合」「客服入口 vs Bax 定位有什么不同，讲一下」。要求说清与相邻平台/产品的边界、是否重复建设、能否复用。
8. **表达含糊要求讲清/举例** — 大量「讲一下」「怎么理解」「看不清，讲一下」「给点例子」「具体是啥」「这个逻辑有点没看懂」。凡是抽象描述、无指导意义的文案（如「提升建议感觉说了跟没说一样」）都要求补例子、补细节。
9. **可验证与工具化诉求** — 「能给我一个表或者一个 agent 么，输入 uid/agency id 看匹配结果」「能按 BPO 流程画个跟进图吗」「画个时间线」。倾向把逻辑做成可自助验证/可视化的工具或图。

## 二、评审风格特征

- **短促直接、问题驱动**：几乎每条都是一个尖锐问句，不写长评语；命中要害即停。
- **先问「为什么做」，再问「怎么做对」**：必要性/优先级永远前置，其次才是逻辑、交互、边界。
- **对齐既有事实**：常以「我记得……」「不是说……吗」把方案和历史决策、既定口径校验。
- **要证据不要形容词**：抽象文案、模糊指标、无指导意义的建议一律要求举例、量化或画图。
- **关注存量与异常**：新功能默认追问存量迁移、拒绝分支、退出/准出的兜底。
