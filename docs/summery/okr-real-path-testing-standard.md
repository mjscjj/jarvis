# OKR 真实路径测试规范

本规范是 OKR 身份、评论、导出及相关页面交互的验收依据。自 2026-09-14 起生效。它定义后续测试要求，不表示这些场景已经完成验收。

## 1. 真实身份与授权范围

用户已明确授权后续使用 **chujiejie.1 / 储节节** 做真实路径测试。该范围内不重复索要测试许可。测试评论、回复和导出使用明确标注的测试内容；一对一 @ 提醒仅发送给本人，不向同事或群聊发送测试消息，不修改正常业务记录。

真实验收必须沿以下路径执行：

```text
本人已核验的网页登录会话／从本人现有授权签发的短时测试会话
                    → 页面操作 → 实际后端 → 实际持久化
                                           ↓
                                 如涉及飞书，调用真实接口
                                           ↓
                              页面刷新及外部结果回读核验
```

- 核对页面用户、当前会话接口及飞书授权所属人一致，并记录对应应用。姓名只用于展示，不能单凭同名认定身份。
- 邮箱可能未返回。不能因按账号搜索邮箱未命中，就断定没有登录或要求重新授权；应继续核对姓名、会话与应用内用户标识，再用真实接口确认身份。
- 用户浏览器的登录、测试浏览器的登录、服务端保存的飞书授权是三个独立状态。存在有效授权不等于测试浏览器已有会话；网页登录有效也不等于飞书凭证仍可用。
- 优先复用测试浏览器中本人的有效登录。测试浏览器没有继承日常 Chrome 会话，但本机已有本人授权时，可以用 `scripts/okr-real-test-session` 先向飞书实时核对 open_id、union_id、姓名，再签发 45 分钟的专用 OKR 测试会话。测试结束调用产品登出接口撤销它。此方式验证登录后的真实业务路径，**不算产品设备登录流程已通过**。不得注入虚构用户或模拟飞书结果，也不得要求用户把 Cookie、访问令牌或刷新令牌贴到聊天中。
- 导出使用当前网页登录人的飞书凭证。评论作者来自当前会话；@ 消息由配置的 Jarvis通知机器人发送，收件人为本人。不能要求通知 Bot 冒充用户发送，也不能让导出回退到服务器默认账号。
- 一个人的测试不能证明两人隔离正确。第二个真实账号必须另有本人授权；没有账号就把双账号真实验收记为未验证，不用模拟账号补成“通过”。

## 2. 测试环境和数据

每次开始记录运行编号、代码提交及未提交改动、访问域名、实例、前后端版本、数据库实际路径和飞书应用绑定。先确认公开域名实际指向哪个服务，不能拿另一个端口的成功替代该环境的结果。

开发验证优先在独立 worktree 和独立数据库中进行。worktree、容器或端口不同不代表数据隔离；本项目开发实例可能共享 `data/okr/`，须检查实际路径和符号链接。飞书账号、通知和云文档不会因本地数据库隔离而自动隔离。

使用标题或正文前缀 `[OKR真实验收 <运行编号>]`，为测试创建专用页面或记录。发布后在目标部署环境重验时也使用专用数据，不在正常讨论中灌入测试内容。

保存测试评论 ID、文档链接、通知回执和处置情况。只清理本轮创建且已确认归属的测试数据；有真实回复或用途不明的记录先保留说明。不得通过恢复整库清理测试而覆盖同期业务写入。涉及产品数据库或资源变动时，按仓库要求提交一致快照，授权文件、Cookie 和令牌不得进 Git。

## 3. 每轮执行顺序

1. 复现用户报告的具体页面和操作，保存错误、网络响应及对应日志。未复现时区分事实与推测。
2. 在隔离环境完成修改和有针对性的单测、类型检查；涉及状态、并发或迁移时运行对应后端测试。
3. 使用本人的真实登录，从浏览器执行受影响业务及相邻关键路径；涉及飞书的操作必须执行真实调用并回读结果。
4. 通过 `./scripts/jarvis-deploy --skip-pull` 构建前后端并重启选定实例。健康检查只证明进程可用。
5. 在最终访问域名重新验证登录、评论和导出等本次涉及的关键路径，检查页面加载的是新产物。主服务与开发预览分别记录，不能互相代替。
6. 输出验收记录；失败和缺少前提的项目不得计为通过。修复后重跑失败项及受影响路径。

纯文档等不影响运行行为的修改无需部署或真实发送消息。业务改动按影响范围选择下列用例；修改共享登录、身份、路由、人员或凭证逻辑时，评论与导出必须一起回归。

## 4. 评论验收

适用入口包括 Plan、Review 填写和会议、周报填写和会议，以及部署版本存在的区域对齐入口。记录逐入口结果，不以一个抽屉成功推断所有入口正常。

| 场景 | 操作与通过条件 |
|---|---|
| 打开与读取 | 页面及 KR/Point 等评论入口可打开，目标、已有讨论和数量正确，无控制台异常或被遮挡的关键按钮 |
| 发布 | 以本人发布测试评论，立即出现且可见；作者身份正确，刷新及重新打开后仍存在，只保存一条 |
| 回复和修改 | 对自己的测试讨论回复、编辑，检查层级、内容和持久化；按产品规则删除本轮测试记录并核验 |
| 加载时发布 | 延迟真实列表响应后发布，再放行；新评论和已有讨论均保留。允许延迟真实网络响应，不得替换返回内容冒充真实服务 |
| 解决与历史 | 标记解决后默认隐藏、数量更新；右上角历史开关可见；重新打开回到默认列表；历史评论直达链接可定位 |
| 页面切换 | 切换周、Plan 或评论目标时没有上个目标的评论串入，迟到响应不覆盖当前列表 |
| 人员与 @ | 搜索本人，核对完整收件身份；评论先保存，通知状态最终与本人收到的卡片及回执一致，卡片能打开正确讨论 |
| 通知失败与重试 | 在隔离环境可控地产生失败，确认评论保留、状态及原因可见；结果不明先核验，已送达不重复发送，不为测试撤销全局权限 |

“评论保存成功”和“@ 已送达”分别验收。UI 显示成功、数据库存在或发送返回成功中的任一项，都不能单独替代完整结果。

## 5. 导出验收

1. 用本人的真实会话从 Review／周报的实际导出按钮操作，不能直接执行 CLI 后宣称页面链路通过。
2. 确认调用选取当前登录人的凭证，必要时经产品现有机制刷新；不使用服务器默认用户或 Bot 创建文档。
3. 打开返回的真实飞书文档，核对创建人／所有者身份、标题、正文及关键结构与页面导出内容一致；记录链接及回读证据。无法读取归属时明确记为未验证，不能仅凭命令参数推断归属。
4. 保留飞书默认密级与分享设置，由本人决定分享；不把“全员可编辑”作为成功前提，不在测试中扩大权限。
5. 核对未登录、授权失效、缺少权限和外部失败时的提示、按钮恢复及链接状态。不得回退到其他身份；超时或部分成功先调查已创建结果，避免盲目重试产生多份。

凭证过期、撤销和缺权限等破坏性条件优先在隔离测试中验证，不主动撤销本人正常授权。若只使用模拟错误覆盖这些分支，必须标注为模拟测试，不能声称真实撤销／过期流程已验证。

## 6. 自动检查与真实验收的边界

单测及模拟接口继续用于快速定位、异常分支和并发覆盖，不能代替真实路径验收。报告必须分别列出：单测、模拟浏览器测试、真实浏览器与外部调用验收、部署后验证。

当前已知检查入口的限制：

- `npm --prefix web test` 运行 `test/*.test.ts`，不包含 `*.browser.mjs`。
- `TestOKRBrowserWorkflow` 缺少 `OKR_BROWSER_URL` 时会跳过；现有测试会注入测试会话，文档创建返回模拟结果，属于模拟集成测试。
- `OKR_BROWSER_EXPORT_ONLY=1` 仅执行导出专项，不能据此报告评论回归通过。
- 已解决评论的模拟浏览器脚本只证明展示交互；不得直接对生产实例运行未经数据范围核对的写入脚本。

`npm --prefix web run test:okr:real` 是独立的真实验收入口。必须设置 `OKR_REAL_BASE_URL`、`OKR_REAL_PROFILE_DIR` 和经核验的 `OKR_REAL_EXPECTED_OPEN_ID`；它可以使用专用浏览器 profile 中已有的产品登录，也可传入 `OKR_REAL_SESSION_FILE` 使用由本人现有真实授权签发的短时测试会话。后一模式只绕过设备登录步骤；页面、后端、数据库与飞书调用仍走真实路径，并在输出里将 `login_flow_tested` 标为 `false`。默认执行九项：八个入口的登录与导航、真实人员目录、Review 评论、周报评论、临时 Plan 定义与评论、区域对齐需求与评论、Review 与周报导出、@ 本人。评论项检查作者、保存、刷新、回复、编辑、解决、历史、重开和回读，并清理本轮评论、Plan 与区域需求。可用 `OKR_REAL_CASES` 选择其中的场景。导出结果只有 UI 和接口创建成功、@ 结果只有发送回执成功时，仍须回读飞书文档归属／正文及本人收件箱后才算完整通过。Review 周次由 `OKR_REAL_WEEK` 指定，普通周报周次由 `OKR_REAL_WEEKLY_WEEK` 指定；临时 Plan 与区域对齐使用 `OKR_REAL_PLAN_QUARTER`。运行时的 JSON 输出只含测试身份标识、评论 ID、通知消息 ID 与文档链接，不输出令牌。

普通 Chrome 窗口中的登录不会自动共享给 Playwright。现有有效飞书授权已足够进行业务路径测试，无需用户重复扫码或提供 Cookie。若要单独验收产品设备登录，则在非无头模式（`OKR_REAL_HEADLESS=0`）用专用 profile 完成一次真实登录；不得把短时测试会话的结果报告为设备登录成功。

本机一键运行入口是 `scripts/okr-real-acceptance`。它先用 `scripts/okr-real-test-session` 对本人现有飞书授权实时核身，短时会话只写入目标服务读取的会话库；然后执行 `web/test/okrRealPath.browser.mjs`，最后用 `scripts/okr-real-readback` 回读飞书文档元数据、正文、通知消息及收件会话成员。浏览器异常退出也会撤销本轮短时会话。`OKR_REAL_CASES` 可选择单项；例如 `OKR_REAL_CASES=navigation,people scripts/okr-real-acceptance`。运行前需按所在机器设置 `PLAYWRIGHT_MODULE` 和 `CHROME_EXECUTABLE`；`OKR_REAL_BASE_URL` 默认是主站，验证开发实例时必须显式指定，并检查该实例使用的会话库，必要时设置 `OKR_REAL_IDENTITY_DB`。证据文件写入忽略 Git 的 `var/okr-real-run.*`，Cookie 和令牌不在测试结果中输出。真实外部读回或卡片跳转有一项失败，整轮即返回非零。

测试入口应明确区分模拟与真实运行。真实运行缺浏览器、账号、服务或权限等前提时，必须报告“未验证”及原因，不能静默跳过后出具全通过报告。新增或调整发布检查时应落实此规则；本规范本身不代表自动门禁已实现。

## 7. 验收报告模板

每次报告至少包含以下内容，详细记录放在 `docs/summery/`；本机敏感调试产物留在不入库目录。

```markdown
# <运行编号> OKR 验收记录
- 代码：提交、未提交改动、前后端版本
- 环境：公开 URL、实际实例、数据库是否共享
- 身份：chujiejie.1 / 储节节；会话与飞书身份核验结果；应用绑定
- 测试数据：专用页面、评论 ID、文档链接、通知回执及清理情况

| 用例与入口 | 模拟／真实 | 操作和结果证据 | 通过／失败／未验证 | 原因 |
|---|---|---|---|---|

- 部署后回归：具体域名、操作、结果
- 未覆盖项及限制：明确列出，不计入通过
- 结论：本次哪些功能已真实验证，哪些仍未验证
```

截图可证明可见交互；响应、持久化与飞书回读共同证明结果。对外报告不得包含完整 Cookie、访问令牌、刷新令牌或应用密钥，也不得用测试数量或 HTTP 200 概括业务全部可用。
