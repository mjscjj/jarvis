# OKR 人员搜索与评论反馈修复（2026-09-14）

用户反馈人员查询慢、重复搜索无缓存、发表评论后看不到新评论。

## 原因和最终行为

人员身份真源仍为配置指定的飞书通讯录，业务持久化使用完整企业邮箱。之前只对 Bot 通讯录全量拉取做了缓存，但当前过渡配置使用 user 查询，没有命中那条路径。user 查询每次串行执行人员搜索和头像查询；页面历史 Owner 的头像也逐人重复查通讯录，占用共享 CLI 并发。前端空结果使用新数组，还触发了头像组件反复更新。

现在在 Directory 层统一缓存 user 查询，所有 OKR 人员选择入口共用：查询与已验证邮箱有效期 5 分钟，相同在途请求合并；按应用和登录用户隔离，落盘私有缓存，重启可复用未过期结果，最多 512 个查询、2048 个人员。候选人立即返回，不等头像；已验证候选人的头像后台补齐，并限制为一个远程请求槽。没有近期身份缓存的历史 Owner 先显示姓名头像，不为每个历史 Owner 发起额外通讯录搜索。广泛查询保留已返回候选人和 has_more 提示。

评论及提醒意图事务提交后立即返回；主服务从持久化 pending 记录执行提醒，沿用跨进程原子领取、回执和未知状态核验，不自动补发历史失败提醒。前端显示等待/发送中状态，后台只刷新提醒状态。新评论插入本地列表并滚动到可见位置；旧列表响应不能覆盖新评论，父组件回调变化也不再清空评论。

## 验证

- 相同关键词真实 API 测量：旧实现连续两次 1.688、1.610 秒；隔离新实例首次 0.840 秒，缓存命中 0.000804、0.000638 秒。这是本机单次样本，不代表所有网络条件。
- Go 通讯录、评论服务、API、服务入口测试通过；前端类型检查和 181 项测试通过。
- 新缓存测试验证 8 个并发查询只有一次上游搜索、选择后的邮箱解析复用、头像不阻塞、重启复用和不同登录用户隔离。
- Playwright 使用隔离数据库，真实提交两条无 @ 评论，分别约 1.10、1.06 秒内完成点击、响应和滚动验证；故意延迟旧列表响应后新评论仍可见，浏览器无异常。脚本：web/test/okrCommentFeedback.browser.mjs；需要显式设置 OKR_BROWSER_URL 指向隔离实例。
