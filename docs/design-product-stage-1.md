# 第一阶段产品方案：单人本地的可信协作主干

> Status: proposal
> Authority: non-normative
> Last verified: 2026-08-04 @ `5baa104`

## 0. 一句话结论

下一阶段的产品重点不是增加自动化能力，而是把 Jarvis 与 Principal 之间的协作回路建成一条可信主干：

> Jarvis 能主动触达，Principal 能就地处置，每个判断可回溯，每个项目有落点。

当前系统的抽取和执行链路已经能跑通，卡点全部集中在人这一侧：Jarvis 停下来等人时没有渠道通知，
人想纠偏时只能打开本地后台，被压缩掉和被判定不做的事情不可见，多项目状态没有落点。
**能力已经够用，界面几乎不存在。**

第一阶段只服务一个本地 Principal，不做多用户、团队权限或 ToB 平台。

## 1. 用户与痛点

### 1.1 核心用户

- 同时参与多个项目的研发负责人、技术 owner 或核心 IC；
- 每天接收大量飞书群、私聊、会议、文档和代码仓库信息；
- 工作任务经常来自自然语言讨论、leader 交办、本人承诺或会议 follow-up，而不是正式工单；
- 需要频繁在项目之间切换，同时要求上下文不丢、执行可追溯；
- 愿意让 Agent 主动推进工作，但要求清楚知道它为什么做、做到哪一步、如何恢复。

### 1.2 痛点到产品能力的映射

| 痛点 | 对应产品能力 | 本方案编号 |
|---|---|---|
| 群聊里说过的事情容易漏 | 收件箱对称：把"发给我的"补齐 | B |
| 会议结论和行动项没有稳定闭环 | 协作主干上的确认与追问（会议线索采集已有） | A |
| 多项目并行时任务、进展、阻塞和仓库散落 | 项目工作台 | C |
| Agent 缺上下文，需要反复解释背景 | 上下文可见 + 世界模型卫生 | C、E |
| 自动化缺确认、审计、恢复和项目视图 | 协作主干 + 阻塞恢复 + 项目工作台 | A、C、D |

这五条痛点没有一条需要新的自动化能力来解决。它们全部落在"人与 Agent 之间的接口"上。

## 2. 从真实运行数据看当前差距

以下是本机 `var/jarvis.db` 在 2026-08-04 的快照，系统自 2026-08-02 起连续运行约两天。
数据量小，但差距已经足够清晰，且几条差距会随运行时间线性放大。

### 2.1 执行停在人这一侧，而人不知道

45 个 Task 中有 12 个处于 `awaiting_approval`，全部在最近一天内堆积；另有 1 个 `needs_human`。
系统提供了 `POST /api/tasks/:id/approve` 和 `reject`，但没有任何主动触达渠道——
Principal 必须主动打开 `127.0.0.1:18800` 才会发现有人在等他。

**产品含义**：一个停下来等待、而没人知道它在等的 Agent，比一个不启动的 Agent 更糟。它既占用了信任，
又没有产出结果。审批率不是提示词问题，是渠道问题。

### 2.2 覆盖范围由 43 个被选中的会话决定

已发现 4961 个飞书会话，实际采集的只有 45 个非 `cold` 会话（25 群、18 私聊、1 话题），
其中 13 个绑定了项目。私聊按活跃度自动纳入前 30 个，且排除 `p2p_target_type=bot`。

被采集的会话里，别人发的消息占多数（534 : 142），所以问题不是"只看得见自己说的话"，
而是**覆盖由会话热度这个与重要性无关的启发式决定**。有人在一个平时不说话的群里 @ 我、
或者一个新私聊第一次交办任务，恰恰是最不该漏的两类事件，而它们和会话热度没有关系。

**产品含义**："群聊里说过的事情容易漏"目前只在被选中的会话内成立。需要增加一条与热度无关、
以"Principal 是接收方"为条件的采集轨道。

### 2.3 不做的决定不可见

213 个 Todo 中 179 个是 `observing`（84%），另有 5 个 Task 执行后回到 `observing`。
这些判断很可能是对的——大量群消息确实不需要行动——但产品上没有任何位置让 Principal
扫一眼"Jarvis 看到了这些、决定不做"，也没有一键推翻的入口。

**产品含义**：Agent 的价值一半来自它做了什么，一半来自 Principal 相信它没漏。
不可见的"不做"不产生信任，只产生怀疑。用户发现一次漏报，就不会再信任这个产品。

### 2.4 失败是死胡同

9 个 Task 处于 `failed`，其中包括"SOP 上传任务被约 80 个文档无读取权限阻塞"。
这类失败的真实语义是"外部条件未满足，需要一个人去要权限"，不是"目标不可达"。
`failed` 之后没有恢复路径，也没有人被告知。

同时，Task 24 和 25 是同题重复（"梳理下周上线对外版 Bax 的上线 Checklist"）。
Todo 侧有向量去重，Task 侧没有，重复直接消耗审批注意力。

**产品含义**：需要区分"这件事做不成"和"这件事现在推不动"。后者必须有出口，而出口在人身上。

### 2.5 多项目没有落点

后台八个入口（Overview、任务、定时任务、待办、背景、设置、进度、运行状态）全部是按对象类型组织的，
没有项目视图。数据侧：7 个项目中 4 个已归档，33 个 Task 挂在同一个项目上，10 个 Task 没有项目；
项目 43「公会agent基建项目」与 44「公会 Agent 基建」近重复。

**产品含义**：核心用户的心智单位是项目，系统的组织单位是表。项目切换时的"上下文不丢"目前只对 Agent 成立
（`context_snapshot` 冻结在 Todo 上），对人不成立——人无法在一个地方看到某个项目现在的全貌。

### 2.6 世界模型只能追加，不能收敛

两天产生 593 条 Fact（project 261、group 198、task 76、person 58），其中同一次 SOP 权限申请
被叙述成多条高度重复的长文本。`relation_fact` 只有 1 条。

工具侧的原因很直接：`jarvis-tools` 有 `append-fact` 和 `list-facts`，**没有更新、合并或标记过期的能力**。
Person、Resource、Relation 都有完整 CRUD，Fact 只能追加。

**产品含义**：`goal.md` 要求世界模型能表达"这条曾经成立，现在被替代了"，当前工具集让这条要求无法落地。
一个持续运行的系统没有收敛机制，上下文质量会随时间下降——这会直接反噬"Agent 缺上下文"这个痛点，
因为噪声上下文和没有上下文同样糟。

### 2.7 差距总结

| 差距 | 证据 | 会不会随时间恶化 |
|---|---|---|
| 停下来无人知 | 12 个 `awaiting_approval` 无渠道 | 会：积压增长 |
| 覆盖取决于热度 | 4961 → 45 个采集会话 | 不会，但漏报后果一次即致命 |
| 不做的决定不可见 | 179 个 `observing` | 会：数量增长后更不可能人工翻 |
| 失败无出口 | 9 个 `failed`，含外部阻塞 | 会 |
| 多项目无落点 | 无项目页；10 个 Task 无项目 | 会：项目数增长 |
| 世界模型只能追加 | 593 条 Fact / 两天，无 supersede 工具 | 会：线性膨胀 |

## 3. 产品定位与第一阶段边界

### 3.1 定位

Jarvis 是**一个人的任务分身**：它替 Principal 盯住多个项目里那些不会变成工单的事，
在得到授权的范围内把事情做完，并且随时能解释自己为什么这么做。

它不是团队协作平台，不是工单系统，也不是通用 Agent 平台。第一阶段的全部设计取舍以
"单个 Principal 是否更省心、更放心"为唯一判据。

### 3.2 三条日常节律

Principal 与 Jarvis 的日常交互应该收敛成三个稳定时刻，而不是散落的一堆功能入口：

| 节律 | 时间方向 | 回答什么 | 当前状态 |
|---|---|---|---|
| 晨间简报 | 面向今天 | 今天最重要的是什么、先做什么 | 正在实现（`internal/morningbrief`） |
| 协作主干 | 过程中 | 需要你确认什么、卡在哪、要不要改方向 | **缺失，本方案主线** |
| 每日进度总结 | 向后复盘 | 今天实际发生了什么 | 已有，仅落盘未触达 |

晨报和日报都是"一次性播报"，它们不能替代主干：主干是双向的，承担确认、纠偏和解阻塞。
第一阶段的核心工作就是把中间这一格补上。

### 3.3 第一阶段原则

1. **补接口，不加自动化**：不新增执行能力，先把已有能力接到人身上；
2. **飞书是唯一主动触达面**：Principal 的注意力在飞书里，本地后台只承担深度查看和配置；
3. **结构化动作用结构化通道，语义用自然语言**：批准/驳回这类不可歧义的动作走卡片按钮，
   解释、纠偏、追问走自然语言，二者不混用；
4. **不定义编号协议**：序号会因重算漂移，把语义编码成协议与本仓库的取向相反；
5. **可见性优先于智能**：被压缩、被延后、被判定不做的内容必须可见且可一键推翻；
6. **项目是组织单位**：任何面向 Principal 的呈现都带项目；无法归属的要显式暴露；
7. **失败必须有出口**：外部条件不满足时求助，不静默终止；
8. **世界模型要能收敛**：能追加就必须能纠正和作废；
9. **能力缺失就诚实标注**：取证不全、渠道不可用时明确说明，不静默补写看似完整的结论；
10. **Go 侧只做机械动作**：路由、幂等、状态、留痕；判断留在提示词和 Skill 里。

## 4. 产品主线：五项能力

A→D 按依赖顺序排列，E 是支撑性工作，与它们并行。

### 4.1 A. 协作主干：飞书内的确认与纠偏

**要解决的**：Jarvis 停下来等人时没人知道（§2.1）；人想纠偏时只能开后台。

**产品形态**：Jarvis 在需要人的时候，向 Principal 私聊发一条消息。这条消息有两种成分：

- **一段自然语言**：它在做什么、调查到了什么、为什么需要你、不批准的后果是什么；
- **两到三个按钮**：批准、驳回、稍后再说。

Principal 点按钮完成处置；如果想改方向，直接回复这条消息说人话——"别发群里，先给我看看"
"范围缩到有权限的部分"。回复不构成批准，只作为补充信息进入这个 Task 的执行上下文。

**为什么必须这样分工。** 这是本方案最重要的一个设计判断：

> 批准是一个不可歧义的授权动作，必须由人做出结构化表达；纠偏是语义，必须保持自然语言。

如果让模型去解读"行吧你发吧"是不是批准，审批这道护栏就名存实亡了——它会退化成"模型自己决定
自己被授权了"。飞书交互卡片的按钮回调（`card.action.trigger`）天然携带 task 身份和动作，
这正是 `AGENTS.md` 允许严格协议的边界：机器协议可以严格，协议里的理由和正文继续保持宽松文本。

**绑定不靠编号，靠消息线程。** Jarvis 发出审批请求时，已经会把这次外发写进
`ExecutionRun.effects`（含 `message_id`）。Principal 的回复带 `reply_to` / `root_id`，
`message` 表已有这两个字段。因此"这句回复属于哪个 Task"是一次机械查找，不需要编号协议，
也不需要新表：**外发 message_id → effects → Task**。

**前置条件必须先决策**：Jarvis Bot 的 `im.message.receive_v1` 当前由 CC Connect 独占，
Jarvis 不保留第二条 event consumer；同一 app 只能有一个事件连接拥有者，轮询侧也排除
`p2p_target_type=bot` 的私聊。也就是说**今天 Principal 回给 Bot 的消息既没有事件流、也不会被采集**。
三条路径：给 Jarvis 单独申请一个 app（推荐，边界最干净）、让 CC Connect 转发、或放开 bot 私聊采集。
这是一项独立基建决策，必须先做，A 的回程才存在。

**Go 侧边界**：卡片回调入口、按钮动作到既有 approve/reject 的机械映射、回复到 Task 的线程绑定与
supplement 写入。判断（要不要发、怎么写、发什么按钮）全在提示词。不新增审批状态，不新增流程阶段。

**先做只出不进的一半。** A 可以拆成两步独立上线：先让 `awaiting_approval` 和 `needs_human`
产生一条飞书通知（复用现有 `feishu-send-message` Skill，零 Go 改动），链路打通后再做回程。
第一步就能把 12 条积压变成当天可见。

### 4.2 B. 收件箱对称：把"发给我的"补齐

**要解决的**：覆盖由会话热度决定（§2.2）。

**产品形态**：增加一条与会话热度无关的采集轨道，条件是"Principal 是接收方"：

- 全部群里 @ Principal 的消息；
- 新出现的真人私聊（不受活跃度 Top N 限制）；
- 被指派为参与人、但 Principal 未发言的会议（会议巡扫已覆盖，需确认口径）。

**实现形态是一个 Skill 加一个定时器，不是新 Go 流水线。** 用
`lark-cli im +messages-search --as user` 定期搜 @ 我，把命中消息原样通过
`jarvis-tools append-clue` 投递进 M2，`(source, external_id)` 天然幂等。采集端只报原文，
不判断重要性——那是 M3 的事。这条轨道与现有 43 会话轨道重叠时由 M3 的去重承接。

**为什么不干脆全量采集 4961 个会话**：成本与噪声都线性上升，而增量价值集中在"点到我"这一小部分。
覆盖的正确方向是按"是否指向我"筛选，不是按数量堆。

**Go 侧边界**：零。新增 `source` 值 + 一份 Skill + 一个定时任务配置。

### 4.3 C. 项目工作台：多项目切换的落点

**要解决的**：多项目状态散落（§2.5）；Agent 上下文对人不可见（§1.2）。

**产品形态**：一个页面，选中一个项目后一屏回答四个问题：

1. **现在有什么在推**：未闭环 Task 及其状态，特别是等我批准和等外部条件的；
2. **卡在哪**：当前阻塞及各自的责任人；
3. **最近发生了什么**：该项目的进展事实与关键消息，按时间排列；
4. **它是什么**：仓库与本地路径、关键人、关键群、背景说明——即 Agent 执行时用到的上下文。

第四块是"上下文可见"的落点：Principal 能看到 Agent 拿到的项目背景，才能相信它不需要被反复解释；
发现背景写错时就地改掉，比在对话里解释一遍更省事。列表按仓库既有约定优先行内编辑。

同一页要显式列出**无法归属项目的 Task**（当前 10 个），否则它们会永久沉底。

**Go 侧边界**：以现有 Task/Fact/Project/Group/Resource 查询接口为主，缺一个按项目聚合的只读查询即可。
不新增表，不改执行链路。

### 4.4 D. 阻塞与恢复：failed 不是终点

**要解决的**：外部阻塞被判定为失败，没有出口（§2.4）。

**产品形态**：语义上区分两件事——

- **目标不可达**：确认这件事不该做或做不成，进入 `failed`，并说明结论；
- **外部条件未满足**：权限没批、别人没回、环境没就绪。它应该走 `waiting`（有明确等待条件）
  或 `needs_human`（需要人推一把），并通过 A 的主干向 Principal 求助：卡在什么、需要你做什么、
  不处理的后果。

**这不需要新的状态枚举。** `waiting`、`needs_human`、`failed` 三个状态已经够表达；
缺的是判断口径（写进 `conf/prompts/m5-system-prompt.md` 和 `conf/rules/m5.md`）和求助渠道（A）。
按 `AGENTS.md`，"这是权限没批还是真的没权限"是语义判断，不能变成 Go 里的分支。

Task 侧的同题重复（§2.4）另作处理：固化前按项目 + 目标做一次语义查重，或在执行 Agent 的调查
环节要求先检索是否已有等价 Task。倾向后者——它是判断，不是机械去重。

### 4.5 E. 世界模型卫生

**要解决的**：Fact 只能追加，世界模型会随时间劣化（§2.6）。

**产品形态**：给巡视 Agent 补上收敛能力，不新增模块。需要三件事：

1. **工具补齐**：Fact 需要更新、合并和标记过期/被替代的能力，与 Person、Relation 对齐。
   这是 `goal.md` 里"时效性"这条要求的落地前提；
2. **职责写进提示词**：巡视 Agent 每轮除了看护未闭环工作，还要收敛重复叙述、把过期结论标掉、
   合并重复项目与人物；
3. **写入纪律**：同一事件不重复叙述，长过程写一条带演进的事实，而不是每步各写一条。

**判定标准是渐进披露真的能用**：默认注入模型的是摘要，模型按需详查。当同一事件有五条近重复叙述时，
摘要必然失真——所以这项不是"整理数据"，是保证上下文质量的必要条件。

## 5. 交付顺序

每一步都能独立上线并单独验证，前一步不通过不做下一步。

| 阶段 | 内容 | 换来什么 | 通过标准 |
|---|---|---|---|
| S0 | 待处置事项的飞书通知（只出不进） | 积压当天可见 | 出现 `awaiting_approval`/`needs_human` 后 Principal 在飞书收到通知，不需打开后台 |
| S1 | Bot 事件所有权 + 卡片按钮处置 + 回复纠偏 | 主干闭合 | 在飞书内完成批准/驳回，回复能进入该 Task 上下文且不构成批准 |
| S2 | 收件箱对称（@我 + 新私聊） | 漏事概率下降 | 一次群内 @ 我在数分钟内成为线索并被判断 |
| S3 | 项目工作台 | 多项目切换有落点 | 单页回答 §4.3 四个问题；无项目 Task 显式可见 |
| S4 | 阻塞恢复口径 + 世界模型卫生工具 | 长期可用 | 外部阻塞不再进 `failed`；Fact 可标过期与合并 |

S0 依赖晨报正在建设的投递路径，成本最低、收益最直接，应当立刻做。S1 的前置是一项基建决策，
决策没做完之前不要在任何产物里承诺"回复即可推进"——让用户对着一个不存在的入口说话，比不做更糟。

## 6. 关键产品判断

**为什么不做文本命令协议。** `推进 1`、`延后 2` 这类协议要求用户记住编号，而编号会因重算漂移；
它还把语义编码成了协议，与本仓库"让模型理解自然语言"的取向相反。结构化动作交给按钮，
其余保持自然语言。

**为什么批准不能由模型解读。** 见 §4.1。审批的价值在于"人明确表达过同意"，一旦这个动作由模型
从自然语言推断，护栏就只剩形式。这也是代码可以严格校验的少数边界之一。

**为什么先做界面而不是 Goal / Verifier。** [长任务 Goal Control](design-long-horizon-agent-goal-control.md)
解决的是"局部成功被误当作目标完成"。这个问题真实存在，但当前数据里的主要损失不是错误关单，
而是 12 个 Task 停在那里没人知道、9 个 Task 失败没人接手。**先修损失最大的那一段。**
Goal Control 的价值会在主干闭合、任务真正跑起来之后显现。

**为什么不扩大采集到全部会话。** 见 §4.2。重要性与热度无关，也与数量无关；正确的筛选条件是
"是否指向我"。

**为什么不做多人协作。** 单人闭环还没跑顺，引入成员、权限和共享视图会立刻污染核心判断链路，
并把每个决定都变成需要考虑他人的决定。第一阶段的所有产品判断都以一个人的体感为准。

## 7. 第一阶段不做什么

- 多用户、租户、团队空间、成员权限、经理视角；
- 文本命令协议与编号协议；
- 为审批新增状态、流程阶段或按 `action_type` 分流；
- 全量采集全部飞书会话、Drive 和远端仓库；
- 新的执行能力、新的自动化场景、新的来源专用 Go 流水线；
- 富交互排程界面（拖拽、日内自动重排、日历写入）；
- 独立 Verifier、Goal Store、Supervisor（留给后续阶段）；
- 为数据源失败增加静默 fallback。

## 8. 验收标准

产品层面用可判定的标准，不用主观感受。

**A 协作主干**

- 每一个进入 `awaiting_approval` 或 `needs_human` 的 Task，都在数分钟内产生一条飞书私聊消息，
  且同一 Task 不重复触达；
- Principal 在飞书内可以完成批准和驳回，动作落到既有 approve/reject 入口并留痕；
- 自然语言回复进入对应 Task 的 execution supplements，且**在任何情况下都不产生批准效果**；
- 渠道不可用时后台可见明确错误，不静默丢弃。

**B 收件箱对称**

- 一次群内 @ Principal 在一个采集周期内成为线索并被 M3 判断；
- 与既有轨道重叠的消息不产生重复 Todo；
- 采集端不做重要性判断，投递内容为原文。

**C 项目工作台**

- 单页回答 §4.3 的四个问题，且每条待处置事项可直接跳到 Task；
- 无项目归属的 Task 显式列出；
- 项目背景、仓库和关键人可就地编辑，编辑后 Agent 下一次执行即读到新值。

**D 阻塞与恢复**

- 因外部条件不满足而停止的事项不进入 `failed`，而是产生一次求助或明确的等待条件；
- 同一目标不产生两个并行 Task。

**E 世界模型卫生**

- Fact 可被标记过期或替代，模型能在不新增表的前提下完成收敛；
- 同一事件在摘要视图中只出现一条当前有效叙述。

## 9. 最大风险

**信任崩塌，而且是单点的。** 用户发现一次"重要的事没出现"，或者被同一件事重复打扰三次，
这个产品就失去了它唯一的用户。两条对策必须内建，不能靠事后调优：

- **漏报侧**：被压缩、被延后、被判定不做的内容必须可见且可一键推翻（§2.3、§4.3）；
  产物里保留"另有 N 项未呈现"这类计数，宁可少写也不省掉；
- **打扰侧**：主动触达按 Task 去重，同一事项一次只发一条；节律固定（晨报、主干、日报），
  不做随机推送。

次级风险是**世界模型劣化**：它不会在一周内暴露，但会在一个月后让所有判断变差。E 因此不能一直排在最后。

## 11. 最终产品判断

第一阶段成功的标准不是 Jarvis 能做更多事，而是：

1. Jarvis 需要人的时候，人当天就知道，并且在飞书里就能处置完；
2. 指向 Principal 的信息不再依赖会话热度这种与重要性无关的启发式；
3. 任何一个项目的当前状态、阻塞和背景，一屏可见，就地可改；
4. 推不动的事情会求助，不会静默失败；
5. 世界模型在连续运行一个月后仍然可用，而不是被自己的记录淹没。

这五条都不需要更强的模型。它们需要的是一条真正闭合的人机主干。
