# Agent 基建 2026 Q4 OKR：基于 Q2/Q3 历史的方向建议

> Status: research snapshot
> Authority: non-normative
> Last reviewed: 2026-09-10
>
> 研究边界：本文刻意不使用当前正在编写的 Q4 草稿作为判断依据，只依据 Q2 技术规划、Q3 正式 OKR、Q3 Runtime 迁移与上线验收、近期线上问题和历史管理反馈反推 Q4。

## 一句话结论

Q4 最自然的主题不是继续“补齐组件”，而是：

> **把 Q3 已统一并上线的 Agent 底座，推进成能可靠完成端到端工作、能用真实结果持续优化、能被新业务低成本复用的生产平台。**

对应的历史演进可以概括为：

- **Q2：搭出来**——SaaS 化、多租户、Gateway、Skill、RAG、后台等基础链路从 0 到 1；
- **Q3：统一并上线**——融合 Eino / OpenClaw 路线，迁移核心业务，验证新 Runtime 不降质并改善性能；
- **Q4：完成工作并规模化**——从“能问答、能查数、组件能用”跃迁到“能完成复杂任务、生产可信、资产可复制”。

## 从 Q3 看到的三个未完成命题

### 1. “基座上线”不等于“任务可靠完成”

Q3 正式 OKR 的 Agent 基建 KR 聚焦统一底座、多租户、RAG、Skill 平台、工具/Agent 网关、沙箱和长任务能力。[1] 8 月的新 Runtime 迁移又覆盖渠道、会话、模型、Tool/MCP、Skill、沙箱、协议、评测和发布等十余个能力域。[2]

这些工作说明平台已经跨过“有没有”的阶段，但上线后反复出现的问题——会话续流/停止、Checkpoint、SubAgent、Skill 装载与路由、模型 fallback、授权、数据一致性、跨渠道展示——都指向同一个未完成结果：**Agent 是否能稳定地把一件复杂工作做完。**

### 2. “有评测”不等于“质量可工程化”

Q3 已完成 235 条生产用例的新旧 Runtime 对比，质量没有回退，7 个评测集平均耗时改善；但真实用户反馈仍持续暴露 Prompt/Skill 版本回退、数据口径不一致、trace 丢失和环境差异。[3]

下一阶段不应只增加评测用例，而要形成：**线上问题进入评测集 → 变更前自动回归 → 灰度/回滚 → 线上结果再次验证**的闭环。评测对象也应从文本回答扩展到环境中的最终结果、工具副作用和禁止行为。[6][7]

### 3. “组件齐全”不等于“平台可复用”

早期技术路线已经给出一个很强的不变量判断：模型和 Runtime 会变化，但 Wiki、Skill、Tool、数据、安全护栏和业务知识是长期资产；Runtime 切换不应让这些资产归零。[4]

Q3 的迁移实践也证明，真正昂贵的部分往往不是 Agent loop，而是 tenant / identity / skill / tool / data / channel 之间的契约对齐。因此 Q4 的平台化结果应看**接入周期、资产复用率、版本一致性和跨场景成功率**，而不是又完成了几个后台页面或接口。

## Q4 可以考虑的五个 Objective 方向

下面不是建议全部都写。前三项是主线候选，第四、第五项是战略 bet。

### Idea A：从“回答问题”升级到“完成端到端工作”

这是最有历史连续性的方向。半年规划已经把 Q4 原始目标写成“完成用户端到端任务（非数据分析类）”，并列出 Agent 通信、多 Agent 协作和事件机制。[4]

可用的 O 表述：

> **O：让 Agent 从问答和单步工具调用，升级为能自主完成端到端复杂工作的执行系统。**

KR 可以围绕：

- 选定 3 类真实工作任务，达到约定的端到端成功率，而不是只验收 SubAgent、Sandbox 等组件；
- 长任务中断恢复率、停止成功率、重复副作用率达到生产门槛；
- SubAgent 在真实任务中证明相对单 Agent 的成功率、耗时或成本收益；
- 跑通至少 1 类事件触发或定时任务，让 Agent 从被动问答迈向主动完成工作。

适合作为 initiative 的内容：Checkpoint、Task 状态机、SubAgent、沙箱、HITL、事件机制。它们不要直接写成 KR。

### Idea B：建立以真实结果为核心的 Agent 质量系统

可用的 O 表述：

> **O：让 Agent 的质量从依赖人工体验，变成可度量、可回归、可持续改善的工程系统。**

KR 可以围绕：

- 核心任务用权威数据或环境最终状态判定成功，形成事实、流程、工具、跨渠道和安全负向评测集；
- 100% 核心 Prompt / Model / Skill / Tool 变更经过生产等价回归与版本留痕；
- 线上高优 bad case 在约定时间内沉淀为回归用例，同根因重复问题明显下降；
- 建立质量、时延、成本三者的联合基线，优化以“单次成功任务成本”为目标，而不是只压 token 或响应时间。

这个方向可以把算法和工程真正绑在一起，也回应了历史上“Agent 基建规划要与算法方案一起给”的要求。[3]

### Idea C：把生产可靠性做成平台默认能力

可用的 O 表述：

> **O：建设业务敢依赖的生产级 Agent Runtime，使每次执行可恢复、可追踪、可治理。**

KR 可以围绕：

- 核心链路 SLO、Tool Call 成功率、P95 任务时延和故障恢复达到约定门槛；
- trace 能串联输入、模型、Prompt/Skill 版本、Tool Call、状态、结果和副作用，核心任务完整率达到门槛；
- 高优问题定位时间和恢复时间显著下降；
- 关键发布具备灰度、自动回归、回滚和变更归因，同类发布回退显著减少。

如果季度资源有限，Idea B 和 Idea C 可以合成一个 O：“可信生产系统”。

### Idea D：把 Agent 资产做成可复制的接入平台

可用的 O 表述：

> **O：让新 Agent / 新业务接入从项目制开发，变成基于标准资产的低成本复制。**

KR 可以围绕：

- tenant / agent / identity / context / skill / tool 的核心模型和继承覆盖规则统一；
- 新业务从条件具备到首个生产成功任务的接入周期降低；
- Skill 的创建、调试、评测、发布、灰度、回滚和效果分析形成闭环；
- 至少 2—3 个新增场景复用同一套 Gateway、Skill、Tool、RAG 和观测能力，复用率或重复开发量有证据改善；
- 同一指标跨 Skill、渠道和租户的数据结果保持一致且来源可追溯。

这个方向的重点不是“平台功能更多”，而是证明平台让交付变快、质量更稳。

### Idea E：Context / Memory / Ontology 成为下一代差异化能力

这是可选的 aspirational bet，不建议与生产收口混在一个 committed O 里。

可用的 O 表述：

> **O：验证结构化 Context 与长期 Memory 能否显著提升 Agent 对人、项目和业务状态的理解。**

KR 可以围绕：

- 用最小实体模型跑通项目状态整理、风险识别或行动跟进等真实工作流；
- 由真实天使用户连续使用，并证明信息收集时间、遗漏率或状态准确性改善；
- 明确继续投入、调整或停止的产品决策，并沉淀可复用的 context / memory / event 原子能力。

这个方向很有潜力，但如果没有明确用户、任务和验证周期，容易重新落入“建设 ontology 能力”的活动型 KR。

## 三种组合方案

### 方案一：稳健型——适合 Q3 刚完成大迁移，需要先收口

1. O1：建设业务敢依赖的生产级 Agent Runtime；
2. O2：建立以真实结果为核心的质量与自进化闭环；
3. O3：让 Agent 资产可以低成本复制到新业务。

优点是确定性强，能把 Q3 暴露的问题彻底收住；缺点是季度故事偏“工程治理”，能力跃迁感稍弱。

### 方案二：进取型——更符合历史规划，我更推荐

1. O1：让 Agent 能完成端到端复杂工作；
2. O2：建立可信的生产运行与质量闭环；
3. O3：让平台资产被多个业务低成本复用。

它的逻辑是：**能力上限、生产下限、规模效率**。三个 O 相互独立，又能形成完整叙事。

### 方案三：探索型——如果高层希望 Q4 押注下一代形态

1. O1：可信生产系统；
2. O2：端到端复杂任务；
3. O3：Context / Memory / Ontology 天使用户验证。

这会牺牲部分平台接入效率建设，换取差异化探索。只有在用户、场景和资源已经明确时才值得选。

## 我最推荐的一版 OKR 骨架

### O1：让 Agent 从“能回答”升级为“能可靠完成端到端复杂工作”

- KR1：在 3 类真实复杂任务上建立生产等价评测，端到端成功率相对 Q3 基线提升明确幅度或达到约定门槛；
- KR2：长任务的中断恢复、停止、重试和副作用幂等达到生产门槛，无结果丢失和重复执行；
- KR3：SubAgent / 多 Agent 在至少 2 类任务上证明相对单 Agent 的净收益；
- KR4：至少 1 类事件触发或定时工作流被真实用户持续使用并完成闭环。

### O2：建立以真实结果为准绳的可信生产与质量闭环

- KR1：核心评测由权威数据、环境状态或人工校准判定，覆盖事实、流程、工具调用和安全负向场景；
- KR2：核心 Prompt / Model / Skill / Tool 变更 100% 经过生产等价回归、灰度和版本留痕；
- KR3：核心执行 trace 完整率、SLO、Tool 成功率、P95 时延和单次成功任务成本达到约定门槛；
- KR4：高优线上 bad case 在约定时限内进入回归集，同根因重复发生率和平均恢复时间显著下降。

### O3：把 Agent 能力沉淀为可复制的平台资产

- KR1：统一 tenant / agent / identity / context / skill / tool 的标准模型和版本契约；
- KR2：打通 Skill 全生命周期，核心生产 Skill 的评测、发布、灰度、回滚和效果追踪覆盖率达到 100%；
- KR3：至少 2—3 个新增业务场景通过标准链路接入，接入周期和重复开发量相对 Q3 明显降低；
- KR4：核心数据和工具在不同 Skill、租户与渠道间保持一致、可追溯，关键跨端工作流端到端运行一致。

## 再深入一层：Q4 真正要跨越的架构台阶

### 1. 从 Session Runtime 转向 Task Runtime

Q3 的大部分能力仍围绕“用户发来一条消息，Agent 在一个 session 中回答”组织。但 Q4 如果真的要完成非查数类端到端工作，核心抽象就不能继续只是 session，而应该出现独立的 **Task / Run**：

- 一个 Task 有明确目标、输入、当前状态和完成判据；
- 一次或多次 Run 可以执行这个 Task；
- Run 可以暂停、恢复、取消、重试和超时；
- SubAgent 是 Run 的子执行者，而不是一次隐形的模型调用；
- Artifact 是 Task 的结果，Effect 是 Task 对外产生的副作用；
- identity、tenant、tool、trace 和 approval 都跟随 Task/Run，而不是靠上下文猜测；
- 评测判断的是 Task 最终是否完成，不只判断最后一条回答好不好。

这个抽象能统一解释 Q3 的很多分散问题：

| Q3 表面问题 | Task Runtime 下的本质 |
|-|-|
| 断流后无法继续、停止不彻底 | Run 生命周期和 checkpoint 不完整 |
| session status 修改导致 Workspace 故障 | 会话生命周期与任务运行态混在一起 |
| SubAgent 方案难验收 | 缺少父子 Task、状态和结果协议 |
| 飞书文档、Sheet、HTML、图表交付不稳定 | Artifact 没有统一登记和交付协议 |
| HITL 在不同渠道表现不一致 | Approval/Interaction 没有成为执行协议的一部分 |
| trace 能看到模型但看不到完整工具链 | 没有围绕一个 Run 贯穿所有执行事件 |
| Agent 说完成但实际写入失败 | Final answer 被误当成 Task outcome |

因此，如果想让 Q4 有鲜明的技术跃迁，可以把 O1 的内核理解为：**建立面向工作的 Agent Task Runtime**。Checkpoint、SubAgent、事件机制、定时任务、HITL 和产物管理都是它的能力，不再是六条平行建设线。

### 2. 从“自动评测分数”转向“可信测量系统”

当前 BAX 线上样本里，普通回答通过率约 73%、workflow 约 91%、总体约 79%—82%；但 judge 对同批样本的两次判断约有 25% 不一致。[3] 这意味着现在最急迫的问题不是把 OKR 写成“质量达到 90%”，而是先让这个 90% 可信。

Q4 的质量 KR 应分两层：

1. **测量可信度**：标注规范稳定、人工评审一致、judge-human 对齐、无法判断样本有明确处理规则；
2. **被测系统质量**：在可信口径下，任务成功率持续提升。

否则团队可能用一个自身漂移 25% 的 judge，去解释 2—3 个百分点的质量波动。那不是精细化运营，只是数字噪声。

建议把评测对象分为四级：

| 任务级别 | 示例 | 主要判定方式 |
|-|-|-|
| L1 信息任务 | 政策问答、知识检索 | 权威答案与引用来源 |
| L2 分析任务 | 指标分析、经营诊断 | 权威数据、计算过程、结论约束 |
| L3 产物任务 | 报告、飞书文档、Sheet、图表 | 最终产物存在且内容满足 rubric |
| L4 行动任务 | 配置活动、发送消息、更新系统 | 目标系统最终状态与副作用审计 |

Q4 的能力跃迁应该表现为 L3/L4 占比和成功率提高，而不只是继续优化 L1/L2。

### 3. 从“功能平台”转向“杠杆平台”

平台不是因为有租户后台、Skill Hub、Tool Gateway 就成立。平台成立的唯一证据是：**第 N 个业务场景比第一个更便宜、更快、更稳定。**

因此，平台复用不建议只写“接入 3 个场景”，还要证明：

- 新场景是否不需要修改 Runtime core；
- 是否主要通过配置、Skill、Tool 和 Context 接入；
- 首个生产成功任务用了多久；
- 复用了多少已经验证过的公共资产；
- 新场景产生的 bad case 是否能反哺公共评测和平台能力。

可以定义一个“标准链路覆盖率”：

> 通过既有 tenant / identity / skill / tool / eval / release 标准链路完成的生产场景数 ÷ 新增生产场景总数。

这个指标比“建设了多少平台功能”更能证明基建的组织杠杆。

## Agent 基建的北极星指标

如果只能选一个主指标，我建议使用：

> **Verified Task Success Rate（经验证的任务成功率）**：在约定任务集合中，经权威数据、环境状态或人工 rubric 验证为真正完成的任务数 ÷ 有效发起任务数。

它要按 L1—L4 任务等级、场景、租户和版本拆分，不能只给一个混合平均数。

它比以下指标更适合作为基建北极星：

- **WAU/PV**：主要受产品入口、运营推广和用户覆盖影响，基建只能共同负责；可以作为业务验收，不应成为基建唯一主指标；
- **Tool Call 成功率**：工具调用成功不代表任务完成；
- **自动 judge 分数**：测量系统尚未校准时不能代表真实质量；
- **Token/响应时间**：是效率和体验护栏，不是最终价值；
- **功能完成数**：只能证明交付活动，不能证明平台有效。

建议采用一主三辅的指标树：

1. **主指标**：分级 Verified Task Success Rate；
2. **可靠性护栏**：SLO、恢复率、重复副作用率、trace 完整率；
3. **效率护栏**：P95 完成时长、单次成功任务成本；
4. **平台杠杆**：Time to First Successful Task、标准链路覆盖率、公共资产复用率。

## 对外一页 OKR 与内部 roadmap 应该分开

对上汇报时，未必需要写三个 O。Q3 正式组织 OKR 里，Agent 基建本身只是 Tech 下的一条 KR。[1] 如果 Q4 仍处在类似层级，更好的写法可能是“一个 O + 四个结果 KR”，内部再按三条 workstream 管理。

### 领导对齐版：一个 O

> **O：将已上线的统一 Agent 基座升级为面向真实业务任务的生产执行平台，使复杂工作可可靠完成、质量可持续优化、能力可低成本复制。**

- **KR1——任务结果**：在三类代表性真实工作中建立 L3/L4 端到端验收，Verified Task Success Rate 达到基线之上的明确提升或目标门槛；
- **KR2——生产可信**：长任务恢复、停止、幂等、trace、SLO 和单次成功任务成本达到约定门槛；
- **KR3——质量闭环**：完成线上评测人工校准，核心变更 100% 经过生产等价回归；高优 bad case 能在约定时限内进入回归集并显著降低同根因复发；
- **KR4——平台杠杆**：至少 2—3 个新增场景通过标准链路进入生产，接入周期和 Runtime 定制量相对 Q3 显著下降。

### 团队执行版：三条 workstream

1. **Task Runtime**：Task/Run、Checkpoint、SubAgent、Event、Artifact、Effect、HITL；
2. **Quality Control Plane**：Eval、Trace、Release、Gray、Rollback、Feedback；
3. **Asset Platform**：Tenant、Identity、Skill、Tool、Context、RAG、Channel Protocol。

这样对上只讲结果和战略，对内才展开组件、Owner、排期和依赖。

## Q4 的优先级顺序

若资源不能同时覆盖所有方向，建议严格按以下顺序：

1. **先让测量可信**：没有可靠基线，就无法判断 Q4 是否改善；
2. **再建立 Task Runtime 最小闭环**：先选 2—3 类工作完成，不追求一次覆盖所有长任务形态；
3. **把线上问题变成发布闭环**：停止依赖人肉发现、临时 hotfix 和跨群追踪；
4. **用新增业务证明复用**：不提前做完整平台，围绕真实第二、第三个场景抽象；
5. **最后投入 ontology、自进化等前沿 bet**：必须有剩余资源和清晰验证场景。

建议资源大致按 **60% 生产收口与质量、25% 端到端任务能力、15% 新方向探索** 讨论，而不是让探索性能力与线上质量平均争抢人力。这是优先级讨论起点，不是固定配额。

## 一个可执行的季度节奏

### 10 月：定义结果，建立可信基线

- 明确 3 类代表性任务和 L1—L4 判定方式；
- 校准人工标注与 judge，确定基线可信区间；
- 定义 Task/Run/Artifact/Effect 最小协议；
- 把核心变更接入版本留痕和回归门禁。

### 11 月：跑通复杂任务与生产闭环

- 在真实场景跑通恢复、停止、SubAgent/HITL 和产物交付；
- trace 串起执行链路，线上 bad case 自动进入回归队列；
- 接入第二个场景，验证哪些能力真的可复用。

### 12 月：规模验证和战略决策

- 扩大真实任务样本，证明成功率、稳定性和成本改善；
- 用第三个场景验收标准接入链路；
- 对 Context/Ontology、事件型 Agent 或更强多 Agent 做继续/调整/停止决策。

## 指标怎么选，才不会把 OKR 写成项目清单

建议优先从以下八个结果指标中选，不必全部使用：

| 结果维度 | 推荐指标 |
|-|-|
| 能力上限 | 端到端任务成功率、连续步骤数、任务类型覆盖 |
| 长任务 | 中断恢复率、停止成功率、重复副作用率 |
| 质量 | 事实准确率、流程成功率、安全负向通过率 |
| 工程闭环 | 变更回归覆盖率、bad case 入库时长、同根因复发率 |
| 生产可靠性 | SLO、Tool Call 成功率、MTTR、trace 完整率 |
| 效率 | P95 任务时延、单次成功任务成本 |
| 平台复用 | 新业务接入周期、公共资产复用率、重复开发量 |
| 真实验收 | 核心任务复用率、连续使用、用户节省时间或完成量 |

具体数字不要凭空拍。Q4 第一周应先锁定 Q3 基线，再决定是写绝对门槛还是相对改善。已有 235 条生产用例可以作为质量与性能基线；新加的端到端工作任务需要单独建立 baseline。[3]

## 不建议直接写进 KR 的内容

- “完成 SubAgent / Sandbox / Tool Gateway / Agent Gateway”；
- “持续优化 Runtime / RAG / Skill”；
- “建设管理后台 / 观测平台 / 评测平台”；
- “支持若干业务需求”；
- “探索自进化 / 多 Agent / Ontology”。

这些都是 initiative 或 roadmap。只有当它们被改写为任务成功率、恢复率、接入周期、复用率或真实用户结果后，才是 KR。OKR 的基本原则也是 KR 应描述可验证的 outcome，而非活动清单。[5]

## 对齐时最值得先拍的五件事

1. Q4 是否明确押注“非查数类端到端工作”，还是先以 Q3 生产收口为第一优先；
2. 哪 3 类真实任务代表 Agent 能力上限，谁提供权威验收；
3. 复杂任务成功率、恢复率、SLO、接入周期分别采用什么 Q3 基线；
4. 平台至少要被哪 2—3 个新增场景复用，避免做成自我验收；
5. Context / Ontology 是正式季度 bet，还是只做小规模 discovery。
